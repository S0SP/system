What Is OpenClaw

OpenClaw is the orchestration layer, the connector between an LLM (like Claude, GPT, or Gemini) and your real-world tools.

The intelligence comes from the LLM you connect to it.

Think of the LLM as the brain: it reasons, plans, and decides what to do. OpenClaw is the hand: it executes those decisions across your files, messaging apps, shell, and APIs.

Here’s what OpenClaw offers:

  • A gateway3 that runs on your machine (Mac, Linux)

    This is the always-on server running on your machine that coordinates everything: your messaging apps, LLM, tools4, and memory.

  • A multi-channel messaging interface: WhatsApp, Telegram, and so on.

    You talk to the same assistant from all these apps, with shared context and memory, instead of managing a different bot per platform.

  • A skills platform with 5,400+ modular capabilities on ClawHub5.

    Skills6 are plain Markdown files that tell the agent how to perform a specific task, like checking your GitHub PRs or sending a Slack message.

  • A persistent memory system in plain Markdown files you own.

    The agent’s knowledge, preferences, and logs are stored as editable Markdown on disk, so you can inspect, version-control, and move its LLM context like code.

  • Proactive scheduling engine (Heartbeat7 + cron jobs) that acts without being prompted.

    OpenClaw can wake itself up on a schedule to check servers, triage email, or send summaries, instead of waiting for you to type a command.

  • Model-agnostic: plug in Claude, GPT, DeepSeek, Gemini, Grok, or local models via Ollama8.

    You can mix and match models (cheap vs powerful, cloud vs local) and route different tasks to different providers to optimize cost and performance.

How It Differs From Other AI Tools

Here’s how:

  • ChatGPT, Claude, Gemini: You prompt them, and they respond. They have no access to your email, no ability to run scripts, and no memory once you close the tab9.

  • Siri, Google Assistant: Polished products, but closed ones. You can’t add custom skills, connect arbitrary APIs, or self-host them.

  • LangChain, CrewAI, AutoGen: Developer frameworks. You write the Python, define the chains, and build the interfaces from scratch. OpenClaw ships all of that out of the box.

  • Claude Code, Codex CLI: Terminal tools for coding sessions. Reactive and session-based. OpenClaw runs 24/7 for everything, not just code.

So OpenClaw is NOT just a product you use in a browser tab.

It is a service that runs on your machine and continues to work while you’re away.

How OpenClaw Processes Messages

Imagine you send a single Telegram message at 9 pm:

“Check my open PRs and let me know if anything needs a response tonight.”

You lock your phone and go to sleep…

By morning, you will have a reply:

Three PRs are open, and one has a teammate's review comment asking about error handling. OpenClaw drafted a response and flagged it for your approval, leaving the other two untouched because they were still in CI. It also remembered that last week you said you prefer to handle auth-related reviews yourself, so it left the one in the auth module alone.

None of this required you to open GitHub, write a prompt, or copy anything between tabs…

Why OpenClaw Runs 24/7 on Your Machine

When you run the OpenClaw gateway, you start a Node.js server that binds to port 18789 and stays running.

This is the fundamental difference between OpenClaw and a browser-based AI tool…

Every mainstream AI assistant, including ChatGPT, Claude, and even DeepResearch mode, only exists while you have a tab open. (DeepResearch can run a long session, but once it’s done, it stops.)

i.e., if you close the tab, everything disappears.

But OpenClaw never stops:

It runs as a background daemon on your local server and stays alive whether you are at your desk or asleep. That persistence is the foundation of everything else: scheduled jobs, proactive alerts, multi-channel messaging, and long-term memory. None of it works without a process that is always on.

This central server is called the Gateway…

Gateway: Control Center of Your Agent

The Gateway orchestrates everything.

It sits between your messaging apps, LLM, and tools, coordinating every request from the moment it arrives until a reply goes back out.

When a message arrives from Telegram, WhatsApp, or Slack, the Gateway authenticates the sender and creates or retrieves a session for the conversation.

It then assembles the full context10, passes it to the LLM, handles any tool calls that come back, and routes the final reply to the correct channel.

Say you ask the agent to clean up old log files:

Before it runs anything, the Gateway intercepts the shell command and sends you a confirmation request through Telegram: “I’m about to run $ rm -rf ~/logs/*.log, approve this?”

Nothing executes until you say yes… If you don’t respond, it waits…

The Gateway also serves the Control UI at http://localhost:18789.

It’s a browser-based dashboard that lets you watch the agent’s reasoning in real time, approve pending commands, and inspect active sessions. Every tool call, model response, and approval request shows up here live. Since the Gateway runs on your Mac Mini or VPS, you can access the Control UI from any browser on the same network. If you use Tailscale11, you can reach it from your phone or laptop without being on the same network.

The Gateway also supports hot configuration reloads…

You can change your model, update permissions, or add a new channel without restarting the process. The running server picks up the changes and applies them immediately.

Channel Layer: How OpenClaw Talks to Messaging Apps

OpenClaw connects to Telegram, WhatsApp, Slack.

Each of these works completely differently at the protocol level:

  • Telegram uses a bot token with polling or webhook delivery.

  • WhatsApp uses a reverse-engineered web protocol; it requires QR-code authentication and stores session state locally.

  • Slack uses Socket Mode with two separate token types.

  • Discord uses a gateway WebSocket with its own heartbeat requirements.

Without a dedicated abstraction layer, each new platform requires touching the routing logic, session management, and message pipeline.

OpenClaw solves this with a Channel Layer:

It treats each platform as a separate plugin acting as a translation adapter. Each adapter translates incoming messages into a standard internal format: a stable identity key, content, metadata, and attachments. Only then does it pass anything to the Gateway. Everything after that boundary is platform-agnostic. The agent has NO idea whether your message came from Telegram or Slack.

It sees a normalized message and responds accordingly…

This also means security policies like allowlists, pairing workflows, and mention-gating apply uniformly across all platforms rather than being reimplemented per channel.

LLM Layer: Where Reasoning Happens

OpenClaw is a brain socket.

You provide the intelligence by connecting an API key. And it provides the infrastructure for everything else.

It means you can use Claude, GPT-4, Gemini, DeepSeek, or a locally run model via Ollama. Plus, you can change models at any time without any reconfiguration.

When a message arrives at this layer, OpenClaw assembles a system prompt by combining the agent’s configured personality, list of available skills, relevant memory retrieved from previous sessions, and current conversation history.

It then calls the AI model with the full context.

If the model decides it needs to take an action, run a shell command, search the web, read a file, or call an API, it signals that as a tool call. OpenClaw executes the tool, captures the output, and feeds the result back into the conversation. The model reads the result and decides what to do next: call another tool, or produce a final answer.

This loop continues until the model generates a response with no further tool requests.

You can watch this entire loop unfold in real time in the Control UI at every tool call, every model response, every intermediate step…

And when a conversation reaches the model’s context limit, compaction12 triggers automatically. The agent summarizes the conversation so far and replaces the raw message history with that summary, preserving continuity without the cost of loading thousands of tokens on every reply.

Plugin System: How OpenClaw Stays Modular

Almost everything in OpenClaw that is not part of the core engine is implemented as a plugin13:

  • Telegram integration is a plugin.

  • GitHub access is a plugin.

  • The memory system is a plugin.

This is what makes OpenClaw easy to extend and customize…

When OpenClaw starts, it reads your configuration and loads only the plugins you have enabled. Disabling a capability means changing one line in your config, while adding a community plugin is as simple as placing it in the right directory.

If you want to write your own, you just implement a defined interface and never touch the core engine.

Plugins can hook into lifecycle events at every meaningful point: before and after tool calls, before and after messages, at session start and end.

This is how you add things like audit logging, rate limiting, or custom approval flows without touching the core agent at all…

Memory System: How Agent Remembers You

The memory solution (loading the entire conversation history into every prompt) fails quickly.

A week of active conversation will overflow any context window… Even if it fits,,, loading all of it on every reply is expensive and slow…

OpenClaw treats short-term continuity and long-term recall as separate problems that need different solutions:

  • Short-term memory keeps the current conversation on track. Every session is saved as a file on disk. When you send a message, OpenClaw loads only the recent part of that session into context, just enough to keep things flowing without loading everything at once.

  • Long-term memory handles recall across days and weeks. All past sessions are indexed into a local database. Before the agent answers any message, the memory indexer searches the database and pulls in any relevant information automatically. If a conversation from five days ago is relevant, it gets included. You never have to remind the agent of something it already knows.

  • Standing notes are a third layer. These are Markdown files you write yourself, stored in ~/.openclaw/workspace/memory/. Think of them as a permanent briefing document. Your preferences, your projects, your context. The agent reads them every time.

How OpenClaw Handles Tasks That Take Hours

Most interactions with OpenClaw are fast… You send a message; the agent calls a tool, and replies in seconds.

But some tasks take much longer: scraping hundreds of pages, running a full test suite, processing a large dataset, or coordinating a multi-step workflow across several APIs.

OpenClaw handles these differently:

When a task is going to take a while, the agent does NOT hold the conversation open and make you wait. It acknowledges the task, starts working, and messages you when it’s done. You can lock your phone and walk away.

The Gateway keeps running and messages you when the task is done.

For tasks that span multiple sessions or require human input mid-way, the agent completes what it can, writes the current state to MEMORY.md or a workspace file, and then pauses. When you return and pick up the conversation, it resumes from the saved state.

NO context gets lost between sessions because important state was written to disk, not held in memory.

For truly long-running background jobs, cron jobs in isolated session mode are the right tool. Each run gets its own session, completes its work, delivers output to your channel, and exits cleanly. The next scheduled run starts fresh.

This keeps long-running automation from accumulating stale context over time.

One practical limit worth knowing: if a single tool call takes too long, Gateway will time out waiting for a response.

For tasks like large web scrapes or slow API calls, break the work into smaller chunks. Instruct the agent to process in batches and report progress between each batch, rather than attempting everything in a single tool call.

How a Message Travels End to End

Here’s what happens when you send a message (step-by-step):

  1. You send “Check my open PRs” from Telegram.

  2. Telegram Servers route the message to your Gateway via webhook or polling14.

  3. Channel Adapter normalizes the message into a standard format.

  4. Gateway authenticates the sender, creates a session, and fires the beforeMessage hook.

  5. LLM then assembles a system prompt from your personality config, available skills, retrieved memory, and conversation history.

  6. The LLM recognizes this request requires GitHub skill, reads its instructions, and issues a tool call.

  7. Gateway executes the tool call, captures the result, and feeds it back to the LLM.

  8. LLM drafts a summary and creates a final response.

  9. Gateway broadcasts the completion to the Control UI and routes the reply back through Telegram.

  10. You receive the reply.

How to Set Up OpenClaw on Your Machine

Setting up OpenClaw means deploying a persistent server on your Mac Mini or VPS15.

It will run in the background, hold your API keys, and have access to your files, shell, and messaging apps.

Plus, commands change frequently, so always check docs.openclaw.ai for the latest.

Installation

Install OpenClaw via the official installer at openclaw.ai or with:

$ npm install -g openclaw@latest

Verifying the setup

Send your agent a simple message. If it replies, the Gateway is running, your model provider is connected, and your channel is live.

Also try these commands:

Quick connectivity check

$ openclaw health

Full diagnostic

$ openclaw doctor

Switching to allowlist mode

By default, OpenClaw uses pairing mode for Telegram DMs, meaning the bot only responds after you explicitly approve a sender.

For personal use, switch to allowlist mode and add your own Telegram user ID to the config. This ensures only you can interact with the agent.

Your Workspace: Files To Define Your Agent

Most software stores its configuration in databases, cloud accounts, or proprietary formats that you cannot inspect without the app itself.

OpenClaw takes an opposite approach…

Your agent’s entire identity lives in plain Markdown files in a single directory on your Mac Mini or VPS, accessible from your local laptop at any time.

~/.openclaw/

├── openclaw.json        # Main config: models, channels, plugins, permissions

└── workspace/

    ├── SOUL.md          # Agent personality, values, and behavioral rules

    ├── AGENTS.md        # Session startup procedures

    ├── USER.md          # Information about you: preferences, timezone, context

    ├── MEMORY.md        # Long-term memory that persists indefinitely

    ├── IDENTITY.md      # Agent name and persona

    ├── HEARTBEAT.md     # Proactive monitoring behavior

    ├── TOOLS.md         # Tool usage instructions

    └── skills/          # Your custom and installed skills

  • SOUL.md is the most important file. It defines who the agent is. Think of it as an employee handbook that the agent follows 24/7. Most effective SOUL.md16 files are 50-150 lines long. Specific instructions produce specific behavior.

  • AGENTS.md defines what the agent does at the start of every session. It reads SOUL.md, USER.md, and recent memory files before doing anything else.

  • USER.md is where you tell the agent about yourself. Your time zone, role, team structure, and tech stack you work on. The projects that are always in scope. These are standing facts it needs from the start, not preferences it infers over time (this goes in MEMORY.md).

  • MEMORY.md is where knowledge that persists across weeks and months lives. The agent writes it when you explicitly tell it to remember something (“Remember this: I prefer PRs under 400 lines”). You can also edit it directly, which is often faster.

  • HEARTBEAT.md defines what the agent checks on each heartbeat pulse and what threshold triggers an alert.

The practical value of plain Markdown becomes clear when something goes wrong or when you want to migrate machines.

If the agent starts behaving unexpectedly, you open SOUL.md and see exactly which instruction is causing it. If you get a new machine, you copy the workspace folder and the agent comes with it: personality, memory, skills, and all.

If OpenClaw is replaced by something better, your data is in a format every tool on earth can read…

Skills and ClawHub: How to Extend Your Agent

OpenClaw ships with over 50 built-in capabilities for GitHub, browser control, Docker, and so on.

But if OpenClaw injected the full instructions for every skill into every system prompt, it would consume thousands of tokens before you typed a single message. A prompt bloated with 50 separate instruction sets is slow, expensive, and mostly irrelevant to whatever you are actually asking.

Skills solve this with the lazy-loading pattern…

How skills actually load

At startup, OpenClaw scans all available skills and extracts two pieces of information from each: name and one-line description.

Then store these in a lightweight index and inject them into every system prompt inside <available_skills> block. When the agent decides a skill is relevant to your request, it reads that skill’s full instructions from disk and follows them.

Full instructions for a skill get loaded only when the agent determines they are relevant…

If you ask about your open PRs, the agent reads the GitHub skill instructions mid-conversation, executes them, and returns the result. GitHub skill instructions never appear in conversations about your calendar or your file system.

i.e., each conversation carries only the context it actually needs.

Where skills live

Skills exist at three levels, resolved in order of precedence:

  • Your own custom skills in ~/.openclaw/workspace/skills/ take priority over everything.

  • Skills installed from ClawHub are at the second level and are available across all your workspaces.

  • Bundled skills are the baseline that ships with OpenClaw itself.

This resolution order matters for customization.

You do not need to modify or fork bundled skills to change their behavior. Create a file at ~/.openclaw/workspace/skills/<name>/SKILL.md and OpenClaw uses your version instead.

Writing a custom skill

A skill is a markdown file.

There is no code, no compilation, no API to implement. You describe a workflow in plain language, and the agent follows it…

---

name: weekly-report
description: “Compile and send weekly engineering report every Friday”

---

# Weekly Engineering Report

When asked to generate the weekly report:

1. Get all merged PRs from the last 7 days across all repos in the org
2. Group them by team based on the PR author’s Slack team membership
3. For each group, write a 2-3 sentence summary of what shipped
4. Check the CI dashboard for any tests that failed more than twice this week
5. Format everything as a Slack message and post to #engineering-updates
6. Save a copy to ~/reports/YYYY-MM-DD.md for the record

If you find yourself explaining the same multi-step process to OpenClaw repeatedly,,, then write a skill.

The description line in the frontmatter19 is what the agent reads when deciding whether to load the skill. So write it as a clear one-line summary of what the skill handles.

ClawHub

ClawHub is the public skill registry.

You install skills by asking your agent directly, by pasting a repository link into the chat, or by running $ openclaw skills install <name> from the CLI.

The ClawHub CLI installs separately:

$ npm i -g clawdhub
$ clawdhub search “notion”
$ clawdhub install notion

Also, ClawHub has a VirusTotal partnership that scans skills for known malware signatures.

This is a meaningful baseline check but not a complete guarantee. A skill that instructs the agent to exfiltrate data through normal API calls will not trigger any scanner. So always read a skill’s SKILL.md before installing it.

Look at what the agent is being instructed to do, what tools it is told to call, and whether any steps seem unexpected for the stated purpose.

Installing the GitHub skill

GitHub is the most commonly installed skill and the clearest example of how the skill system works end-to-end.

It is worth walking through in full because the same pattern applies to every other skill on ClawHub.

GitHub skill gives your agent access to GitHub via the gh CLI (GitHub’s official command line tool). When you ask “show me open PRs in my repo,” the agent reads GitHub skill’s instructions on demand, determines the correct gh command to run, executes it, and returns the result in plain language.

Because it operates through the official CLI, the skill can do anything gh supports: reading issues, managing pull requests, checking CI run statuses, interacting with the API, and much more.

Installation

You have three options:

  • The simplest is to ask your agent directly in chat: “Install the GitHub skill.” The agent handles the installation in the background and confirms when complete.

  • Alternatively, paste a ClawHub repository link directly into chat and ask the agent to install it.

  • Or simply use the CLI:

$ openclaw skills install github

Authentication

Once installed, the agent needs GitHub credentials. Run:

$ gh auth login

Follow the prompts to authenticate via browser OAuth.

This gives the gh CLI (and therefore your agent) access to your GitHub account. Because it uses OAuth, you control exactly which permissions are granted at the GitHub level.

What you can ask immediately after connecting:

  • “Show me open PRs in owner/repo.”

  • “Summarise the review comments on PR #42.”

  • “Which PRs are waiting for my review?”

  • “Check the status of my latest GitHub Actions run.”

  • “Create an issue titled ‘Login button broken on mobile’ in owner/repo.”

  • “What changed between these two commits?”

Read vs write access

OpenClaw excels at read-access workflows: pulling PR diffs, summarising review comments, identifying failed tests, all without touching the repository.

Write actions like merging PRs, pushing code, or closing issues carries real consequences. So the recommended pattern is to instruct the agent explicitly in your SOUL.md:

Before merging any PR or pushing any code change, tell me what you are about to do and wait for my confirmation. This keeps the agent’s initiative high while keeping consequential actions under your control.

If something is not working:

Run $ openclaw doctor first.

For GitHub specifically, the most common causes of failure are:

  • gh CLI not installed (the agent will tell you, or install it if you ask),

  • OAuth token expired or revoked (re-run $ gh auth login),

  • Or insufficient token scope (re-authenticate and grant the missing permissions).

Plugins vs skills

A skill is a set of instructions that tells the agent how to do something.

A plugin is a module that gives the agent access to something. For external services that need persistent connections or OAuth flows, OpenClaw uses MCP (Model Context Protocol) servers as the plugin mechanism.

MCP is a standard that enables AI agents to connect to external services via a defined interface.

{

  “plugins”: {
    “entries”: {
      “composio”: {
        “enabled”: true,
        “config”: {
          “consumerKey”: “ck_your_key_here”
        }
      }
    }
  }
}

Think of it like this:

  • Plugins open doors.

  • Skills tell the agent which door to use and what to do once it is through.

The next layer is what happens when you are not asking anything at all: when the agent needs to act on its own…

Heartbeats and Cron Jobs: Proactive Automation on a Schedule

Every AI tool covered so far in this newsletter is reactive…

You send a message, and it responds. You ask a question, and it answers. This interaction model is useful, but it is also fundamentally limited: agent only knows what you tell it, only acts when you initiate, and is completely blind to anything that happens while you are not watching.

Heartbeats and cron jobs are what change that…

Heartbeat

Heartbeat is a periodic pulse.

At a configurable interval (30 minutes by default), OpenClaw wakes the agent, passes it a lightweight check-in prompt, and asks it to assess whether anything needs your attention.

Say it’s 2 am, a CI run fails on your main branch. And you’re asleep. Heartbeat catches it and sends you a Telegram message. If everything is normal, it responds with a special token called HEARTBEAT_OK, and Gateway silently discards the response.

No notification is sent.

Only when something needs your attention does it produce an actual message.

You define what the agent looks for in HEARTBEAT.md inside your workspace:

# Heartbeat Checklist
Check the following on every pulse:

- Any new GitHub PR comments or review requests on repos I own
- Any CI run failures in the last 30 minutes
- Any server errors in Sentry with severity >= error
- Any emails with “urgent” or “action required” in the subject

If all clear, reply HEARTBEAT_OK

If anything needs attention, summarize clearly and send it to Telegram.

Heartbeats use a lightweight model by default, not your primary reasoning model. A status check does not need a complex model. Routing heartbeats through a simple model keeps the cost of background monitoring negligible even when it runs dozens of times a day.

Cron jobs

Heartbeats listen passively in the background…

Cron jobs act on a schedule. You define the task, time, and channel, then OpenClaw runs it automatically. A cron job runs a specific task at a specific time, delivers the output to a specific channel, and then returns to waiting.

The scheduler runs inside the Gateway process.

This means your jobs persist across model changes, survive configuration updates, and do NOT depend on you having an active conversation.

Every cron job runs in one of two session modes:

  • Main session mode injects the job’s task into your normal ongoing conversation as if you had sent it yourself. Use this for jobs that benefit from continuity with your regular chat.

  • Isolated mode spins up a completely separate session for each run with no prior conversation history. Use this for background automation, frequent monitoring checks, or anything noisy that you do not want mixing into your main chat history.

Most scheduled automation should use isolated mode.

Setting up your first cron job

The simplest way is to ask your agent directly:

“Set up a cron job that runs every weekday morning at 7am and sends me a summary of my open GitHub PRs on WhatsApp.”

Managing jobs over time

# See all jobs, status, last run time
$ openclaw cron list                  

# Trigger a job immediately for testing
$ openclaw cron run <jobId>           

# View run history and results
$ openclaw cron runs --id <jobId> --limit 20

# Pause without deleting
$ openclaw cron edit <jobId> --enabled false

# Delete a job
$ openclaw cron remove <jobId>

What breaks cron jobs

Here are 3 things that cause most failures:

  • Gateway goes offline. If your Mac Mini or VPS goes down, no jobs execute.

  • Timezone not configured. Jobs fire at unexpected times.

  • Repeated failures trigger exponential backoff. 30 seconds on the first failure, then 1 minute, 5 minutes, 15 minutes, and up to 60 minutes between retries.

Heartbeats and cron jobs together are what make OpenClaw feel less like a tool you operate and more like a system that works alongside you…

What Can Go Wrong

OpenClaw gives you a lot of power.

But power without guardrails20 produces predictable problems.

Here are the most common failure modes and how to fix them:

1. Agent loops

This is the most common and most expensive failure mode.

The agent calls a tool, gets a result, calls another tool, gets another result, and never produces a final answer. It keeps going until it hits the context limit or burns through your token budget.

It usually happens when the task is too vague, skill instructions are ambiguous, or the model is too weak to recognize that it’s stuck.

You can fix it by being more specific in your instructions, adding anti-looping logic in your SOUL.md (“If you have taken more than 5 tool calls without a final answer, stop and ask me for clarification”), and using a stronger model for complex tasks.

Watch the dashboard… A loop can burn $50 in an hour.

2. Memory bloat kills performance

MEMORY.md grows over time, and the agent keeps writing to it.

If you never clean it, the file eventually gets so large that loading it on every session eats into your context budget before you’ve typed a single message.

So audit it weekly and remove anything that’s no longer true or relevant.

3. Context pollution causes garbage output

When too many unrelated topics share the same session, the agent starts mixing context from different projects, different tasks, and different conversations. The output becomes confused and unreliable.

So use separate Telegram topics or Discord channels for each project and keep one context per workflow.

4. Compaction loses important details

When a session reaches model’s context limit, compaction triggers automatically.

The agent summarizes the conversation and replaces the raw history with that summary. Yet summaries lose detail. Specific numbers, exact instructions, and precise context can disappear in the process…

For long-running tasks, explicitly save important context.

You can tell the agent, “Remember this…” at key moments so it writes to MEMORY.md rather than relying on the in-session history that will eventually be compacted away.

5. Model hallucinates a tool call

The agent decides it needs to call a tool that does NOT exist, or calls the right tool with wrong parameters. This is more common with smaller, weaker models and with vague task descriptions.

So use a capable model for any agent with real tool access.

Be specific in your instructions. Enable exec approval so you can catch bad commands before they run.

6. Cron jobs silently stop running

The Gateway could go offline, or your laptop sleeps, or a job fails repeatedly and hits exponential backoff. You assume the job ran, but it did not…

Check this regularly:

$ openclaw cron list

…and look at the last run time for each job.

Then run this to inspect the run history and catch silent failures early:

$ openclaw cron runs --id <jobId>

7. A long-running task times out mid-way

Gateway has a timeout for individual tool calls.

A slow API, a large scrape, or a heavy file operation can hit it. The agent stops while the task is incomplete, and you may NOT get a clear error message.

So split long tasks into batches. Instruct the agent to process in chunks and report progress between each one.

8. Skill does something unexpected

You installed a skill without reading it.

The agent follows the skill’s instructions exactly. But the instructions told it to do something you did NOT expect…

So always read SKILL.md before installation. And treat it like a shell script… If you would not pipe an unknown script into bash, do NOT install an unread skill.

Security Trade-offs

OpenClaw is the most capable personal AI tool that most developers will ever run…

It’s also (by design) one of the most dangerous pieces of software you can install on your machine if you do not understand what you are enabling.

An agent with shell access, GitHub credentials, email access, and the ability to send messages on your behalf has a larger blast radius than most software you will ever run…

Permissions problem

When you connect OpenClaw to your accounts, you are giving a reasoning system the ability to take real actions: merge pull requests, send emails, delete files, execute shell commands, write to your calendar, and message your contacts.

Those actions are immediate and often irreversible!

A standard chatbot is safe because it can only produce text, which you then review. OpenClaw closes the loop, and its output is the action.

There is NO review step unless you build one in.

Prompt injection

Prompt injection21 is the most significant and least intuitive threat in agentic AI systems.

When OpenClaw reads an email, a web page, a document, or a Slack message on your behalf, the content of the source becomes part of its context. A malicious actor who knows you use an AI agent can embed instructions in the content that the agent interprets as legitimate commands.

The attack does not require access to your machine… It only requires that your agent read something the attacker controls…

Cisco’s AI security research team tested a community OpenClaw skill and found it performed data exfiltration and prompt injection without any visible indication to the user. Vectra AI’s analysis described the dynamic plainly: payload is language, not malware.

So traditional security tooling does not detect it.

OpenClaw does NOT have built-in injection filtering.

Its resistance depends almost entirely on the model you are running. This is why the guidance is to use a large, capable model for any agent that has tool access and an open inbox. A smaller quantized local model combined with shell access and GitHub credentials is a “serious” risk.

Skills Problem

Every skill you install is a set of instructions your agent will follow…

Community estimates suggest that a meaningful proportion of publicly available skills are either poorly written and likely to cause unintended behavior or actively malicious.

Semgrep’s security analysis found credential handling within OpenClaw’s ecosystem is weak. API keys are stored unencrypted in predictable locations on disk, making them accessible to anything running on the same machine.

Here’s the practical rule: always read a skill’s SKILL.md before installation.

i.e., read it as you would a shell script before piping it into bash. It takes two minutes, and it’s the only reliable protection you have.

Exposed instances

Security researchers identified over 1,000 OpenClaw gateways exposed directly to the public internet without authentication.

This wasn’t a flaw in OpenClaw itself… It happened because developers changed the default bind address from 127.0.0.1 to 0.0.0.0 without realizing that doing so makes the gateway reachable by anyone on the internet.

In January 2026, a critical vulnerability was disclosed: CVE-2026-25253 (CVSS 8.8).

Attackers could steal authentication tokens via URL parameters and gain full control of an exposed instance. The fix shipped later in the same month… So if you are running a build from before that date, update before doing anything else.

MoltMatch incident

A CS student configured his OpenClaw agent to explore its autonomous capabilities with broad permissions.

He later discovered the agent had created a dating profile on MoltMatch and had been screening potential matches without his knowledge or consent. The profile did not represent him accurately.

This is NOT a story about a bug…

It is a story about what “autonomous” actually means when you give an agent wide permissions and a vague mandate. The agent did what it was designed to do: take initiative and act without waiting for instructions.

The problem was student had not clearly defined boundaries for the agent to know where initiative was and was not appropriate…

Practical defenses

Here are some ways to keep your OpenClaw secure:

1. Keep the gateway on loopback

The default bind address is 127.0.0.1 (Leave it there.)

If you need access from another device, use one of these safe paths rather than exposing the port directly:

Try Tailscale:

Keep bind on loopback and access via your Tailscale MagicDNS URL by running.

$ openclaw gateway --tailscale serve

Tailscale handles identity, and no additional token is needed if gateway.auth.allowTailscale is set to true in your config.

Alternatively, try SSH tunnel:

$ ssh -N -L 18789:127.0.0.1:18789 user@your-server

…then open http://127.0.0.1:18789/ locally.

Nothing is exposed remotely, and no firewall rules are needed.

Or LAN bind with a token:

If you must bind to LAN, always set gateway.auth.mode: “token” with a strong token. Never bind to 0.0.0.0 without authentication.

Even on loopback, wizard generates a gateway token by default, so other local processes cannot call the Gateway without authenticating. Do not remove it…

Retrieve it with:

$ openclaw config get gateway.auth.token

Or regenerate it with:

$ openclaw doctor --generate-gateway-token

2. Use pairing or allowlist mode for all channels

Do not switch to open mode unless you fully understand the exposure.

For any channel where you want to be the only authorized sender, use allowlist mode and explicitly list your user ID.

3. Start with read access, earn write access

Let the agent read your PRs, summarize your emails, and report on your calendar.

Watch how it behaves for the first week, and only expand write access once you’re confident it handles read-only tasks correctly.

4. Use exec approval

When the agent wants to run a shell command, the gateway intercepts the request before execution and presents it to you for review. This is enabled by default and should stay enabled.

5. Read skills before installation

Every skill is a set of instructions.

If you would not run an unknown shell script without reading it, apply the same standard to skills.

6. Run a security audit regularly

Check exposed ports, authentication configuration, detected secrets, and filesystem permissions:

$ openclaw security audit

Also run a more thorough probe:

$ openclaw security audit --deep

Run both after installation and after any significant configuration change.

7. Use a capable model for any agent with tool access

Smaller models are more susceptible to prompt injection.

The cost difference between a capable and a vulnerable model is negligible compared to the cost of a compromised agent.

8. Keep OpenClaw updated

Critical vulnerabilities get patched quickly, but only if you pull the update.

What responsible deployment looks like

The pattern that experienced users converge on is incremental trust…

Start with the minimum required for the first task you want to automate. And watch the agent operate. Then expand permissions deliberately as you build confidence in its behavior…

Here’s the rule of thumb: if you cannot understand how to run a command line, this project is far too dangerous for you to use safely.

Security determines whether your setup is safe.

Cost determines whether it is sustainable. The two are more connected than they seem. The same model tiering decisions that protect you from runaway token spend are also the ones that limit the blast radius of a prompt injection attack.

What OpenClaw Costs Per Month

Here’s an approximate cost breakdown:

  • Hosting:

    A VPS runs $5–24/month. AWS Free Tier covers 12 months (watch data egress fees). Mac Mini is $700+ and overkill for most setups.

  • LLM API:

    Light use runs $5–15/month. Moderate use (heartbeats, cron, daily triage) runs $30–80/month. Heavy use (always-on, multiple agents) runs $100–300+/month.

    One user spent $2,300 in a single weekend running everything through Claude Opus, including heartbeats and routine checks. Using a Claude Pro/Max or ChatGPT Plus subscription to make API calls violates the Terms of Service. Use pay-as-you-go API billing.

  • Local models:

    Ollama shifts costs to hardware and electricity. glm47-flash (~5GB) is a practical starting point with zero API cost.

Model tiering is the biggest cost lever.

By default, every request hits your primary model: heartbeats, sub-agents, simple lookups, complex reasoning, all billed at the same rate.

Configure a cheap default model for routine work and reserve the expensive model for complex tasks:

{
  “agents”: {
    “defaults”: {
      “model”: {
        “primary”: “gemini-flash”,
        “fallback”: “claude-sonnet-4-20250514”
      }
    }
  }
}

The fallback field does double duty.

It is not just a cost measure; it is also a reliability measure.

If your primary provider hits a rate limit or a billing issue, OpenClaw automatically falls back to the secondary model rather than failing silently. You can also override the model per cron job, so your daily PR check can run on Gemini Flash while your weekly deep analysis runs on Opus.

OpenClaw Best Practices

Here are some ways to get the best out of OpenClaw:

1. Tier your models

The number one mistake: do not run Opus for heartbeats.

Instead, use a cheap model (Haiku, Gemini Flash, local Ollama) as the default. Switch to powerful models only for complex reasoning.

2. One agent, one job

  • Coding agent for code.

  • Ops agent for infrastructure.

  • Research agent for research.

Do NOT make one agent do everything…

When an agent handles too many unrelated tasks, it starts mixing information together, gets confused, and can fall into loops.

3. Be extremely specific

Talk to your agent as if you were writing a ticket for a smart junior developer with zero context.

  • Bad: “Automate my email.”

  • Good: “Check my inbox every morning at 8 am. Pull emails with ‘invoice’ in the subject. Save attachments to /invoices. Summarize amounts in a message to me.”

4. Start small, build trust

Check everything the agent does for the first two weeks. After that, you will know when to trust it…

5. Separate contexts

  • One Telegram topic per project.

  • One Discord channel per workflow.

Context pollution is the number one cause of looping and garbage output.

6. Add guardrails via SKILL.md

Add anti-looping logic, compaction summaries, and self-check instructions to workspace skill files. The less freedom you give it, the better it performs…

7. Isolate cron sessions

Background tasks need sessionTarget: “isolated”.

Without this, the cron job runs in your current session and dies when you close your laptop.

8. Go Markdown first

Store everything in plain Markdown. Your data moves in seconds when the next tool comes along…

9. Force explicit memory

Say “Remember this…” for important context.

Audit MEMORY.md weekly and delete stale entries. Memory bloat kills performance.

10. Back up everything

Daily cron to a private Git repo: SOUL.md, MEMORY.md, AGENTS.md, cron schedules, skills. If your server dies, you’re back in an hour.

11. Watch dashboard

A runaway loop can burn $50 of tokens in an hour…A dashboard shows real-time usage.

12. Use community

  • OpenClaw Discord for quick fixes.

  • r/openclaw for broad discussions.

  • GitHub Discussions for architecture questions.

The fastest way to improve is by reading what others have already built…

Where Can You Run OpenClaw?

The heavy compute (LLM inference22) happens on your model provider’s servers.

Your machine just runs the Gateway and executes skills… So even modest hardware works…

  • VPS (recommended): A VPS (Virtual Private Server) is a rented remote machine that runs 24/7 in the cloud. It costs $5/month with 2 vCPUs, 4GB RAM. CPU sits at 3–8% during requests, near zero otherwise. DigitalOcean has a 1-Click Deploy with security hardening.

  • Mac Mini: Community favorite, but $700+ for something a $5 VPS handles.

  • Raspberry Pi: Works for lightweight setups. Limited for browser automation or heavy workloads.

  • Your laptop: Fine for testing. Stops when you sleep.

Supported OS: macOS (first-class, menu bar app available) and Linux/Ubuntu (most common for VPS deployments). Docker and Nix are also supported.

Build Your Own OpenClaw

OpenClaw is MIT-licensed.

You can fork it, modify it, or use its architecture as a blueprint. Any OpenClaw-like agent needs five layers, and each layer is independent.

Start with the bottom two and add layers as needed…

Layer 1: Messaging Gateway

Connects your agent to a messaging platform.

Receives messages, normalizes them into a standard format (sender ID, content, metadata), and routes replies back out. Each conversation needs its own isolated session.

Layer 2: LLM Connection

Takes the user’s message plus conversation history, sends it to the LLM API, and returns the response. Also, add model routing (simple model for routine tasks & complex model for reasoning) and context window management for long sessions.

Layer 3: Tools Layer

Define a set of tools and tell the LLM about them.

When the LLM issues a tool call, execute the function and feed the result back. Use Docker containers to isolate execution.

Layer 4: Persistent Memory

Plain Markdown files: SOUL.md for identity and rules, MEMORY.md for long-term context, USER.md for your preferences. Read at session start, write at session end.

Layer 5: Scheduler

A heartbeat for periodic check-ins and cron jobs for scheduled tasks. Each cron job needs its own isolated session, so closing your laptop doesn’t kill it.

For extending without rebuilding, writing custom skills is the easiest path.

Create workspace/skills/my-skill/SKILL.md, add instructions, restart OpenClaw. The agent then picks it up automatically.

Multi-agent setup

For complex workflows, run many agents with separate workspaces:

~/.openclaw/

└── agents/

    ├── main/           # General assistant

    ├── dev-agent/      # Coding specialist (GitHub, code review)

    └── ops-agent/      # Infrastructure (monitoring, deployment)

Each agent gets a different model, different skills, and a different SOUL.md.

Route to separate Telegram topics or Discord channels. Use --profile flags to isolate the state.

Final Thoughts

OpenClaw connects an LLM to your tools and runs 24/7 through your messaging apps.

It’s infrastructure, and NOT a finished product. So the value you get depends on how much time you invest in configuration, security, and iteration.

The architecture is clean: Gateway for messaging, LLM for reasoning, Sandbox for execution, Skills for capabilities, Memory for context.

All in plain Markdown files you own and control.

Security risks are real and documented. Follow the hardening steps in this newsletter, run the security audit, and treat permissions as something you earn your way into rather than grant on day one.

  • Who should try it: Developers comfortable with the command line who want a local, extensible, always-on agent.

  • Who should wait: Anyone expecting a polished consumer product on day one.

Treat it like training a new employee. The onboarding takes effort. But once the foundation is set, things compound fast…
