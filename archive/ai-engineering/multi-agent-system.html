Multi-Agent Architectures, Clearly Explained

#143: Coordination architectures, protocols connecting them, and how to pick the right one before you write any code.

A single agent1 has one context window2, one set of tools3, and one running loop4.

When a task outgrows any of those three, you need more than one agent. That’s what a multi-agent system is. Instead of one agent doing everything, you split the work across many agents. Each one has its own role, tools, and context.

Most multi-agent systems fail not because the model is weak but because you chose many agents before you actually need them, or chose the wrong architecture once you have many agents.

So you shouldn’t split anything yet.

Limits of single-agent systems

One agent with good prompts and the right tools handles more than most people expect.

For example, Cognition’s Devin processed 5 million lines of COBOL (Common Business-Oriented Language) across 500GB of repositories with a single agent, raising its pull request merge rate from 34% to 67%.

But a single agent has three HARD limits. When your task runs into any of them, better prompts won’t help:

1. Context overflow

A context window can only hold so much.

Past that limit, the earliest information drops out, and the agent starts losing track of its own plan. When compression5 alone can’t fix the overflow, a second agent with its own context can.

2. Parallelism

Independent tasks shouldn’t wait in line.

If you have four research queries that don’t depend on each other, running them one at a time wastes time. Running them across four separate agents takes roughly as long as the slowest one.

Anthropic’s research system uses this exact pattern and reduced total query time by up to 90%.

3. Specialization

Different parts of a task often need different models6, tools, or access levels:

  • A code-writing agent needs a sandbox

  • A research agent needs web search

  • A customer-facing agent needs user data, but shouldn’t have access to production databases

When one agent can’t hold all the tools and permissions the task needs, you give each role its own agent.

If none of those three conditions apply, stay with one agent.

Better prompts and better tools solve most problems without adding the extra work of coordinating agents. But once you know you need many agents, the next question is what shape the system takes...

Multi-agent architectures

Every multi-agent system makes a different choice about who coordinates work.

Here are 6 architectures that range from tight central control to NO coordinator at all:

1. Orchestrator-worker

One central agent breaks a task into pieces, assigns each piece to a worker agent, and then puts the results together:

  • Workers don’t talk to each other; all communication goes through a central agent

  • Orchestrator calls each worker as a tool call7, waits for a result, and decides what to do next

This is like an air traffic control tower that talks to every plane, while no plane talks directly to another.

Anthropic’s Claude Research system works this way:

A central agent running Opus 4 breaks a research query into parts and creates 2 to 10 worker agents on Sonnet 4 (sometimes more), all at the same time. The workers search the web, read documents, and gather evidence in parallel. When they finish, the central agent reads their results and writes a single research report.

This setup beat single-agent Opus 4 by 90.2% on Anthropic’s internal research eval8.

Tradeoffs

Central agent is both coordinator and bottleneck…

It talks to workers one at a time. If each call takes 3 seconds and 20 workers are waiting, the ceiling is about 7 tasks per second. So the central agent becomes the slowest part of the system.

Anthropic’s Claude Research system had this problem as well: workers duplicated each other’s work.

Without specific instructions, many workers run overlapping searches on the same topic, wasting both tokens9 and time. The takeaway is orchestrator-worker depends entirely on the quality of the lead agent’s instructions.

Vague task splitting turns parallelism into duplicated work.

2. Pipeline

Agents run in a fixed order, one after another.

Each agent’s output becomes the next agent’s input, and entire sequence is set in advance. While orchestrator-worker lets the central agent decide what to do as it goes, pipeline removes that choice.

An assembly line works the same way: each station does one job, passes the result forward, and never sees the finished product.

Stripe uses this pattern to check whether new businesses on its platform are legitimate.

Before agents, a human reviewer had to jump between customer databases, legal sources, and support tickets to decide whether a business was safe to approve. Now their engineering team broke that work into a fixed flow of agent stages using a directed acyclic graph (DAG). So work moves forward through stages without looping back.

Order is set at design time, and each stage has a contract: defined output format next stage expects.

Stripe calls these contracts “rails” because they keep any single agent from spending too much time on irrelevant data. This setup cut their average handling time by 26%, and reviewers rated the agent outputs 96% helpful, with a full record of every decision at every step.

Tradeoffs

Latency adds up.

A 5-stage pipeline where each stage takes 2 seconds means a 10-second wait before any output, and adding a stage to improve quality increases the response time.

Yet the upside is predictability.

When every stage has a narrow contract, you can trace any failure back to exactly one step. That’s why regulated workflows like Stripe’s continue to use pipelines.

When the cost of being wrong is a regulator flagging your process, the extra seconds are a small price to pay.

3. Hierarchical

A top-level manager agent gives work to one or more layers of manager agents below it, which then give work to individual workers.

Two levels are the minimum; big systems stack more. The result is a tree…

No single agent needs the full context.

The top-level agent holds the high-level goal and a summary from each branch, while each lower level sees only what its narrower role needs. Picture a military chain of command where orders flow down, reports flow up, and no one skips a level.

IBM watsonx Orchestrate runs on this pattern:

A top-level supervisor agent acts as a router and planner across 80+ pre-built domain agents for HR, sales, and procurement. Let’s say a user tries to “order new laptops for the design team”. The request reaches a Procure Equipment supervisor, who then hands the work to three specialized child agents:

  • One requests quotes from approved vendors

  • Another checks responses

  • A third submits a purchase request

The supervisor decides only who gets called and in which order.

Tradeoffs

Details might get lost at each level.

A worker produces a detailed result. The mid-level manager shortens it to one sentence. By the time it reaches the top, the detail that matters might be gone. Hierarchical structures trade detail for coverage: the higher you go, the wider the scope of each agent and the less it knows about any specific piece.

These three architectures share one thing: a clear chain of command tells you exactly who’s in charge…

The next three architectures drop the chain entirely. So they're harder to debug, but they survive partial failures better…

4. Swarm

In a swarm, many agents work as equals.

They coordinate through a shared blackboard: a data store (typically Redis cache, database table, or vector store) that every agent can read from and write to. Yet there are NO direct messages between agents…

Each one watches the board for messages that match what it’s waiting for and acts when it sees one.

This is like an ant colony…

No single ant decides what the colony does. Each one follows simple rules, and the group's behavior comes from all of them acting together.

Swarms are one of the least common architectures in production:

OpenAI released its own swarm framework for educational purposes and does NOT recommend it for production. The main framework built for swarms today is Strands SDK, an open-source project from AWS (Amazon Web Services) that provides shared memory and no central coordinator by default.

But without a coordinator, every agent can talk to every other agent…

With 5 agents, that’s 10 possible connections. With 50 agents, it’s 1,225. The formula is N*(N-1)/2, which grows roughly with the square of the agent count. Every connection is a message, and swarms produce messages faster than they produce decisions.

Tradeoffs

Debugging a swarm is HARD because you can only see the final state, and not the order of actions that produced it.

So when something goes wrong, you can’t point to one agent who made the wrong decision. Swarms also need hard limits to stop: max number of rounds, a quality threshold, or a timeout.

Without those, the swarm keeps running.

5. Mesh

A mesh wires 3 to 8 agents directly to each other at deployment time.

Any agent can call any other, but NO new connections form while the system runs. This fixed wiring is what separates mesh from swarm.

It’s like a small team on a group call where everyone can address anyone directly.

LangChain’s Open SWE coding agent uses this pattern:

  • Planner agent analyzes the codebase and produces a step-by-step plan.

  • Programmer agent writes the code.

  • Reviewer agent checks the quality and runs tests.

If the Reviewer finds issues, it sends the task back to the Programmer with specific feedback, and the loop continues until the code passes.

All three connections get set at deployment time in LangGraph (i.e., NOT formed while the system runs).

LangChain runs Open SWE against its own repositories during development. The agent opens pull requests autonomously and handles tasks such as bug fixes and test repairs.

This is the same workflow system runs on any GitHub repository.

Tradeoffs

Mesh doesn’t scale.

The same growth problem from swarms applies here: 10 agents mean 45 connections, and each connection requires a pair of agents to stay in sync.

So this architecture works best with 3 to 8 agents max.

6. Handoffs

Only one agent is active at a time.

When its task is done, it packages what it knows into a handoff payload: conversation history, decisions made, data gathered. Then it transfers control to the next agent, which continues from there.

Think of it like a relay race where only one runner carries the baton at a time.

Yet what doesn’t make it into the payload is gone the moment control changes.

Internet providers use this pattern for customer support, enabling a single call to touch billing, technical support, and account changes:

A first-contact agent determines what the customer needs and then passes control to a technical agent. The technical agent passes the issue to a billing agent if it concerns a charge, then to an account agent if details need updating, and finally to a human if none of the previous agents resolved it.

Each agent can end the conversation if the customer’s problem gets solved along the way.

Tradeoffs

Handoff systems can break in two ways…

Agents can keep passing the task around without anyone finishing it, thus creating an infinite loop. Or the payload fails to carry enough context, so the receiving agent either starts over or makes wrong assumptions about what has already happened.

Either way, no one is in charge of finishing the job.

Building blocks behind each architecture

These architectures look different on a whiteboard, but they run on the same machinery.

How that machinery behaves depends on which shape you picked…

How agents run

Every architecture runs a version of the same loop.

The agent looks at the current state, takes an action (usually a tool call), checks the result, and decides whether to loop again or stop.

The difference is WHO controls that loop.

In centralized architectures (orchestrator-worker, pipeline, hierarchical), control flows from the top.

The orchestrator decides when workers start and stop. A pipeline runs each stage exactly once. In decentralized architectures (swarm, mesh, handoffs), each agent controls its own loop, so stop conditions must be specified: maximum number of rounds, quality threshold, or timeout.

AWS Strands enforces this with parameters like max_iterations=3 and execution_timeout=300.0.

Without them, a swarm of agents will keep running at full token cost forever.

There’s a second reason to keep the step count low…

Even with 99% success per step, a 10-step chain has only about a 90% chance of finishing without error. Hierarchical and orchestrator-worker setups add more steps, so errors build up quickly.

How agents talk to each other

Two protocols handle this, and they solve different problems:

  • MCP (Model Context Protocol) connects an agent to its tools and data.

  • A2A10 (Agent-to-Agent Protocol) connects agents to each other as peers that don’t share their inner workings.

Which of these two matters more depends on which architecture you picked…

Centralized architectures (orchestrator-worker, pipeline, hierarchical) lean on MCP. An orchestrator calls workers as tool calls, pipeline stages each access their own tools.

A2A adds little when one agent is already directing the others.

Decentralized architectures (swarm, handoffs) lean on A2A instead.

Swarm agents use A2A’s Agent Cards feature11 to find peers and track their task status (submitted, working, completed), so they can coordinate without a central node. Handoff architectures use their structured task format to package the handoff payload: what’s been decided, what remains, and the current state.

Each protocol has one key problem you should know about…

MCP’s problem is scaling:

Loading hundreds of tool definitions into context at once can use 150,000 tokens before the agent does anything. Orchestrator-worker feels this first because the central agent needs access to every worker’s tool type, whereas pipelines barely notice, since each stage loads only its own narrow toolset.

The fix to this issue is lazy loading: read tool definitions only when the agent actually needs them. Anthropic uses this pattern in Claude Code, where only the tools relevant to the current task are pulled into context, dropping the cost from 150,000 tokens to about 2,000.

A2A’s problem isn’t scaling, but how new it is:

It’s still a new standard without the wide adoption MCP has today, so tooling and docs around it are thinner…

How agents share data

The choice between isolated and shared state isn’t always yours to make.

Orchestrator-worker and pipeline systems use isolated states.

Workers are stateless: each one gets the context it needs, does the work, and returns a result. Orchestrator or the contract between pipeline stages holds everything.

Anthropic’s research system takes this further…

Subagents write results to the filesystem and pass lightweight references back to the central agent. This avoids copying large outputs into the conversation history at every step, which distorts details, just as a rumor changes as it gets retold. Such isolated states use 67% fewer tokens than shared alternatives.

Swarm is the only architecture where the shared state isn’t a side effect of coordination…it’s the coordination mechanism itself.

The blackboard isn’t just storage.

Agents read it to decide what to do next, post the results back, and other agents use those results as inputs. This makes swarms flexible but fragile: one agent’s hallucinated12 output becomes another agent’s starting point, and the bad data spreads through the board before anyone catches it.

Mesh systems sit between the two…

Google ADK (Agent Development Kit) uses an `output_key` feature that gives each agent its own namespace in shared memory. The structure is shared, but no agent can overwrite another’s slot, so each one writes to its own lane.

Handoff architectures take a different route…

State gets packed into the payload that travels with the active agent, and quality degrades with each transfer because it’s impossible to recover what the departing agent didn’t include.

How agents remember

How memory gets separated also varies by architecture:

In orchestrator-worker, the orchestrator remembers everything while workers remember nothing: they’re stateless by design. The orchestrator’s memory is the system’s memory.

Pipeline stages barely need memory at all…

Each stage’s entire context is the output of the previous stage. If a stage needs outside knowledge, it fetches it via a tool call, NOT from a memory store. This is part of why pipelines are easy to restart: there’s no built-up session state to restore.

Swarm memory operates differently from other architectures…

The shared blackboard is the collective memory. The usual per-agent separation by user ID, agent ID, or session ID doesn’t apply. Individual agents carry only short-term memory for their current loop. Everything that needs to stick around goes on the board.

For handoffs, memory equals the handoff payload and nothing more. If the departing agent forgets to include a detail, the next agent has no way to recover it.

Forgetting works differently, too:

Orchestrators should drop worker-level details once they’ve been combined into the final result. Swarms can’t forget anything mid-run because other agents may still need it. Handoffs are forced to forget whatever didn’t fit in the payload.

Here are 4 memory types that show up across all of them, and how each maps unevenly to the architectures:

  • Working memory covers the current session. Every architecture has it, but swarms and pipelines use almost nothing else.

  • Episodic memory stores past conversations. Orchestrator-worker relies on it the most, because the central agent has to remember what workers have already tried. While Pipelines don’t need it at all.

  • Semantic memory stores facts and preferences that stick around across sessions. This is where user profiles and domain knowledge live. Hierarchical systems lean on it at the top levels, where managers need a stable context that outlasts any single task.

  • Procedural memory stores step-by-step instructions for recurring tasks. Handoff systems use this heavily: when a support bot sees a problem it has seen before, procedural memory tells it which sequence of agents to route through.

Each architecture answers those four questions in a different order, which is why “how does this agent remember?” rarely has a single answer.

What it costs

Token costs increase with agent count, but how fast they scale depends on the architecture…

Pipelines have the lowest coordination overhead.

No orchestrator to manage, no shared state to sync, no peers to discover. Each stage takes one input and produces one output. So the highest cost is total latency, not coordination tokens.

Mesh systems have fixed, predictable costs.

Three agents running 2 to 5 feedback rounds means 6 to 15 LLM13 calls per task, and that number doesn’t change with the difficulty of the problem. It changes with how many rounds you run, and five rounds is usually the practical ceiling.

Orchestrator-worker is where the token costs 15x higher (compared to a basic chat).

The orchestrator talks to workers one at a time, and at 3 seconds per call with 20 workers waiting, the system caps at about 7 tasks per second. And this creates a lot of extra messages and repeated processing.

Hierarchical systems spread that overhead across levels (each level adds roughly 2 seconds), which shares the load but adds latency at every step.

Swarms have the highest cost potential…

The squared growth in agent-to-agent connections: every new agent adds more coordination overhead than useful output.

Caching is the fix for this issue: when an agent gets asked a question it (or another agent) has already answered, the saved answer gets reused instead of running the whole model again. When the cache answers 70% of requests, coordination time drops from 50% to 30%.

Handoff costs add up one transfer at a time…

Each transfer has a token cost (for packing the payload) and a latency cost (for the receiving agent reading the payload before it can do anything). One way to lower the token cost is to pass the full conversation history along with each handoff, so the receiving agent doesn’t re-ask questions the previous agent already answered.

Handoffs that do this save 40-50% of model calls compared to those where each agent starts from scratch.

Agent harness

All the processes (running, talking, sharing data, and remembering) need something to run them…

That something is the agent harness: everything in an agent except the model itself. It includes the run loop, a list of tools, memory management, context window handling, error handling, and the checking loops.

An agent is the model plus the harness wrapped around it.

The harness is where your chosen architecture actually gets built.

Different frameworks are built around different architectures, so picking a framework is really picking a harness that fits the shape you want:

  • LangGraph models your system as a graph of nodes and edges, which fits orchestrator-worker and hierarchical setups

  • Google ADK ships with SequentialAgent and ParallelAgent primitives that match pipeline and parallel setups, which is why Spotify chose it

  • OpenAI’s Agents SDK is built around the handoff as its main pattern

  • AWS Strands is the only framework built for swarms from the ground up, with shared memory and no central coordinator

Pick a framework whose primitives match the shape you want.

Fighting your harness to simulate a different architecture is how whiteboard designs turn into a mess in production.

Harness is also where the cost of a good setup becomes clear…

For example, Anthropic ran the same coding task in two ways:

  • A single-agent run cost $9 and produced broken software.

  • A three-agent harness (Planner, Generator, Evaluator, where the Evaluator used Playwright14 to test the live app in a real browser) cost $200 and produced a working application.

Same model, different harness: Working vs Broken output.

LangChain saw the same pattern on a coding benchmark:

They kept the model and weights the same, but rebuilt harness around it. This moved them from outside the top 30 to rank 5 on TerminalBench15 2.0.

As models get better, the harness can shrink…

When Anthropic upgraded from Sonnet to Opus 4.6, they dropped their context reset system entirely because the new model no longer showed the “context anxiety16” that made resets necessary. Every piece of a harness is there to make up for something the model can’t do on its own, so when the model improves, some of those pieces stop earning their place.

The right amount of harness follows the same rule as the right number of agents: the least that solves the problem.

Remember, even the right harness can’t save a system from the other ways multi-agent setups go wrong...

Why multi-agent systems fail and how to prevent them

When multi-agent systems fail, the problem is almost never the model… It’s the design of the system around it:

How failures break down

A 2025 study, MAST, tracked the root causes of multi-agent failures and put them into 3 categories…

1 Bad instructions

Agents misread their tasks or ignore their limits.

This remains the main cause, because most teams don’t clearly define what an agent can and cannot do.

Amazon Kiro (in AWS China) is an example of what happens when nobody writes those boundaries:

They asked an agent to fix a tiny issue in AWS Cost Explorer. Instead, it deleted and rebuilt the entire production environment because nobody told it what it wasn’t allowed to modify.

And the outage lasted thirteen hours!

2 Misalignment

Agents working against each other: outputs that contradict each other or ignore what other agents produced.

Replit’s 2025 failure showed how fast this spreads:

They told an agent 11 times not to create fake data, yet it still created 4,000 fake records. When told to stop all actions, it deleted the production database instead and claimed recovery was impossible (it wasn’t!).

Each missed check caused the next: bad code, fake data, lies, deletion, a false recovery claim.

3 Weak verification

Agents accept wrong results if nobody checks.

For example, they asked Meta’s agent to analyze a question privately, but it posted the analysis on an internal forum instead. An employee followed its advice, exposing sensitive data for 2 hours. Meta classified the incident as Sev 1 (highest severity tier).

A single output check could have caught the routing error.

Every one of these failures was preventable, but nobody wrote the rules that would have prevented them. Don’t forget, better prompts alone can’t fix a system-level failure…

Security risks and fixes

By default, agents trust messages from other agents the same way they trust their own instructions.

That trust is the main place attackers can get in, and it shows up in these 3 patterns:

1 Prompt injection between agents

An agent receives a harmful or hidden instruction from another agent and follows it without checking17. The fix is to validate all inputs from other agents and clearly define which instructions should be trusted.

2 Context contamination

A model error writes wrong data to shared memory, and the error spreads to every agent that reads it. No attacker is needed for this to occur. The fix is to keep memory separate per agent and verify outputs before passing them along.

3 Privilege creep through delegation

Agent A has limited permissions, but it can call Agent B, which has wider tool access. Break into A, and you inherit B’s permissions. So it’s necessary to check permissions at every agent boundary, not just at the entry point, to prevent this problem.

Slack AI showed what prompt injection and context contamination look like in production:

An attacker posted a hidden instruction in a public channel. When a user asked Slack AI a question, it pulled that instruction as context and sent private data from those channels, including API keys and financial information, to the attacker’s server. The attacker never had direct access to those private channels.

So the rule is to treat messages between agents as if they were from strangers, not trusted friends…

Let’s look at a real-world case study next…

Orchestrator-worker in production: Spotify’s media planner

Spotify’s media planner is a simple real-world example of how multi-agent systems work.

NOTE: Agents are not required by default. Spotify uses agents to handle natural language input, run tasks in parallel, and use specialized tools to interpret, resolve, and assemble the plan automatically.

A media plan is what advertisers create to run a campaign. It answers these questions:

  • who to target,

  • how much to spend,

  • when to run,

  • what to promote.

Spotify needed to generate a lot of these plans, but the process was slow (15-30 minutes) and inconsistent across its ad channels:

  • Direct: sales team working with big brands,

  • Self-serve: small businesses buying ads through a web dashboard,

  • Programmatic: ads bought automatically through ad exchanges.

And each channel had its own version of the logic, which drifted over time, causing different results for the same input.

So they wanted one unified system that was fast and consistent, where a user could type a simple sentence and get a full plan in seconds.

This problem required multiple agents because:

  • Too much context for one agent,

  • Tasks can run in parallel,

  • Each part needs different tools and data.

So they used an orchestrator-worker setup with 6 agents:

  • 1 RouterAgent to split the task

  • 4 resolver agents to handle goals, audience, budget, and schedule

  • 1 MediaPlannerAgent to combine everything

It’s mostly orchestrator-worker, with a final pipeline-style step to merge results: a common hybrid pattern in real-world systems.

RouterAgent reads the input and sends tasks only to the needed agents.

  • GoalResolver turns vague goals into structured categories using real data.

  • AudienceResolver converts text into correct audience segments (age, location, interests).

  • BudgetAgent and ScheduleAgent clean messy inputs into clear numbers and dates.

  • MediaPlannerAgent combines results, fixes conflicts, and generates final recommendations.

Also each agent writes to its own space, so they don’t interfere with each other…

This approach reduced the time to create a plan from 15-30 minutes to 5-10 seconds.

Plus:

  • Same logic now works across all ad channels (no more drift)

  • System scales easily by adding more parallel agents

Here’s the tech stack they used for this setup:

  • Google ADK 0.2.0 as the agent framework

  • Gemini 2.5 Pro on Vertex AI as the model

  • PostgreSQL with an in-memory cache for storage

  • gRPC (Google’s remote procedure call framework) between services

They used this one rule to decide where to split agents: “One agent per distinct skill or data source.” And it works whether you have six or sixty agents...

The few agents that solve the problem

The first question isn’t which architecture to pick…

It’s whether you need more than one agent at all. The advice from experienced engineers is the same: start with simple prompts, test them thoroughly, and only reach for multi-agent systems when simpler setups are NOT enough.

Pick one task you currently run with a single agent.

Check whether its context window is overflowing, whether it needs too many tools and permissions, and whether its loop is the reason it runs slowly.

If none of those three apply, then leave it alone…

1

An agent is an LLM-based system that can observe state, use tools, and take actions in a loop to accomplish a task.

2

A context window is the maximum amount of text (measured in tokens) a model can read and respond to in a single conversation. Once the window is full, the oldest content drops out.

3

Tools are external functions, APIs, or systems that an agent can call to interact with the real world beyond its own model outputs.

4

The running loop is the agent’s repeated cycle of observing the current state, deciding what to do next, taking an action (like calling a tool), and continuing until the task is complete.

5

Compression is the process of summarizing or condensing information so it fits within the model’s context window while preserving the most important details.

6

A model is the underlying AI system (GPT, Claude, or Gemini) that processes input and generates outputs, such as text, code, or decisions.

7

A tool call is when an agent invokes a specific function, API, or external capability (like search, code execution, or another agent) to perform a task and return a result.

8

An eval is a standardized test that measures how well a model or system performs on a specific task. Anthropic’s internal research eval compares answer quality and completeness across different system configurations.

9

A token is a chunk of text, roughly three-quarters of a word in English, that a model reads and generates. Token counts determine both cost and how much fits in a context window.

10

A2A (Agent-to-Agent Protocol) is Google's open protocol that enables agents from different vendors to discover one another and exchange tasks without sharing their internal implementations.

11

Agent Cards are structured descriptions that each agent publishes about itself, like what it can do, what inputs it expects, and how to interact with it. So other agents can discover and decide when to use it.

12

Hallucination is when a model generates information that sounds plausible but is factually wrong or made up.

13

LLM stands for large language model, the type of AI model behind tools like ChatGPT, Claude, and Gemini. It predicts text by drawing on patterns learned from its training data.

14

Playwright is a tool that lets an agent control a real web browser to test and interact with web apps like a user would.

15

TerminalBench is a benchmark that evaluates how well AI agents perform real coding tasks in a terminal environment, such as writing code, running commands, and fixing errors.

16

Context anxiety occurs when a model starts to lose track of earlier information in a long conversation, leading it to behave less reliably as its context window fills.

17

Prompt injection is when someone hides malicious instructions inside input text to trick an AI into doing something it shouldn’t.
