What is an ML System?

Traditional software runs on rules you write by hand.

If the temperature is above 90°F, turn on the AC. If the user clicks “buy,” charge the card. Every decision is hardcoded in code.

ML systems work differently.

Instead of writing rules, you feed the system examples (thousands or millions of them), and it figures out the rules on its own. Show it a million past rides, and it learns to predict how long your Uber will take. Show it billions of watch sessions, and it learns which movie to recommend next.

This sounds magical, but it’s just data engineering. Data flows in, patterns get extracted, predictions flow out, and the system keeps learning from its own results.

Every concept in this newsletter maps to a stage in this pipeline.

Raw Material: How Data Becomes Intelligence

You can have the fanciest model in the world. If your data is garbage, your predictions will be garbage.

1. Features

A feature is a single, measurable piece of information model uses to make predictions.

Think of features as the columns in a spreadsheet that describe each example.

If you’re predicting whether someone will click on an ad, your features might include the user’s age, the time of day, the device they’re using, and how many ads they’ve already seen this session. Each of these gives the model a different angle on the same question.

In Spotify’s Discover Weekly, features might include your most-played genres, the time of day you usually listen, and how often you skip songs. The model doesn’t “hear” the music. Instead, it reads the features.

The quality of your features often matters more than the sophistication of your model. Which raises the question: where do good features come from?

2. Feature Engineering

Feature engineering is the process of transforming raw data into features that help a model learn better.

Raw data is messy and unstructured. Feature engineering is about cleaning it up, reshaping it, and extracting the signal.

Think of it like preparing ingredients before cooking. You don’t throw a whole chicken into the pan. You cut it, season it, and lay it out first.

For example, Uber’s raw data might say “ride requested at 2024-12-25 08:47:32 UTC.”

Feature engineering transforms that into: day of week (Wednesday), time of day (morning rush), holiday (yes), weather (rainy). Each transformation gives the model a more useful signal than the raw timestamp alone.

Sometimes the most powerful features aren’t in the raw data at all. A feature like “average number of rides this user takes per week” requires aggregation across many records. That kind of creativity is what separates good feature engineering from great ones.

But features alone aren’t enough. The model also needs to know what the “right answer” looks like.

3. Labels & Ground Truth

A label is the answer you’re training the model to predict. Ground truth is what actually happened in the real world.

If you’re building a spam filter, the label for each email is “spam” or “not spam.” If you’re predicting home prices, the label is the actual sale price. The model learns by comparing its guesses against these known answers.

Ground truth sounds simple, but it’s often surprisingly hard to get right.

When Netflix asks “did the user enjoy this movie?”, the ground truth is ambiguous. Did they watch to the end? Did they rate it? Did they watch something similar next? Different definitions of ground truth lead to different model behaviors.

💡 How you define your label shapes what the model actually learns. Choose carefully. Pick the wrong definition of success, and the model will optimize for the wrong thing.

With features and labels defined, the next step is splitting the data so the model can actually learn and prove it learned the right things.

4. Training, Validation & Test Sets

You don’t test a student with the same questions they practiced on.

The same principle applies to ML. The data gets split into three groups, each with a specific job.

  1. Training set is what the model actually learns from. It sees these examples during training.

  2. Validation set is your mid-training checkpoint. It tells you which model version performs best.

  3. Test set is the final exam. If the model performs well here, it’s ready for the real world.

Most teams split their data 70/15/15 or 80/10/10.

The exact ratio depends on how much data you have, but one rule is non-negotiable: test set must never influence model development. Otherwise, you’ve let the student peek at the final exam.

At Netflix, this might mean training on viewing data from January through October, validating in November, and testing in December. This time-based split is especially important for ML systems because real-world data changes over time, a pattern we’ll revisit in Section 5.

Now that we have our data organized, there’s one more data problem that trips up many real-world systems.

5. Class Imbalance & Data Leakage

Class imbalance happens when one outcome is far more common than the others.

In fraud detection, maybe 1 in 10,000 transactions is fraudulent. In medical diagnosis, most patients don’t have the rare disease. The model can achieve 99.99% accuracy by simply predicting “not fraud” every time and still be completely useless.

Fixing class imbalance usually involves techniques like oversampling the rare class, undersampling the common class, or adjusting the model’s loss function to penalize mistakes on rare examples more heavily.

Data leakage occurs when the answer is hidden within the training data.

You’re building a model to predict late deliveries, but your dataset includes “customer complaint filed.” That complaint only exists because the delivery was already late. Of course, the model looks accurate. Remove that feature, and it’s useless.

💡 If your model scores above 95% on the first try, check for leakage. If it scores above 99%, check for class imbalance too.

Clean data is only useful if it actually reaches your model. That’s where pipelines come in.

6. Data Pipelines & ETL

Data pipelines are automated workflows that move data from its raw sources (databases, event logs, third-party APIs) through a series of transformations and into a format the model can use.

ETL stands for Extract, Transform, Load. Extract the raw data from its source.

Transform: clean, join, aggregate, and engineer features from it. Load the results into a feature store or a training dataset.

This is the plumbing part of ML.

And like real plumbing, nobody thinks about it until something breaks. Not the model, not the algorithm. A dropped row, a null value, a late pipeline run. No errors thrown, just silently worse predictions.

Uber runs thousands of data pipelines daily. Everyone has monitoring, alerting, and quality checks. Bring this up in an interview, and you’ll immediately stand out as the guy who actually thinks about how ML works in practice.

Pipelines produce data, but how do you keep track of which data a given model was trained on?

7. Data Versioning

Data versioning means tracking exactly which version of a dataset was used to train each model.

Just like software engineers use Git to track code changes, ML teams need to track data changes.

Why does this matter? Imagine your model’s performance suddenly drops. Without data versioning, you have no way to answer: “What changed? Was it the model or the data?” With versioning, you can compare the current training data with previous versions and pinpoint exactly what changed.

Data versioning also enables reproducibility, a requirement in regulated industries like finance and healthcare.

If an auditor asks, “Why did the model make this decision six months ago?”, you need to be able to recreate the exact model and training data from that point in time.

Tools like DVC (Data Version Control) and MLflow help teams manage this.

In an interview, mentioning data versioning shows you understand that ML systems aren’t just about models. They’re about the entire lifecycle of data and code working together.

With clean, well-structured, and tracked data in hand, it’s time to teach the model how to find patterns in it.

Pattern Machines: How Models Actually Learn

A model doesn’t “know” anything. It finds patterns in data and uses them to make predictions.

8. Model Training & Loss Functions

Model training is the process of showing the model examples and letting it adjust its internal settings until its predictions get closer to the ground truth.

Think of it as a student taking practice tests over and over, getting a little better each time.

The mechanism that drives improvement is the loss function. A loss function measures how wrong the model’s predictions are. After each batch of examples, the model calculates the loss (how far off it was) and adjusts its internal settings to reduce that number.

Over millions of examples, those small adjustments add up.

Different problems need different loss functions.

Predicting a number (like Uber’s ETA) might use mean squared error, penalizing big misses more than small ones. Classifying something (like spam vs. not spam) typically uses cross-entropy loss, which measures how confident the model was in the wrong answer.

The choice of loss function shapes what the model optimizes for. A model trained with mean squared error will try to be accurate on average. A model trained with mean absolute error will be more robust to outliers. Small decisions here have big downstream effects.

But what exactly is the model adjusting? That’s where parameters come in.

9. Parameters & Hyperparameters

Parameters are what the model actually learns.

Think of them as the model’s memory: every pattern gets encoded as a number. GPT-4 has hundreds of billions. A simple recommendation model, a few million. You don’t write them. The model discovers them on its own.

Hyperparameters are the settings that control how the model trains.

You set them before training starts: how fast the model adjusts (learning rate), how many examples it processes at once (batch size), how many times it loops through the data (epochs), and the model’s architecture.

If the model is a student, parameters are the knowledge in their head, and hyperparameters are the study plan: how many hours a day, which subjects first, and how many practice tests.

Bad hyperparameters can make a good model fail.

A learning rate that’s too high, and the model never converges. Too low, and it takes forever to train. Too few epochs and it underfits. Too many and it overfits. In practice, teams run many training experiments with different hyperparameters and compare results on the validation set.

There’s one type of parameter that powers almost every ML system you’ll encounter in interviews: embeddings.

10. Embeddings

An embedding is a way to represent something (a word, a user, a product) as a list of numbers that captures its meaning.

Instead of treating “cat” and “kitten” as completely different labels, embeddings place them close together in a vectorial space because they’re related concepts.

Think of it as a map. On a regular map, cities that are near each other geographically are plotted close together. In an embedding space, concepts that are similar in meaning are plotted close together. “Comedy” and “rom-com” would be neighbors; “horror” would be distant, but still in the same galaxy as other genres. “Accounting” would be in another universe.

Embeddings are everywhere in real ML systems.

Spotify uses song embeddings to find tracks that are musically similar to what you’ve been listening to. Netflix uses movie embeddings and user embeddings to match viewers with films they’re likely to enjoy.

Embeddings are how ML systems make sense of the real world. A user, a product, a sentence. Turn them into vectors, and suddenly you can calculate which ones are similar, which ones are related, and which ones to recommend.

With all this learning machinery, there’s a critical danger: the model might learn too well.

11. Overfitting & Regularization

Overfitting is when a model memorizes the training data too well, including noise and accidents.

It crushed the practice tests by memorizing answers rather than understanding patterns. When the real exam shows up with different questions, it fails. An overfitted model might learn that “every email from Bob is spam” because Bob happened to send spam in the training data, but Bob isn’t always spam.

The opposite problem is underfitting: the model is too simple to capture the real patterns. It fails both the practice tests and the real exam.

Regularization is the umbrella term for techniques that prevent overfitting.

These include adding a penalty for model complexity, randomly dropping parts of the model during training (dropout), or simply stopping training before the model starts memorizing.

You can detect overfitting by watching performance on the training set vs the validation set. If training performance keeps improving but validation performance plateaus or gets worse, the model is memorizing rather than learning.

💡 In interviews, overfitting often comes up as a tradeoff question: “How would you balance model complexity with generalization?”

12. Transfer Learning

Transfer learning is the idea of reusing a model trained on one task for a different but related task.

Instead of training from scratch every time, you start with a model that already understands general patterns and fine-tune it for your specific problem.

Think of it like hiring a chef who already knows how to cook. You don’t teach them to boil water. You teach them the specific recipes at your restaurant. They ramp up much faster than someone who’s never been in a kitchen.

This is especially powerful when you don’t have much data.

Training an image classifier from scratch might require millions of labeled images. But if you start with a model pre-trained on ImageNet (which has millions of generic images), you can fine-tune it on just a few thousand medical images and get strong results.

In practice, transfer learning is the default approach for most teams.

Very few companies train models from scratch. They start with a pre-trained foundation and adapt it. Google’s BERT model, for example, was pre-trained on a massive text corpus and then fine-tuned by thousands of teams for tasks ranging from sentiment analysis to medical record classification.

Transfer learning saves time, data, and compute. But even a well-trained model can be too large to deploy efficiently. That’s where compression comes in.

13. Model Compression

Model compression is a set of techniques for making models smaller and faster without losing too much accuracy.

A model that works great on a research GPU might be far too large or slow for a mobile app or a real-time serving environment.

There are three main approaches:

  • Quantization reduces the precision of the model’s numbers. Instead of storing each parameter as a 32-bit floating point number, you use 16-bit or even 8-bit. The model gets 2-4x smaller with minimal loss in accuracy.

  • Knowledge distillation trains a small “student” model to mimic a large “teacher” model. The student learns not just the correct answers but also the teacher’s confidence levels, which yields better performance than training the small model from scratch.

  • Pruning removes parameters that contribute the least to the model’s predictions, making the model smaller without losing much accuracy.

Apple uses model compression heavily to run ML features on-device: Siri, keyboard predictions, and photo recognition all run on your phone using compressed models.

The full-size versions of these models would drain your battery in minutes.

💡 When an interviewer mentions latency, mobile, or cost, compression is usually part of the answer: quantization, pruning, distillation.

At this point, the model has learned its patterns and is small enough to deploy. But a model sitting on a researcher’s laptop isn’t useful to anyone.

The next challenge: getting predictions to millions of users.

Serving at Scale: From Model to Millions of Predictions

Training a good model is half the job. Serving it to 10 million users per second is the other half.

14. Batch vs Real-Time Inference

Inference is just the technical term for “making predictions.”

Once a model is trained, inference is what it does in production: taking in features and outputting a prediction.

There are two ways to do this:

Batch inference means running predictions on a large dataset all at once, usually on a schedule. Every night, compute recommendations for all 200 million Netflix users and store the results. When someone opens the app, their pre-computed recommendations load instantly.

Real-time inference means computing predictions on demand, the moment a request comes in. When you type a search query into Google, the ranking model runs in real time to order the results for your specific query.

The tradeoff is freshness vs cost.

Batch is cheaper and simpler, but can’t react to what the user is doing right now. Real-time is responsive but requires infrastructure that can handle thousands of predictions per second with low latency.

Most production systems use both.

Netflix pre-computes your home page recommendations (batch) but re-ranks them in real time based on what you just watched.

Once you decide when to make predictions, the next question is how to serve them efficiently.

15. Model Serving & Latency

Model serving is the infrastructure that takes a trained model and makes it available to handle prediction requests. It’s the bridge between “this model works on my laptop” and “this model serves 50 million users.”

Latency is how long a prediction takes. For a search engine, every millisecond matters. Google has found that an extra 500ms of latency reduces traffic by 20%. For a nightly email recommendation, latency barely matters.

In interviews, you’ll often be asked about latency budgets.

A typical constraint might be “predictions must return within 100 milliseconds at the 99th percentile.” This means only the slowest 1% exceed that threshold.

Strategies for reducing latency include using simpler models, caching frequent predictions, quantizing the model to run on cheaper hardware, and batching multiple requests together. The right approach depends on the tradeoff between prediction quality and response time.

Keeping latency low gets even harder when the model needs features that live in different places. That’s where feature stores come in.

16. Feature Stores

A feature store is a centralized system for storing, managing, and serving features.

Without one, every team computes features independently, often with different logic, leading to inconsistencies and bugs. Think of it as a shared kitchen pantry. Instead of each cook buying and preparing their own ingredients, everyone pulls from the same organized inventory.

Feature stores solve a critical problem: training-serving skew.

If the features computed during training are even slightly different from the features computed during serving, the model’s performance will silently degrade. A feature store guarantees that both training and serving use the exact same feature definitions and logic.

Uber’s Michelangelo platform is a well-known example. It stores thousands of features (driver ratings, historical trip times, real-time traffic data) and serves them consistently to both training pipelines and real-time prediction services.

💡 If an interviewer asks “how would you keep training and serving features consistent?”, feature store is the answer they’re looking for.

Feature stores solve consistency. The next decision: where does the model itself live?

17. Cloud vs On-Device Deployment

With cloud deployment, the model lives on a server, and predictions travel over the network. With on-device deployment (also called edge inference), the model runs directly on the user’s phone, car, or sensor.

Cloud deployment is simpler to manage: instant updates for all users, no device constraints, unified access to GPUs. But it requires a network connection and adds latency from the round-trip.

On-device deployment eliminates network latency and works offline, but the model must be small enough to run on constrained hardware, and updates require pushing new model versions to every device.

Google uses on-device models for features like Smart Reply in Gmail on your phone. The model runs locally for instant suggestions. But Google Search ranking runs in the cloud, where it needs massive compute and fresh index data.

The choice often comes down to latency requirements, model size, privacy constraints, and whether the model needs access to centralized data.

18. Prediction Caching

Prediction caching is exactly what it sounds like: storing the results of previous predictions so you don’t have to recompute them.

If a thousand users ask for recommendations for the same trending movie, the system can compute the prediction once and serve the cached result to everyone else.

This is a classic speed-vs-freshness tradeoff.

Cached predictions are fast and cheap to serve, but they might be stale. A user who just watched a movie will still see recommendations based on their pre-watch profile until the cache refreshes.

Caching works best when predictions are expensive to compute, and the input space is predictable.

If you can anticipate the most common queries or user segments, you can pre-compute and cache those predictions. For highly personalized, real-time predictions where every input is unique, caching helps less.

Amazon uses caching heavily for product recommendations.

The “Customers who bought this also bought” section is largely pre-computed and cached. It doesn’t change every time someone loads the page. But the homepage hero recommendations might be more personalized and computed in real time.

Caching speeds things up. But what happens when you need to update the model behind the cache?

19. Model Versioning & Rollbacks

Model versioning means tracking every model you’ve trained (its code, hyperparameters, training data version, and performance metrics) so you can reproduce it or roll back to a previous version if something goes wrong.

Rollbacks are the ML equivalent of “undo.” If you deploy a new model and it starts performing worse, you need to revert to the previous version instantly.

This sounds obvious, but many teams learn this the hard way.

A new model passes all offline tests, gets deployed, and then a subtle bug in the feature pipeline causes it to perform poorly on a specific user segment. Without the ability to roll back quickly, users suffer until the problem is diagnosed and fixed.

Good model versioning also enables A/B testing. You can’t compare Model A vs Model B if you don’t know exactly which model each user is seeing.

Tools like MLflow, Weights & Biases, and SageMaker provide model registries that handle versioning, metadata tracking, and deployment management. In an interview, treating model versioning as critical infrastructure, not an afterthought, shows production maturity.

Now that predictions are flowing to users, the next question is: how do you know if the model is actually working?

Measuring Success: Offline Metrics vs Real-World Impact

20. Offline Metrics (Precision, Recall, AUC)

Offline metrics are how you evaluate a model before it ever sees real users. You run the model on your held-out test set and measure how well it performs.

The most common metrics are:

  • Precision answers: “Of all the items the model predicted as positive, how many were actually positive?” If your spam filter flags 100 emails as spam and 90 really are spam, precision is 90%.

  • Recall answers: “Of all the items that were actually positive, how many did the model catch?” If there were 200 real spam emails and the filter caught 90, the recall is 45%.

  • AUC (Area Under the Curve) measures the model’s ability to rank positive examples higher than negative ones, regardless of any specific threshold.

Precision and recall trade off against each other.

A spam filter that’s extremely aggressive (flags almost everything) will have high recall but low precision. A conservative model flags only what it’s very confident about (high precision), but misses a lot (low recall).

💡 In interviews, always ask: “What matters more, precision or recall?” It shows you understand there’s no universal answer, only tradeoffs that depend on the problem.

Offline metrics tell you if the model is technically good. But the real question is whether it helps the business.

21. Online Metrics

Online metrics measure how the model performs with real users in production.

These are the business metrics that actually matter: click-through rate, conversion rate, revenue per user, time spent on platform, and user retention.

A model can have great offline metrics and still hurt the product. An aggressive recommendation model might increase short-term clicks (good offline metrics) but recommend so much clickbait that users stop trusting the platform and leave (bad online metrics).

At TikTok, offline metrics are just the first filter.

A model that improves precision on “will the user like this?” only ships if online metrics (watch time, completion rate, retention) also go up.

The gap between offline and online metrics is one of the most important concepts in ML system design, and one we’ll cover shortly. But first, there’s a distinction that experienced engineers know to watch for.

But even when a model performs well on both offline and online metrics, things can still go wrong. That’s where operational metrics come in.

22. Operational Metrics vs ML Metrics

ML metrics measure model quality.

Operational metrics measure everything else: latency, throughput, error rates, uptime. When an ML system underperforms, the cause isn’t always the model itself. That’s why operational metrics matter. If the feature store times out, the model gets stale data. If a pipeline breaks, it stops seeing recent behavior. Same model, wrong inputs, worse results.

A recommendation system might suddenly show worse results, not because the model degraded, but because the feature store hit a timeout and started serving stale features, or because a data pipeline broke and the model hasn’t been retrained on recent data.

In an interview, if you’re asked, “How would you debug a model that’s performing worse in production?”, the best answer starts with operational metrics.

Check if the system is healthy first. Are features being served correctly? Is latency within budget? Are all data pipelines running? Only after ruling out infrastructure issues should you investigate the model itself.

💡 Most ML production fires are infrastructure problems, not model problems. Always check the plumbing before blaming the algorithm.

Once you’re tracking the right metrics, you need a way to compare model versions. That’s what A/B testing is for.

23. A/B Testing

A/B testing is the gold standard for measuring whether a new model actually improves the product.

You split real users into two groups: Group A gets the current model, Group B gets the new model. After enough data, you compare the online metrics between the two groups.

This is the only reliable way to establish causation. Offline metrics can tell you the new model is more accurate, but only an A/B test can tell you whether that accuracy translates into better user experience and business outcomes.

The keyword is statistical significance.

You need enough data to be confident that the difference you see is real and not just random noise. Running an A/B test for too short a time, or on too few users, leads to bad decisions.

Netflix runs hundreds of A/B tests simultaneously across different parts of its recommendation system. A new ranking model might look great in offline tests, but actually decrease viewing time when tested on real users.

Without A/B testing, they’d never catch that.

Merge into one paragraph: “A/B testing often reveals something frustrating: the best model on paper loses in production. That’s the offline-online gap. Why does it happen?

24. The Offline-Online Gap

Offline metrics are calculated on historical data, a frozen snapshot of the past.

But production is live. Users react to predictions, preferences shift, new products launch. The model learned one reality, but it’s serving in another.

That’s the offline-online gap.

Another common cause: in offline evaluation, you measure the model’s prediction quality.

But in production, the user experience depends on the entire system: latency, UI, context. A more accurate model that’s slower to serve might lose to a faster, slightly less accurate one because users don’t wait around.

This is why production ML teams never skip A/B testing, even when offline metrics look great. And it’s closely related to a specific technical trap that catches many systems.

25. Training-Serving Skew

Training-serving skew occurs when the data or features the model sees during training differ from those it sees in production. The model learned patterns from one distribution, but it’s serving predictions on a slightly different one.

This can happen for subtle reasons.

Maybe a feature that’s computed as a daily average during training is computed as a real-time rolling average during serving. Or a feature uses timezone-adjusted timestamps in training but UTC timestamps in serving. The model doesn’t know the difference. It just makes worse predictions.

Training-serving skew is one of the most common and hard-to-debug problems in production ML. The model doesn’t throw an error. It just silently gets worse. The fix is feature stores and shared feature computation logic.

Feature stores and shared feature computation logic fix skew.

But they don’t tell you if the model actually performs better. For that, you need experiments. A/B is the gold standard, but they’re slow. Interleaving gets you answers faster.

26. Interleaving Experiments

Interleaving is an alternative to A/B testing that can detect differences between ranking models much faster. Instead of splitting users into separate groups, you show each user results from both models, mixed together on the same page, and measure which model’s results users prefer.

Think of it like a blind taste test.

Instead of giving one group Pepsi and another group Coke, you give everyone both and see which one they reach for more often. Because every user sees both models, you need far fewer users to reach statistical significance.

Netflix pioneered this approach.

Rather than running a traditional A/B test for weeks, they interleave results from competing ranking models in the same row. If users consistently engage more with one model’s selections, the signal emerges much faster, sometimes in days instead of weeks.

The catch is that interleaving only works well for ranking and recommendation problems. It doesn’t apply to systems where the user sees only one result (e.g., a binary classification). But for the ML systems most commonly discussed in interviews (search, recommendations, feeds), it’s a powerful evaluation tool.

27. Data Drift

Data drift is when the statistical properties of the input data change over time. The model was trained on data that looks one way, but the real-world data starts looking different.

Imagine you trained a delivery time prediction model in 2019.

Then COVID hits, and suddenly, traffic patterns, restaurant hours, and order volumes look nothing like the training data. The model’s predictions start degrading, not because the model broke, but because the world changed.

Data drift is slow and sneaky.

It doesn’t trigger errors. Your model continues making predictions confidently. They just get gradually worse. Common causes include seasonality, changing user demographics, new product launches, and shifts in user behavior.

Detecting data drift requires monitoring the statistical properties of incoming features and comparing them with the distribution of the training data. When drift exceeds a threshold, it’s time to retrain.

Data drift is about the inputs changing. But sometimes the relationship between inputs and outputs changes too.

28. Concept Drift

Concept drift is when the relationship between features and labels changes over time. The data might look the same, but what constitutes a “correct” prediction has shifted.

The difference from data drift is subtle but important.

For example, what “good content” means on TikTok evolves constantly. A video style that was engaging six months ago might feel stale today. The features (video length, music, effects) haven’t changed, but what users respond to has.

The mapping from features to engagement has shifted.

Another example: credit scoring models trained before a recession might fail during one.

The same income level and credit history that previously predicted low risk now predict higher risk. The features are the same; the world’s response to them changed.

💡 Data drift is easy to spot: your input distributions shift and monitoring catches it. Concept drift is invisible. Inputs look exactly the same, but the right answer has changed. You only find out when you check predictions against outcomes.

Both types of drift are made more complex by a powerful force that acts on every ML system in production.

29. Feedback Loops

A feedback loop occurs when a model’s predictions influence the data it will be trained on in the future. The model shapes its own future training data, for better or for worse.

Virtuous loops make the system better over time. When Spotify recommends a song, and you play it, that interaction generates new data that helps Spotify understand your taste better. More listening → better data → better recommendations → more listening.

Vicious loops make the system worse. If a hiring model gives lower scores to candidates from a certain background, fewer of them get hired, which generates training data suggesting they’re “less qualified,” which reinforces the bias. The model becomes a self-fulfilling prophecy.

Feedback loops also cause a subtler problem: the model stops exploring.

If a recommendation system only shows you what it already thinks you’ll like, it never discovers you might love jazz, because it never recommends jazz.

Breaking vicious loops requires intentional interventions: introducing randomness into predictions (exploration), collecting data independently of the model, and monitoring for bias in outcomes.

Knowing that models degrade over time, the question becomes: when and how should you retrain?

30. Retraining Strategies

Retraining means updating a model with newer data so it stays accurate as the world changes. The question is how often and what triggers it:

  1. Scheduled retraining happens on a fixed cadence: daily, weekly, or monthly. It’s simple and predictable. Netflix might retrain its recommendation model weekly to incorporate the latest viewing patterns.

  2. Triggered retraining happens when a monitoring system detects that performance has dropped below a threshold. For example, when data drift exceeds a certain level or online metrics decline.

  3. Continuous training means the model is constantly learning from new data in near real-time. This is the most complex, but it keeps the model fresh.

The tradeoff is freshness vs cost and complexity.

Continuous training requires heavy infrastructure. The downside: there’s no buffer. A bug in a pipeline, a labeling error, a sudden anomaly, and the model absorbs it before anyone notices.

In interviews, match the strategy to the use case.

Fraud patterns evolve daily, so train continuously. Movie preferences shift slowly, so weekly is fine. Interviewers want to see you reason through it, not memorize a default.

Retraining keeps models fresh. But what happens when the model fails anyway?

31. Failure Modes & Degradation Strategies

Every ML system will eventually fail.

What separates good systems from bad ones is how they fail. Graceful degradation means the system continues to provide value even when the ML component breaks.

Common failure modes include: the model server goes down, features become unavailable, predictions take too long, or the model starts returning obviously wrong results.

The key principle is having fallback strategies.

If the personalized recommendation model fails, fall back to popularity-based recommendations. If the real-time pricing model times out, use the last known good prediction. If the fraud detection model throws an error, flag the transaction for manual review rather than auto-approving it.

Amazon’s product recommendations have multiple fallback layers.

If the personalized model can’t run, it falls back to “customers who bought this also bought,” then to category bestsellers, then to site-wide popular items. The user always sees something reasonable.

Fallbacks keep the system running. But how do you know when to trigger them? That’s where monitoring comes in.

32. Model Monitoring & Alerting

Model monitoring is the practice of continuously tracking a model’s behavior in production to catch problems before they become disasters.

Unlike traditional software, where bugs usually cause obvious errors, ML models fail silently. They keep returning predictions that look normal but are gradually getting worse.

A good monitoring system tracks multiple layers:

  • input data distributions (are the features shifting?),

  • prediction distributions (is the model’s output changing?),

  • model performance metrics (are precision and recall holding?),

  • and business metrics (are users still engaging?).

Monitoring shows you what’s happening.

Alerting tells you when to care. When a metric crosses a threshold (say, feature freshness drops below a certain level, or the model’s prediction confidence suddenly shifts), an alert fires. The best systems have tiered alerts:

  • informational (investigate when you can),

  • warning (investigate today),

  • and critical (page someone now).

The goal: catch problems at layer one before the user complains. Better yet, catch them before the new model is even live.

33. Shadow Deployment & Canary Releases

Shadow deployment and canary releases are strategies for safely deploying new models without risking the entire user base.

In a shadow deployment (also called shadow mode or dark launch), the new model runs alongside the current production model. Both receive the same requests, but only the old model’s predictions are served to users. The new model’s predictions are logged and compared. This lets you evaluate real-world performance without any user impact.

In a canary release, the new model is deployed to a small percentage of traffic (say, 1% of users) while the other 99% still use the old model. If the new model performs well on that 1%, you gradually increase the traffic split: 5%, 10%, 25%, and so on until it reaches 100%.

The two approaches complement each other.

Shadow deployment is the safest way to validate a new model against real traffic with zero risk to users. Canary releases are how you gradually roll out a model that’s passed shadow testing, with the ability to roll back instantly if something goes wrong.

This is how most major tech companies ship model updates.

LinkedIn, for example, shadow-tests new feed ranking models for days before starting a canary rollout. If the canary cohort shows any degradation in engagement metrics, the rollout is automatically halted.

Common Interview Problems: Five Systems You’ll Be Asked to Design

Every ML interview question is a variation of a few core patterns. Learn them, and you can improvise the rest.

34. Recommendation Systems

Recommendation systems predict what a user will like based on their past behavior and the behavior of similar users. They’re the most commonly asked ML design questions because they touch every concept we’ve covered: features, embeddings, serving, metrics, drift, and feedback loops.

There are two fundamental approaches:

  • Collaborative filtering finds users who behave similarly to you and recommends what they liked. “Users who watched Breaking Bad also watched Better Call Saul.”

  • Content-based filtering matches the attributes of items you’ve liked with similar items. “You liked this action movie with a strong lead, here’s another one.”

Modern systems combine both approaches and add deep learning.

Netflix’s system uses user embeddings and movie embeddings. When your user embedding is close to a movie’s embedding in the latent space, that movie surfaces in your recommendations.

The typical architecture has two stages: candidate generation (quickly narrow millions of items to hundreds of candidates) and ranking (carefully score and order those candidates).

Recommendation is fundamentally a ranking problem. So is search. So are ads. That makes ranking one of the most important concepts to nail.

35. Search & Ranking

Search and ranking is the problem of ordering a set of items by relevance to a query or context. Google Search, Bing, LinkedIn’s feed, Airbnb’s listing order. All are ranking problems.

The ML model takes a query (or user context) and a set of candidate items, and outputs a relevance score for each. The items are then sorted by score and presented to the user.

Key features in a ranking model typically include:

  • query-item relevance (how well the item matches what the user is looking for),

  • item quality signals (ratings, freshness, popularity),

  • user personalization signals (past behavior, preferences),

  • and context signals (time of day, device, location).

The metric that matters most for ranking is usually NDCG (Normalized Discounted Cumulative Gain), which measures how well the model puts the best results at the top. Position matters a lot. A great result on page 2 is nearly worthless because most users never scroll that far.

Airbnb’s ranking system, for example, considers hundreds of features: listing quality, host responsiveness, price relative to similar listings, the guest’s preferences from past bookings, and real-time availability. The model re-ranks results in real time based on the specific user viewing the page.

Not every ML system is about showing users what they want. Some exist to stop what shouldn’t happen.

36. Fraud Detection

Fraud detection is a classification problem with extreme class imbalance, high stakes, and adversarial opponents, making it one of the most challenging questions in ML system design.

The core challenge is that fraudsters actively adapt.

Unlike movie preferences, which shift gradually, fraud patterns change deliberately and quickly. A model that catches today’s fraud tactics might miss tomorrow’s, because the fraudsters are studying the system and finding new ways around it.

This makes fraud detection a constant arms race.

The model needs to be retrained frequently (sometimes continuously), and the system needs multiple layers of defense: rule-based filters for known patterns, ML models for novel patterns, and human review for ambiguous cases.

Key design considerations include:

  • handling extreme class imbalance (1 in 10,000 transactions),

  • minimizing false positives (blocking legitimate customers is expensive),

  • operating in real time (you have milliseconds to decide),

  • and dealing with concept drift (fraud patterns evolve constantly).

Stripe’s fraud detection system, Radar, uses a combination of rule-based systems and ML models trained on billions of transactions across its network.

The model evaluates hundreds of signals (transaction amount, location, device fingerprint, merchant category, user behavior patterns) and returns a risk score in milliseconds.

37. Ads Ranking

Ads ranking determines which advertisement to show a user at a given moment.

It’s one of the highest-revenue ML applications in the world. Google, Meta, and Amazon all make the majority of their revenue from ML-powered ad systems.

The core challenge is optimizing for multiple objectives simultaneously. The system must balance:

  • advertiser value (they want clicks and conversions),

  • user experience (they don’t want irrelevant or annoying ads),

  • and platform revenue (the business needs to make money).

The ranking model typically predicts both the probability that a user will click the ad (pCTR) and the probability they’ll convert (pCVR), then combines these with the advertiser’s bid to produce a final ranking score.

Ads ranking is particularly interesting in interviews because it introduces the concept of auction mechanisms.

Advertisers bid on ad slots, but the highest bidder doesn’t always win. The system factors in predicted engagement and ad quality. This alignment of incentives is what makes the system sustainable.

The latency requirements are brutal.

The entire pipeline (candidate generation, feature retrieval, model inference, auction) must complete in under 100ms because the ad must be ready before the page finishes loading.

38. Content Moderation

Content moderation uses ML to detect and remove harmful content (hate speech, misinformation, graphic violence, spam) at a scale that human reviewers alone can’t handle. Platforms like YouTube, Facebook, and TikTok see millions of posts per hour.

No human team can review them all.

The ML system typically operates as a multi-stage pipeline. A fast, lightweight model scans all content in near real-time and assigns risk scores. Content above a high-confidence threshold is automatically removed. Content in an ambiguous middle zone gets routed to human reviewers. Content below the threshold stays up.

The core tradeoffs are precision vs recall with real consequences.

Too aggressive (high recall, low precision) and you censor legitimate speech, angering users and attracting regulatory scrutiny. Too lenient (high precision, low recall) and harmful content stays up, damaging the platform’s reputation and user safety.

Content moderation also faces severe adversarial challenges.

Bad actors constantly evolve their tactics: misspellings, coded language, images with text overlays, or borderline content that’s technically within policy. The model must be retrained frequently, and the policy definitions themselves change over time (a form of concept drift).

Now let’s zoom out and look at the patterns that tie everything together.

Tying It Together: How to Structure Your Answer

This article is a plain-English field guide to ML system design.

You don’t need to know TensorFlow, write Python, or understand gradient descent math. Just what these terms mean in practice, so you can structure clear answers, ask sharp follow-up questions, and walk through any ML system with confidence.

You’ve got the vocabulary. Now here’s how to use it, whether you’re in an interview, a design review, or explaining a system to your team.

Every ML system design question follows the same skeleton. Learn these patterns, and you can improvise the rest.

The Two-Stage Pattern

Almost every large-scale ML system follows a two-stage architecture: candidate generation → ranking.

The reason is simple math.

If you have 100 million items, you can’t run a complex ranking model on all of them for every request. It would take too long. So the system first uses a fast, lightweight model to narrow the field from millions to a few hundred candidates. Then a more powerful (and expensive) model carefully ranks those candidates.

YouTube uses this pattern.

A lightweight model quickly retrieves a few hundred video candidates from a pool of billions. Then a deep neural network carefully ranks those candidates based on predicted watch time, considering your full viewing history and current context.

This pattern applies to recommendations, search, ads ranking, and almost any system where you’re selecting from a very large pool.

In an interview, describing this two-stage approach immediately signals that you understand how these systems work at scale.

The Cold Start Problem

The cold start problem occurs when the system has no data about a new user, a new item, or both. A new user signs up for Spotify.

What do you recommend when you know nothing about them? A new song is uploaded. Who should hear it?

Common solutions include:

  • For new users: ask for preferences during onboarding, use demographic features, fall back to popularity-based recommendations, or leverage “wisdom of the crowd” by showing what’s broadly popular.

  • For new items: use content-based features (genre, description, creator) until behavioral data accumulates, or use an “exploration” strategy that deliberately shows new items to a random sample of users to collect feedback.

In interviews, mentioning the cold start problem shows you think about edge cases that real production systems have to handle.

A Framework for Any ML Design Question

Here’s how to approach any ML system design question:

  1. Clarify the problem. What are we predicting? Who are the users? What are the constraints (latency, scale, cost)?

  2. Define the data. What features are available? How do we get labels? Is there class imbalance? What does the training data look like?

  3. Design the model. What type of model fits the problem? What’s the training pipeline? How do we handle overfitting?

  4. Plan the serving. Batch or real-time? What’s the latency budget? Do we need a feature store? Cloud or on-device?

  5. Choose the metrics. What offline metrics matter? What online metrics tie to the business? How do we A/B test?

  6. Handle production. How do we detect drift? What are the retraining strategies? What are the fallback strategies if the model fails?

The beauty of this framework is that it maps directly to this newsletter's sections.

Each stage has clear concepts, tradeoffs, and vocabulary. Walk through this structure in any interview, and you’ll sound like someone who’s actually built ML systems, not someone who just read about them.

Closing Thoughts

You just read 38 concepts. Forget most of them.

What matters: when the interviewer asks you to design a recommendation system, you don’t freeze. You ask about the data. You talk about candidate generation and ranking. You mention latency constraints, cold start, feedback loops, and how you’d know if it’s working.

Every ML system has tradeoffs all the way down. Now you speak the language.
