In the early days, running apps was simple.

Most applications ran on a single server, and managing them was quite easy. Then microservices became popular. Instead of a single app on a single server, companies were running hundreds of apps across hundreds of servers.

But managing this became extremely difficult.

Engineers had to decide where apps should run, what to do when apps crash, how to handle more traffic, and how to update apps without downtime. Most people handled this with scripts and manual work. It worked for a while, but as systems grew, system started breaking more often, and downtime became more common.

Google faced this problem on a massive scale.

So they built an internal system called Borg. Borg was used to manage apps across thousands of servers. It automates scheduling, scaling, and self-healing across many servers. Years later, Kubernetes (k8s) was built based on many of the same ideas as Borg and got released as an open-source system. Since then, it has become the standard platform for running distributed systems and microservices.

Kubernetes could look simple from the outside, but within the cluster, many components constantly work to keep your apps running.

Kubernetes Architecture Overview

To understand Kubernetes, we first need to look at its architecture.

Then we can dive into the individual components…

Kubernetes architecture is a distributed system:

It doesn’t run on just one server. Instead, it operates on a group of servers that work together, known as a Kubernetes Cluster. These servers could be virtual machines or bare metal servers. The components of Kubernetes are distributed across these servers over a single network.

At the highest level, the Kubernetes cluster consists of two key components: control plane and worker nodes.

We will go through each of these components in detail later...

Control Plane Node

Think of the control plane as the brain of the Kubernetes cluster.

It manages global decisions for the cluster. Plus, it schedules apps, checks system health, and ensures the cluster remains in the desired state.

The control plane contains these components:

  • kube-apiserver

  • etcd

  • kube-scheduler

  • kube-controller-manager

  • Cloud-controller-manager

Worker Node

Imagine the worker node as the muscle of the Kubernetes cluster.

It’s responsible for running workloads (containerized applications) in the cluster. And it contains these components:

  • kubelet

  • kube-proxy

  • Container runtime

i.e., control plane decides what runs where; worker nodes run the containers.

Kubernetes continuously checks and fixes the system. This ensures everything runs as expected…

A cluster can have many control plane nodes and worker nodes; this usually depends on the number of workloads to be deployed.

In production systems, it’s typical to have many control plane and worker nodes. This setup keeps the system stable. It also ensures applications run smoothly, even if some machines fail or are unavailable.

Plus, Kubernetes has a strong, decentralized structure. It automatically moves workloads to healthy nodes upon node failure. This keeps your system running smoothly.

This makes Kubernetes the foundation of a reliable and self-healing distributed system.

Desired State and Actual State

One of the most important ideas in Kubernetes architecture is the concept of desired state and actual state.

When we deploy an application to Kubernetes, we don’t start it in the cluster ourselves. Instead, we tell Kubernetes what we want the system to look like; for example, we could say we want three replicas of an application running.

This description of what we want is called the desired state.

The actual state is what is currently running in the cluster.

Kubernetes always checks the desired state against the actual state. If it finds a difference, it automatically tries to fix it.

For example, if one app crashes or a node fails, the actual state no longer matches the desired state. Kubernetes detects this and automatically creates a new app on healthy nodes to bring the system back to the desired state. The ongoing task of checking and fixing the system is called the reconciliation loop.

This is a key concept in how Kubernetes operates.

Now we understand Kubernetes architecture, let’s learn the control plane and worker nodes…

Kubernetes Control Plane Core Components

We already saw how the control plane makes global decisions for the cluster, but it does NOT do that as a single component.

Instead, control plane is divided into five components that work together to manage the entire cluster state.

These components have their own specific roles:

  • One component is the central hub for all cluster communication.

  • Another stores the cluster data.

  • One makes scheduling decisions.

  • Another continuously monitors cluster health and keeps it in the desired state.

  • And the last one integrates Kubernetes with your cloud provider to manage resources such as load balancers, routes, and storage volumes.

Let’s look at each of the control plane components and the concepts behind each:

1. Kube-Apiserver

The kube-apiserver is central to the Kubernetes control plane.

It serves as the key hub of the cluster, exposing the Kubernetes API. Almost every operation in the Kubernetes cluster goes through the API server. The other cluster components don’t talk directly with each other. Instead, they use the kube-apiserver to read and update the cluster state. This lets the parts work independently but still connect through a central system. Also, when you interact with Kubernetes, you do not interact with the Kubernetes nodes and their components directly.

Instead, you interact with it via kube-apiserver.

It handles your requests and updates the cluster state.

All messages between the API server and other components are encrypted using TLS1. This keeps unauthorized users out and protects communication within the cluster.

i.e., API server is central communication hub of Kubernetes; without it, the cluster cannot function.

Key Responsibilities of Kube-Apiserver

  1. Exposes cluster API endpoint: It’s the only component in the control plane that the outside world can talk to. When you run a kubectl command (kubectl is the command-line tool to interact with Kubernetes), it sends a request to the API server over HTTPS. When your app gets deployed in the cluster, it’s talking to the API server.

  2. Single entry point for all operations: All requests to the cluster go through the API server. This includes requests from you and from internal Kubernetes components. Components do NOT communicate directly with each other. They talk only to the API server. Because of this, API server always has a complete picture of what is happening in the cluster.

  1. Authentication and Authorization: It checks who is making the request. Then, it confirms if they have permission to take the action. If either check fails, the request stops right there.

  1. Notifies the rest of the system when something changes: Once a change is saved, API server notifies every interested component.

  1. Stores cluster state in etcd: Kubernetes keeps all cluster details in etcd. This is a fast, lightweight database made for storing cluster state. Nothing reads or writes to it directly except the API server. Every change has to go through it first, this keeps the data clean and consistent.

Since the API server stores all cluster state in etcd, etcd becomes the source of truth for the entire Kubernetes cluster.

Let’s now look at etcd and understand its role in the control plane…

2. Etcd

etcd is a distributed key-value store (distributed database) that Kubernetes uses to store the entire cluster data.

It keeps track of what is running, what should run, and how each Kubernetes component is set up. Since it stores all data about the cluster, it is also called the single source of truth for the Kubernetes cluster.

Kubernetes API server stores all information ever received in etcd.

The scheduler and controller manager monitor the API server for changes. They help keep the cluster in its desired state. The API server reads data from etcd. This makes etcd the central storage system for the entire cluster.

etcd is a key part of the Kubernetes control plane.

It’s crucial to back it up regularly in production settings. If etcd data is lost, the cluster loses its state. So Kubernetes won’t know what applications are running, what nodes exist, or what the system’s desired state is.

i.e., etcd is the database that stores everything about the cluster.

Key Responsibilities of Etcd

  • Stores cluster state: All Kubernetes objects are stored in etcd. This includes Pods, Deployments, Services, Nodes, ConfigMaps, and Secrets.

  • Acts as the source of truth: The entire cluster state is stored in etcd, and all the components in the cluster rely on this data to make decisions.

  • Enables cluster recovery: Backups of etcd can be used to restore the entire cluster state in case of failure.

Also, etcd is the only StatefulSet component in the control plane.

i.e., etcd must be carefully managed and backed up, as it contains the entire cluster state.

Now we know how Kubernetes stores its cluster state; let’s explore how it decides where to run applications…

3. Kube-Scheduler

The kube-scheduler decides which node will run a pod.

A pod is the smallest unit you can deploy in Kubernetes. It acts as a wrapper for one or more containers. Whenever a pod is created, it remains in the cluster without a node being assigned to it.

The scheduler always checks for these pods.

It assigns them to the right node based on available resources and pod setup.

Let’s learn how the scheduler works:

  1. Watches for unassigned Pods: The kube-scheduler monitors the API server. It checks for pods that haven’t been assigned to any node after creation.

  2. Gets the list of available nodes: It gets the information about all worker nodes and their available resources.

  3. Filters Nodes: The scheduler removes nodes that don’t meet the pod's requirements. This includes:

    • Not enough CPU or memory

    • Not enough GPU

    • Node is under maintenance

    • Pod needs a GPU, but the node lacks one

  4. Scores for remaining nodes: After removing some nodes, it scores each remaining node. It considers resource availability, scheduling policies, load balancing, and so on. Then, it selects the node with the highest score from the filtered list.

  5. Updates the Pod information: The scheduler updates the Pod object via the API server and assigns the selected node.

i.e., scheduler does not run the pod itself; it only decides which node the pod should run on.

Once the scheduler assigns a Pod to a node, kubelet on that node is responsible for actually running the container.

4. Kube-Controller-Manager

The kube-controller-manager is part of the control plane.

It monitors the cluster and ensures the actual state matches the desired state. It runs multiple controllers, each handling a specific task in the cluster. These controllers monitor the cluster’s state using the Kubernetes API.

If they find a mismatch between the desired and actual state, they work to correct it.

To understand this better, let’s look at an example:

Imagine an application on Kubernetes set to run three replicas. This is the cluster’s desired state. But one of the replicas crashes, and the actual state becomes 2 instead of 3. The controller will detect this difference and will automatically create a new replica of the application to make it three again. This is how the controller continuously monitors the cluster state and matches it with the desired state.

Kubernetes is self-healing and highly automated because it continuously monitors the cluster. It resolves differences between the desired and actual states.

Here is a list of important built-in Kubernetes controllers:

  • Node Controller: Detects node failures and responds when nodes become unavailable.

  • Replication Controller: Ensures the correct number of Pod replicas are running.

  • Deployment Controller: Handles rolling updates and ensures Deployments maintain the desired state.

  • Endpoint Controller: Updates endpoints for Services when Pods change.

  • Namespace Controller: Manages namespace lifecycle and resource cleanup.

  • Service Account Controller: Creates and manages service accounts and tokens.

  • Job Controller: Ensures jobs are completed successfully.

All the controllers in Kubernetes work as a control loop.

i.e., it continuously monitors the cluster state via the API server and compares the actual state with the desired state. Kubernetes has a control loop feature that’s key to its design.

This allows for self-healing, auto-scaling, and rolling updates.

5. Cloud Controller Manager (CCM)

The kube-controller-manager manages internal cluster tasks.

But Kubernetes must also connect to cloud providers for resources.

This includes:

  • Load balancers for services

  • Storage volumes for persistent data

  • Virtual machines for nodes

The cloud controller manager handles this.

The cloud controller manager helps Kubernetes stay cloud-agnostic. It does this by keeping cloud-specific logic separate from the main Kubernetes components. Kubernetes can run on various cloud providers, such as AWS, Google Cloud, and Azure. It can also work in on-premises environments. Best of all, there’s no need to change the core Kubernetes code.

The cloud controller manager connects Kubernetes to the cloud provider’s infrastructure.

We have looked at the control plane components that manage the cluster and make decisions. But the control plane does not run applications itself. The actual applications run on the worker nodes.

So let’s look at the worker node components and see how they work…

Kubernetes Worker Node Core Components

The actual application and workload run on Kubernetes worker nodes.

The control plane decides which apps to run and where to run them. While worker nodes handle these apps, report their status, and ensure everything runs smoothly.

Each worker node has several parts that help Kubernetes run and manage containers on that machine.

The key components of a worker node are kubelet, container runtime, and kube-proxy.

Let’s learn these one by one:

1. Kubelet

The kubelet is the primary component on every worker node, and it acts as a Kubernetes agent that runs as a systemd daemon2.

It’s responsible for managing the pods assigned to a node and ensuring that all workloads on that node run correctly.

Kubelet talks to the API server to get instructions on which pods to run on which node. It receives pod specs and then uses the container runtime to start and manage the containers.

If a container crashes or stops, the kubelet tries to restart it to maintain the desired state.

Key Responsibilities of Kubelet

  • Container management (CRI) uses the Container Runtime Interface to talk with the container runtime. This helps start and manage containers.

  • Logs and exec access offer endpoints for streaming logs and running commands in containers.

  • Storage management (CSI) works with storage plugins via the Container Storage Interface. It allows attaching and mounting volumes.

  • Networking setup (CNI) uses CNI plugins to assign Pod IP addresses and configure networking rules.

  • Health monitoring monitors container & node health and reports status to the control plane.

i.e., kubelet performs three key tasks on a node: manages containers via CRI, handles storage via CSI, and oversees networking via CNI.

2. Container Runtime

This component is responsible for running containers on the Kubernetes worker node.

Kubernetes itself cannot run containers directly. So it uses a container runtime such as containderd to pull container images, create containers, start them, and stop them when needed. It also handles storage and networking for each container.

When the Kubelet gets pod specs from the API server, it works with the container runtime. It pulls the needed container image from the registry and starts the container.

3. Kube-proxy

Kube-proxy is a key component on every worker node.

It manages networking and traffic routing within a Kubernetes cluster.

When you deploy applications on Kubernetes, they’re exposed through a service. A service provides a stable IP address and DNS name3 for a group of pods. It watches the API server for changes related to pods or services. When a new service is created, or a pod goes down, kube-proxy updates the network rules on its node.

This ensures traffic is always directed to live and ready pods.

Traditionally, kube-proxy used iptables.

Iptables are rules in the Linux kernel that intercept network packets and redirect them. You don’t see this process, but it ensures your request reaches the right destination. Meanwhile, kube-proxy quietly rewrites traffic routes.

Many clusters are gradually replacing kube-proxy with eBPF4-based tools, such as Cilium.

eBPF performs the same traffic routing more efficiently. It has much less overhead, especially at scale, where iptables rules can number in the thousands and affect performance.

In short, kube-proxy ensures that requests coming to a Service are routed to the correct Pods, even if the Pods are running on different nodes.

So far, we have understood the architecture and core components of Kubernetes.

Now, the next question should be: how do all these components actually work together to run an application?

To understand how it all works, let’s look at how Kubernetes operates as a system…

How Kubernetes Works

Kubernetes consists of many components that work together in specific ways.

Let’s go through the process step by step and see what happens inside the cluster when we deploy an application…

Step 1: Desired State Is Defined

To define the desired state, the user could write a YAML file that describes what should run in the cluster.

For example, the user could define:

  • Which container image to run

  • How many replicas of the application should run

  • How much CPU and memory the application needs

  • Networking configuration

  • Environment variables and secrets

The user applies this configuration to the cluster using the kubectl command.

This does not start the containers; instead, it tells Kubernetes how the system should look. This is called the desired state.

Step 2: Request Is Processed by the API Server

After the user applies the configuration, the request hits kube-apiserver. This is the entry point of the cluster.

API server then performs these tasks:

  • Validates the request

  • Authenticates and authorizes the user

  • Creates Kubernetes objects (such as Pods or Deployments)

  • Stores the desired state in etcd

Once the desired state is saved in etcd, Kubernetes understands that an application must run. But it still needs to determine where the application will run.

Step 3: Pods Are Assigned to Nodes by the Scheduler

The kube-scheduler continuously watches the API server for new Pods that have not yet been assigned to a node.

After finding these unscheduled pods, it looks for worker nodes by filtering and scoring the nodes based on several factors, such as:

  • Available CPU and memory

  • Node health

  • Affinity and anti-affinity rules

  • Taints and tolerations

  • Resource requests and limits

After the scheduler selects a node, it updates the pod information in the API server with the chosen node.

Step 4: Pods Are Started by the Kubelet

The kubelet on the chosen node is also watching the API server.

The moment it sees that a pod has been assigned, it immediately starts taking action. It pulls the container from the registry. Then, it creates the container using the runtime. Next, it starts the container and monitors it to keep it running.

If the container crashes, the kubelet “restarts” it.

If the node loses contact with the control plane, the kubelet keeps the containers running based on what it last knew.

Step 5: Networking Is Managed by Kube-Proxy

After your pods are running, they need to communicate with each other and receive traffic from users.

This is handled through Kubernetes Services and networking components.

Kube-proxy runs on each worker node and helps route traffic to the correct Pods.

Services provide a stable IP and load balance traffic across many pods.

Step 6: Desired State Is Maintained by Controller Manager

This is what makes Kubernetes different from a simple deployment tool…

Once your application is running, Kubernetes does NOT stop working.

The controller manager monitors the cluster’s current state. It checks this against the desired state you set:

  • If a pod crashes, it creates a new one.

  • If a node goes down, it reschedules the pods that were running on it.

  • If someone manually deletes a pod, it brings it back.

You said you wanted three replicas of your app running? Kubernetes will keep working to make that true, not just once, but continuously, forever!

This is the reconciliation loop.

And this is the core idea behind how Kubernetes works. These steps make Kubernetes self-healing, fault-tolerant, and scalable. It keeps your applications running just as you intended.

Core Kubernetes Objects

The core Kubernetes components are API server, scheduler and kubelet.

But these components do NOT directly manage the workloads in Kubernetes. Instead, everything in Kubernetes is represented as an object. These are the building blocks you define, deploy, and manage. Think of them as the vocabulary you use to tell Kubernetes what you want running in your cluster.

You don’t manage containers and servers by hand.

Instead, you define objects that describe the system. Kubernetes then works continuously to match the state these objects define. This object-based model is one of the most important ideas in Kubernetes architecture.

Kubernetes objects can be broadly grouped into three categories:

  • Workload objects

  • Networking objects

  • Configuration objects

Each category plays a different role in managing applications in the Kubernetes cluster.

Let’s look at what role each category plays one by one:

Workload Objects

Workload objects describe what applications should run in your Kubernetes cluster and how…

These objects mainly define how the container should run, how many instances of a container should run, and where they should run.

1. Pod

It’s the smallest deployable unit in Kubernetes.

Every container you run in Kubernetes lives inside the pod. A Pod usually runs one container. Yet it can run many containers that work closely together.

These containers share the same network and storage.

Pods are ephemeral: they’re temporary and can be created/destroyed at any time.

If a Pod crashes or the node on which it is running fails, Kubernetes automatically creates a new Pod to replace it. But when a Pod is replaced, any data stored in it is lost. Because of this, we do NOT store crucial data directly inside Pods. Kubernetes uses persistent storage, such as Persistent Volumes, to keep data safe. This data can survive Pod restarts or failures.

Pods are never created or managed directly.

They’re usually created and managed by higher-level objects, such as deployments and daemonsets.

2. ReplicaSet

Its only job is to ensure a specified number of Identical Pods are running at any given time.

If you specify three copies and one crashes, ReplicaSet creates a new one. If you accidentally end up with four, it deletes one of them.

ReplicaSets are not created directly either.

Deployments handle ReplicaSets for you.

i.e., you get all the features of a ReplicaSet. Plus, you can easily roll out updates and roll them back.

3. Deployment

It’s an object you could use to run stateless apps.

This includes web servers, APIs, and background workers. Its job is to manage the ReplicaSet underneath, which in turn manages the pods underneath it. It also provides features such as rolling updates and rollbacks.

4. DaemonSet

Its only job is to ensure a copy of a specific pod runs on every node in the cluster or on every node matching a certain criterion.

It’s NOT about running many copies of your app as ReplicaSet does. Instead, it’s about running one copy per node.

This is often used for system-level services. Examples include logging agents, monitoring agents, and networking components. These services need to run on every node.

Whenever you need something running everywhere, a DaemonSet is the right object.

5. StatefulSet

Most applications don’t care which pod handles a request; any replica would do.

But some applications do care...Databases or distributed systems need stable identities. They also require predictable startup and shutdown orders. Plus, they need persistent storage that remains bound to them even if they restart on a different node.

StatefulSets are used during these scenarios.

Each pod in a StatefulSet has a fixed name, such as pod-01, pod-02, or pod-03. It also gets its own persistent storage that stays connected to it. If pod-01 restarts, it comes back as pod-01 with the same storage attached, not as a random new pod.

Deployments are for stateless applications.

Any Pod can replace another Pod. StatefulSets are for stateful apps.

Each Pod has its own identity and storage.

6. Jobs and CronJobs

Deployments and Statefulsets are designed to run forever.

But what if you only need something to run only once and then exit? For example, database migrations or batch processing tasks?

In such cases, we use Jobs.

Kubernetes runs the pod, waits for it to complete successfully, and then marks it as completed. Similarly, CronJobs are used to run Jobs on a schedule, such as running the job every night at midnight or every hour.

Networking Objects

Networking objects allow applications in the cluster to communicate.

They also let users access these applications. It controls how traffic flows in and out of your cluster.

Let’s dive in!

1. Service

We already saw pods are ephemeral (temporary).

They get created, crash, and then restart on different nodes with different IP addresses. So you can’t rely on a pod’s IP address to send traffic to it because it gets a new IP every time it’s recreated.

A Service solves this issue by giving a stable network endpoint to a group of pods.

It doesn’t matter how many pods are behind it or where they’re running. The Service’s IP and DNS name stay the same. Traffic hits the Service and Kubernetes routes it to one of the healthy pods.

There are three main types of services:

  • ClusterIP: Makes the Service reachable only inside the cluster.

  • NodePort: Exposes it on a port on every node, making it reachable from outside.

  • LoadBalancer: Provision an external load balancer through your cloud provider and receive a public IP.

2. Ingress

A LoadBalancer service gives one external IP per service.

Now imagine you have 100s of services:

Getting a LoadBalancer external IP to expose each of your services would cost you a lot. Ingress solves this issue by letting you route external HTTP and HTTPS traffic to many services through a “single” entry point. It provides routing rules to direct external traffic to the correct Service based on the URL or domain name.

For example,

  • Requests to /api go to the API service.

  • Requests to /dashboard go to the frontend service.

All through one external IP.

3. Gateway API

The Gateway API is the newer and more advanced replacement for Ingress.

Ingress was designed only for simple HTTP traffic routing, matching a URL path and sending it to a service. This was great for simple setups.

But it hit limits when you need these features:

  • Traffic splitting between app versions

  • Header-based routing

  • Redirects

  • More control over traffic flow in your cluster

Gateway API was built to manage everything smoothly.

It offers a cleaner and more flexible design. This is the current direction of the Kubernetes ecosystem.

Configuration Objects

Configuration Objects in Kubernetes are responsible for keeping your app config and sensitive data separate from your application containers.

Let’s keep going!

1. ConfigMaps

ConfigMaps store non-sensitive data.

This includes environment variables, config files, and app settings. Your pods read this information at runtime.

Store configuration in ConfigMaps rather than in your container image. It automatically injects into pods when they start.

This allows you to change the configuration without rebuilding your image. You can update your ConfigMap at any time, and your pods will always pick up the latest values.

2. Secrets

Kubernetes Secrets work like ConfigMaps.

Yet they hold sensitive data such as passwords, API keys, and TLS certificates. Kubernetes keeps them separate from your application containers. This setup gives you better control over access.

But Kubernetes secrets are NOT as secure as their name implies.

By default, they’re stored as base64 encoded strings in etcd.

This is encoding, not encryption. Anyone with etcd access or the right cluster permissions can decode these strings and read the secrets. So if you need real security, use tools such as HashiCorp Vault, AWS Secrets Manager, and External Secrets Operator.

They also rely on built-in Kubernetes Secrets.

How Kubernetes Manages Resources

Each application needs CPU, memory, and other resources to run properly.

If you don’t manage resources properly, one app uses too many resources, affecting other apps running in the cluster…

Kubernetes addresses resource consumption by using resource requests and limits, scheduling options, placement rules, and autoscaling5. This method allows Kubernetes to run many applications efficiently on the same infrastructure.

It ensures each app receives the resources it needs.

Resource Requests and Limits

Every pod you run on the Kubernetes cluster requires CPU & Memory.

But the real question is how much CPU and memory are required, and how to tell Kubernetes about it? You do this through two Deployment settings for each container in the Deployment file.

They’re called resource requests and limits:

  • Resource Requests: It’s the minimum amount of CPU or memory a container needs to run. The Kubernetes scheduler checks the pod’s requests. It considers only nodes with sufficient resources to run the container.

  • Resource Limit: It’s the maximum amount of CPU or memory a container is allowed to use. This stops the container from using extra resources. It also ensures other applications on the same node get the resources they need.

It is crucial to understand the Kubernetes Scheduler does NOT consider the actual CPU and memory usage when placing pods.

Instead, it only looks at the resource requests defined in the pod specification.

So it’s essential to set proper requests and limits for the pods to run smoothly.

Affinity, Taints, and Tolerations

Sometimes you want applications to run on specific nodes or prevent some applications from running on certain nodes.

Kubernetes offers three key tools:

  • Node affinity

  • Pod affinity & anti-affinity

  • Taints & tolerations

Let’s see how each of these works:

  • Node affinity: This allows you to tell Kubernetes a pod should run on a specific node based on labels. For example, you label certain nodes as high-memory or GPU-enabled and tell specific pods to only run on those nodes.

  • Pod Affinity: This allows you to tell Kubernetes a pod should be scheduled on a node where certain other pods are already running. This is useful when two services communicate frequently, and you want them on the same node to reduce latency.

  • Pod Anti-Affinity: This is the exact opposite of Pod Affinity. This allows you to tell Kubernetes certain pods should not be scheduled on a node where some other pods are running. This is helpful for applications with many replicas. If you spread the replicas across several nodes, one node’s failure won’t take down the application. The other nodes will keep it running.

  • Taints and Tolerations: This allows nodes to select pods rather than pods choosing nodes. A node gets a taint, which is just a marker that says “pods are not allowed to run on that node unless they have the toleration to run on the node.” So only pods with matching toleration are allowed to run on the tainted node. And Pods without matching toleration are scheduled on another node.

These features give Kubernetes more control over where workloads are placed in the cluster.

Autoscaling

At the start of the newsletter, we discussed how difficult it is to manage microservices manually, especially when traffic changes suddenly.

You can’t constantly add or remove servers manually every time traffic spikes or drops.

This is where Kubernetes Autoscaling fits in…

Here are the autoscalers you must know about in Kubernetes:

  • Horizontal Pod Autoscaler (HPA): This scales the number of pod replicas up/down based on metrics such as CPU usage or memory usage. If your pods are constantly running at 80% CPU, HPA adds more pods because your pods can’t handle extra traffic on their own. When traffic and CPU usage drop, pods scale down.

  • Vertical Pod Autoscaler (VPA): This tool solves the same problem in a different way. It adjusts the CPU and memory requests for containers, NOT the number of pods.

  • Cluster Autoscaler: This works at the cluster level rather than pod level. The cluster autoscaler increases the number of nodes automatically whenever there aren’t enough nodes with available resources to schedule the pods. When nodes are underutilized, and their pods can be moved elsewhere, it removes the extra nodes to save cost.

  • KEDA (Kubernetes Event Driven Autoscaler): The HPA scales based on CPU or memory usage. But many real-world applications need to scale based on external events rather than resource usage. For example, messages in a queue, rows in a database, and requests at an HTTP endpoint.

    This is where KEDA is used.

    KEDA works by monitoring external event sources and automatically scaling the number of pods based on those events. This allows Kubernetes to scale applications even when CPU and memory usage are low while workload demand is high.

    Kubernetes uses various autoscaling mechanisms. They help automatically adjust applications and infrastructure. This adjusts to workload demand.

You now have a cluster that runs workloads, routes traffic, and automatically manages resources.

But none of that matters if any user can modify resources, applications can access sensitive data, and services can communicate with everything in the cluster.

To prevent this, Kubernetes uses a multi-layer security model.

Let’s take a deeper look at how this security model works…

Security Model

Kubernetes uses a security model with several layers.

It controls who can access the cluster, what actions they can take, how workloads are isolated, and how sensitive data is stored…

Here’s how those layers work:

Authentication: Who are you?

The first step in the security of the Kubernetes cluster is authentication.

The Kubernetes cluster verifies the identity of the user or service requesting access to the cluster. The authentication can be achieved using certificates, tokens, or identity providers.

After the user/service identity is verified, the next step in the security of the cluster is authorization.

Authorization and RBAC: What can you do?

After authenticating the user, Kubernetes verifies the actions the user is permitted to perform.

This is achieved through Role-Based Access Control (RBAC).

Role-Based Access Control allows you to create roles with different permissions. For example, these roles can let users create pods, view services, or update deployments.

The roles can then be bound to users or services:

  • A team has permission to deploy applications.

  • Another team has permission to manage networking.

  • Only administrators have permission to update the cluster settings.

Role-Based Access Control enables users & services to perform actions for which they have permission.

Namespaces: Isolation inside the cluster

Namespaces are used to achieve logical partitioning within a Kubernetes cluster.

Kubernetes lets you use one cluster for different teams or apps using namespaces.

i.e., you don’t need to create separate clusters for each environment.

For instance:

  • development namespace

  • staging namespace

  • production namespace

Resources within a namespace are not visible to other namespaces unless configured to be so.

This allows you to share the same cluster without conflicts.

Network Policies: Who can talk to whom?

By default, many Kubernetes networking setups allow pods to communicate with each other.

Network policies allow you to control communication between your pods and services…

Using network policies, you can configure:

  • Only frontend pods can communicate with backend pods

  • Database pods can only be accessed if backend services start the communication

  • Some services cannot be communicated with from outside the cluster

This provides another level of security, this time on the network level.

Secrets: Managing sensitive data

Kubernetes Secrets store sensitive information such as passwords, API keys, and certificates.

They are key to security. Kubernetes manages access with RBAC, namespaces, and service accounts. i.e., applications can ONLY access their allowed secrets, not those of other apps/teams.

In large clusters, managing access to Secrets is vital for overall security.

Admission Controllers: Enforcing policies

Once the API server authenticates & authorizes a request, it passes through a series of admission controllers.

Only after that can anything be written to etcd. These controllers inspect the request, modify it, or reject it entirely based on policy.

An admission controller can:

  • Prevent containers from running as root

  • Require resource limits

  • Enforce security policies

  • Restrict which container images can be used

This helps enforce organizational policies and security standards across the cluster.

Until now, we have been talking about running applications in Kubernetes. But most real applications need to store data. Databases, uploads, logs, and user data cannot disappear when a container restarts.

So Kubernetes needs a way to store data outside containers. This is handled via persistent storage…

Persistent Storage

Containers in Kubernetes are ephemeral…they can be created & destroyed at any time.

If data were stored inside the container itself, that data would be lost whenever the container is replaced. This method works well for stateless apps, such as web servers. But it struggles with databases, message queues, and apps that need to store data.

To solve this problem, Kubernetes “separates” compute from storage…

Kubernetes provides persistent storage independent of Pods and containers.

i.e., data is NOT tied to specific containers.

Persistent Volumes, Persistent Volume Claims, & Storage Class

Kubernetes provides storage management through Persistent Volumes and Persistent Volume Claims.

Persistent Volume

It’s a storage resource in the cluster.

This storage resource comes from different devices. These include cloud disks such as AWS EBS and Google Persistent Disk. You can also use network storage or local storage devices.

This is the actual storage resource.

Persistent Volume Claim

It’s a request for storage resources by user or application.

The user or application requests storage resources through a Persistent Volume Claim. This way, they don’t access the resources directly.

Kubernetes then maps the Persistent Volume Claim to the Persistent Volume.

Storage Class

It’s used to define different storage types in a cluster.

A Storage Class allows the cluster to automatically provision storage when a Persistent Volume Claim is created. This replaces the need for a Persistent Volume. The process of automatically creating storage using a Storage Class is known as dynamic provisioning. It defines the storage type, such as SSD, a regular disk, or network storage. Then, the cluster automatically sets up the storage based on the type.

We have now looked at how Kubernetes works, its architecture, components, networking, security, and storage.

We have a fairly complete picture of how Kubernetes operates as a system…

But understanding how Kubernetes works is only part of the story. The next important question is why Kubernetes became so popular and what problems it actually solves well.

So before we finish, let’s step back and look at what Kubernetes gets right…

What Kubernetes Gets Right

Kubernetes is more than just a container orchestration tool.

It manages distributed systems reliably and automatically. To understand its architecture, look at the key parts: control plane, worker nodes, scheduling, storage, networking, and controllers.

Each design choice addresses real infrastructure issues you once had to manage manually.

There are a few key things Kubernetes gets very right in its architecture:

1. Everything is Declarative

One of the most fundamental concepts in Kubernetes is the declarative model.

You don’t need to start, restart, or scale apps by hand. Just declare the system state you want. Kubernetes then works to match the actual system to your declared state.

You don’t tell Kubernetes how to run something step by step; instead, you tell it what the system should look like.

This model allows Kubernetes to:

  • Automatically recreate failed containers

  • Maintain the number of replicas

  • Perform rolling updates

  • Roll back failed deployments

  • Automatically scale applications

Instead of manually operating the infrastructure, the system becomes self-managing.

2. Self-Healing by Default

Kubernetes always checks the desired state against the actual state.

So it can fix problems automatically when something goes wrong.

Kubernetes can:

  • Restart containers if they crash

  • Replace unhealthy Pods

  • Move workloads if a node fails

  • Reschedule Pods on healthy nodes

  • Maintain the desired number of replicas

This self-healing happens through controller manager & reconciliation loop.

They keep an eye on the cluster and fix any gaps between the desired & actual state.

3. Built for Scaling

Kubernetes is designed to run applications across many machines, NOT just a single server.

The architecture is designed to scale in several ways:

  • Pod scaling using Horizontal Pod Autoscaler

  • Node scaling using Cluster Autoscaler

  • Rolling updates without downtime

  • Load Balancing Using Services

  • Distributed scheduling across nodes

So Kubernetes can handle both small applications and large distributed systems.

4. Runs Anywhere

Another key advantage of Kubernetes is portability.

Kubernetes provides a consistent API and environment regardless of where it runs:

  • Public cloud (AWS, GCP, Azure)

  • Private data centers

  • Hybrid cloud environments

  • Local development machines

Applications can be deployed similarly in various environments.

This reduces vendor lock-in and makes infrastructure more flexible.

Kubernetes gets a lot right, including self-healing, declarative configuration, portability, scalability, and so on.

But no system gets everything right, and Kubernetes is no exception. The same architectural decisions that make it powerful introduce extra costs and failure modes.

Let’s keep going!

Architecture Trade-offs

Here’s what the architecture gets wrong:

Etcd is a Single Point of Failure

Etcd stores the entire cluster state…This makes etcd one of the most critical components in Kubernetes architecture.

If etcd is unavailable/corrupted:

  • Cluster state will be lost

  • Kubernetes would not know what Pods should run

  • Deployments and Services information will be lost

  • The cluster needs to be restored from backup

Running etcd as a three or five-node cluster protects against individual node failures.

It doesn’t protect against data corruption, accidental deletion, or a bad upgrade. Losing etcd data doesn’t just take down your cluster; it erases the cluster’s entire memory. Managed services handle etcd backups automatically.

If you’re running Kubernetes yourself, this isn’t optional.

Operational Overhead

Running Kubernetes is NOT just about running applications… You also have to manage the cluster itself.

Operating Kubernetes usually involves:

  • Cluster upgrades

  • Node upgrades

  • Networking configuration

  • Storage configuration

  • RBAC and security policies

  • Monitoring and logging

  • Backup and disaster recovery

  • Autoscaling configuration

  • Certificate management

Kubernetes often needs platform engineering6 or DevOps support to keep it running.

(This is necessary even before deploying applications.)

If you have a smaller team, this operational overhead can be significant…

Debugging Becomes Harder

Kubernetes is a distributed system, so debugging issues is trickier than on a single server.

A simple issue requires checking:

  • Pod logs

  • Pod events

  • Node status

  • Scheduler decisions

  • Networking issues

  • DNS resolution

  • And so on!

Troubleshooting can be tricky because problems can arise at many levels.

This complexity is higher than in simpler deployment environments.

Kubernetes Is Not Always the Right Tool

Kubernetes is very efficient, but it is not always the best solution for every system.

Kubernetes makes the most sense when:

  • You need auto-scaling

  • You have many services

  • You need high availability

  • You run distributed systems

  • You need infrastructure portability

  • You have a team to manage the platform

Kubernetes is overkill when:

  • You have a small app

  • You have a small team

  • You don’t need auto-scaling

  • You just need to run a few services

  • You don’t need complex deployments

In these cases, simpler options such as managed container services/serverless platforms can be easier to use.

Closing Thoughts

Kubernetes is NOT just a tool for running containers.

It’s a distributed control system built around a single idea: reconciliation loop. You declare what you want. Kubernetes continuously works to make it true.

Every component you learned about exists to serve the loop:

  • API server is the single entry point for everything happening in the cluster

  • Etcd holds the cluster’s entire state and is the source of truth the reconciliation loop works from

  • Scheduler decides where workloads run based on resources, rules, and availability

  • Controller manager watches for drift between the desired and actual states and acts on it

  • Kubelet on each node does the actual work of starting and keeping containers running

  • Kubernetes objects: deployments, services, statefulsets, and configmaps are the vocabulary you use to express what you want the system to look like

  • Resource management, security, and storage are key layers. They ensure that real workloads run safely, reliably, and predictably.

The reconciliation loop runs beneath everything.

It keeps comparing, adjusting, and self-healing…It never stops.

Yet Kubernetes is not simple; its architecture introduces complexity & operational overhead. Many of the features making Kubernetes powerful also make it harder to operate and debug.

Kubernetes is well-suited to systems that require scalability, high availability, and automation. But it will be overkill for smaller apps/teams.

Ultimately, Kubernetes goes beyond just running containers.

It builds a system to manage other systems. It automates deployment, scaling, recovery, networking, and storage for distributed apps…
