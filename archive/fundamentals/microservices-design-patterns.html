1. API Gateway

An application programming interface (API) gateway is a single entry point for your services.

A client must “never” call services directly.

The gateway gives them a single address and forwards each request to the correct service. Plus, it centralizes the cross-cutting concerns: authenticates requests, enforces rate limits, terminates Transport Layer Security (TLS), caches responses, and translates protocols.

i.e., your services stay focused on business logic instead of repeating cross-cutting logic across the codebase.

Analogy

A hotel front desk routes guest requests.

You never walk into the kitchen or the laundry room yourself. Instead, you ask the desk, and they route your request to the right department.

i.e., one point of contact hides a dozen moving parts.

Tradeoff

A gateway simplifies clients1, centralizes security and observability, and lets you reshape services behind a stable interface.

But it adds a network hop, and could become a single point of failure if you run only one instance. Plus, it can become a development bottleneck when every team must change it, and it risks becoming a mini-monolith if you add business logic inside.

So run it behind a load balancer for high availability and keep it thin.

Why it matters

Use an API gateway when many services sit behind one public API, mobile and web apps need a single endpoint, or you want to handle authentication and rate limits in one place.

It can also help you move clients from a monolith to microservices without breaking the existing API…

Some popular implementations are Kong, NGINX, Envoy, AWS API Gateway, and Apigee.

TIP: Pair it with the Backends for Frontends2 pattern (more on this in concept 15) when different clients, such as web and mobile apps, need different APIs.

2. Database per Service

Each service has a private database that NO other service directly touches.

A service keeps its own data and exposes data only through its API.

Other services ask for what they need instead of directly reaching into the tables. This keeps services loosely coupled: you can change a schema, switch between databases, or add an index, and nothing breaks…

i.e., database becomes an implementation detail hidden behind the service boundary.

Analogy

A shop with its own stockroom that only its staff enter.

Customers ask at the counter, and the staff fetches what’s needed. Nobody wanders into the back.

Because one team controls the stockroom, it stays organized, and changes surprise nobody.

Tradeoff

Private databases give each team independence, isolate failures, and let each service pick the right storage for its job.

But queries that span services get harder, you lose cross-table joins & foreign keys, and keeping data consistent across services needs patterns such as Saga, API Composition, and Transactional Outbox3.

A shared database looks easier on day one but silently couples every service over time.

Why it matters

Every microservices system has independent deploys, or services with very different data shapes & access patterns.

This pattern makes microservices independent. So treat a “shared database” as a red flag.

Popular data stores are PostgreSQL, MySQL, MongoDB, and DynamoDB.

3. Circuit Breaker

A circuit breaker temporarily stops calls to a failing service, giving it time to recover and protecting callers from cascading failures.

The breaker wraps a remote call & watch failures:

  • When calls succeed, it stays closed and traffic flows.

  • When failures cross a threshold, it opens, and every call fails fast without touching the failed service.

  • After a cool-down, it goes half-open and lets one trial call through.

  • If this succeeds, it closes again; if not, it opens & waits longer.

This turns a slow, resource-draining timeout into an instant, cheap rejection.

Analogy

An electrical fuse trips when too much current flows.

Instead of letting a fault burn down the house, the fuse cuts the circuit. Once the problem is fixed, you reset it and power returns.

The breaker does the same for a failing dependency, cutting it off before it drags everything down.

Tradeoff

They add error-handling paths and need careful tuning of thresholds & timeouts.

Plus, they can trip on a “brief” blip and reject good traffic, and require monitoring so you notice an open circuit.

Why it matters

Calls to a remote/third-party dependency must degrade gracefully, or one slow service must NOT take down the whole request path.

Resilience4j (Java), Polly (.NET), and Envoy proxy implement breakers, and a service mesh (more on this in concept 20) such as Istio can apply them without code changes.

4. Event-Driven Messaging

Services communicate by publishing & consuming events through a “message broker” instead of calling each other directly & wait.

A direct call couples the caller to the callee in time: the caller blocks for a reply, and a failure on either side breaks the request.

Event-driven messaging breaks this link. A service publishes an event to a broker and moves on, and any number of consumers can subscribe & react on their own schedule.

This publish-and-subscribe style also lets you add new consumers later without touching the producer.

Analogy

A phone call versus a group channel:

A phone call needs both people free at the same instant. A message posted to a group channel waits until each reader is ready, and everyone interested sees it.

New people can join the group channel later and still get the updates.

Tradeoff

It trades simple request-reply for eventual consistency.

Plus, debugging gets harder across an event chain, and there’s a need to handle duplicate & out-of-order delivery.

Why it matters

Workflows where steps can happen asynchronously, fanning one event out to many services, decoupling producers from consumers, or smoothing traffic spikes with a buffer.

Apache Kafka, RabbitMQ, AWS SNS and SQS, and Google Pub/Sub are popular broker implementations.

TIP: Pair it with the Idempotent Consumer pattern4 (more on this in concept 17), because at-least-once delivery means duplicates will happen.

5. Service Discovery

Service discovery lets services find each other by name through a registry, which updates itself as instances start, stop & move.

In microservices architecture, instances come and go, and their addresses change constantly. i.e., hard-coding a location breaks the moment a service moves.

Each instance registers its address with a service registry when it starts and de-registers when it stops. Callers query the registry by name to get a current, healthy address.

Here are 2 ways to implement service discovery:

  • client-side, where the caller queries the registry and load-balances itself,

  • server-side, where a load balancer or the platform does it.

Analogy

A contacts app instead of numbers scribbled in pen…

When a friend changes their number, the app updates and you can still reach them. The registry keeps every service’s current contact details, so callers always reach them.

Tradeoff

  • It adds infrastructure,

  • Makes the registry a critical dependency,

  • Needs health checks to stay accurate, and a stale cached lookup can still send traffic to a dead instance.

Why it matters

Fixed addresses are NOT practical for auto-scaling fleets, containerized deployments with shifting IPs, blue-green and rolling deploys5.

Consul, etcd, and Netflix’s Eureka are classic registries, while Kubernetes builds discovery in through DNS and Services.

Most service meshes6 include it, so you often get discovery for free at scale.

6. Retry with Backoff

Retry with backoff reattempts a failed call a few times with a growing delay, turning brief glitches into successes without hammering a struggling service.

Networks blip, and a call that fails once often succeeds on the next try.

A naive retry loop can stampede a service that’s already down. Backoff fixes this by waiting longer between each attempt, usually “doubling” the delay, and jitter adds randomness so many clients don’t retry in lockstep.

A retry limit and a timeout cap the total effort so a stuck call gives up instead of hanging forever.

Analogy

Redialing a busy phone line.

You wait a moment and try again, not forty times in a row, and you give up after a few rings rather than holding the line all day.

Each wait is a little longer so you’re not jamming the line.

Tradeoff

Retrying a non-idempotent call can double-charge or double-write; aggressive retries can amplify an outage into a retry storm, and extra attempts raise tail latency7 for the request.

TIP: Only retry idempotent operations, always add jitter, and pair retries with a circuit breaker.

Why it matters

Calls to flaky networks/third-party APIs, transient database errors, or any remote operation that’s safe to repeat.

Resilience4j & Polly provide retry with exponential backoff and jitter out of the box.

Timeout, retry with backoff, and circuit breaker together are standard resilience mechanisms for remote calls.

7. Decompose by Business Capability

Split a system into services along the natural lines of the business, using business capabilities and domain-driven design8 to draw the boundaries.

The HARD part of microservices is deciding where one service ends and the next begins…

Here are two methods to guide you:

  • Decomposing by business capability splits the system by what the organization does, such as orders, payments, or shipping. Then gives each capability a service.

  • Decomposing by subdomain uses domain-driven design (DDD) to model the business and carve it into subdomains.

Each becomes a bounded context: a boundary inside which every term carries one precise meaning.

Boundaries drawn this way follow the business, which shifts far more slowly than the code.

Analogy

Think of a company with different departments:

Sales handles selling, Shipping handles deliveries, and Payments handles billing. Each department owns its own work. Even the same word can mean different things. For example, a "customer" means an order and delivery address to Shipping, but payment details & invoices to Payments.

A bounded context keeps each meaning separate, so teams don't interfere with each other.

Tradeoff

Choosing the right service boundaries needs a good understanding of the business.

If you split services the wrong way, they end up constantly calling each other. While changing those boundaries later becomes difficult because each service already owns its own data and responsibilities.

Why it matters

Use this pattern when you’re building a new microservices system, breaking a monolith into smaller services, or giving each team ownership of a specific business area.

8. Saga

A saga manages a transaction that spans services as a sequence of local steps, each with a compensating action that undoes it if a later step fails.

A single database gives you ACID transactions, but once a business action spans services, this guarantee disappears…

A saga restores correctness without distributed locks. Each service performs its local step and emits an event/message that triggers the next. If a step fails, the saga runs compensating steps in reverse to undo the earlier work.

Sagas come in two styles:

  • Choreography: services react to each other’s events,

  • Orchestration: one central coordinator drives the steps.

Analogy

Booking a trip one piece at a time.

You reserve a flight, then a hotel, then a car. If the car falls through, you cancel the hotel and the flight. Each cancellation is a compensating step that walks the booking back to where it started.

Tradeoff

Sagas are eventually consistent, so different services won’t all be updated at the same time.

If something fails, you need extra code to undo earlier steps, such as issuing a refund after an order has already shipped. As more services join the workflow, it also becomes harder to understand and debug how events flow through the system…

Why it matters

Use a saga when one business action, such as placing an order or booking a trip, needs to update many services and stay correct even if one step fails.

Orchestration engines such as Temporal, Camunda & AWS Step Functions help manage the workflow for you.

Choose an orchestrated saga when the process has many steps, and you want one place to control and monitor the entire workflow.

9. Health Check API

A health check API is an endpoint each service exposes so the platform can tell if the instance is alive & ready to serve traffic.

The orchestrator needs a signal it can poll.

A health endpoint (/health) returns OK when the service and its critical dependencies are working.

Platforms such as Kubernetes use three kinds of health checks:

  • A liveness check asks, "Is the application still running?" If it fails, the platform restarts the application.

  • A readiness check asks, "Can the application handle requests right now?" If it fails, the platform stops sending traffic to that instance but leaves it running.

  • A startup probe gives slow-starting applications extra time to finish starting before the other health checks begin.

Analogy

A heartbeat monitor on a hospital patient…

A steady beep means all is well. While a flatline tells the staff to act immediately.

The check turns an invisible internal state into a signal anyone watching can act on.

Tradeoff

A simple health check that only returns “200 OK” says the service is healthy even when its database connection is broken.

But a check that tests every dependency can become slow, add extra load & make many services fail at once when one dependency has a problem.

TIP: Check the dependencies that truly determine whether the service can handle traffic, and keep the check fast & focused.

Why it matters

Services running under Kubernetes, ECS, or a load balancer, zero-downtime deploys, and automatic recovery from crashes.

10. Distributed Tracing

Distributed tracing follows a single request across every service it touches, tagging it with a trace ID and recording the time spent in each hop.

When one request fans out across ten services, a “plain log” cannot tell you which hop was slow…

Tracing assigns each request a trace ID at the edge and propagates it through every call. Each service records a span, a timed segment of its own work, and reports it to a tracing backend. The backend then puts them together into one waterfall timeline, so you see the full path and the bottleneck.

Because tracing every request costs real money, systems sample a fraction at scale.

Analogy

A package tracking number:

One number follows your parcel through every depot and truck, with a timestamp at each stop. You can see exactly where it is and where it got delayed, even though dozens of facilities handled it.

Tradeoff

  • Every service must be configured to generate and pass tracing information to the next service.

  • Tracing also adds a small amount of work to every request.

  • In large systems, only some requests are traced to reduce overhead, so you won't capture every request.

Why it matters

Debugging latency in microservices, finding bottlenecks, understanding dependencies, or root-causing errors across services.

OpenTelemetry is the vendor-neutral standard for instrumentation, with Jaeger, Zipkin, AWS X-Ray, and Datadog as common backends.

11. Service Instance per Container

Package each service instance as a container and hand it to a deployment platform that schedules, scales, and restarts instances automatically.

A service needs a home that behaves “identically” everywhere & is trivial to copy.

A container bundles the service with its runtime and dependencies, so it runs the same on your laptop & in production. You run one service instance per container, then give those containers to a platform such as Kubernetes.

The platform places containers on machines, restarts ones that crash, scales replicas up and down with load, and reschedules them when a node dies… all with nobody touching a server by hand.

Analogy

Standardized shipping containers…

Because every container is the same shape, any crane, ship, or truck can move it without knowing what’s inside.

A software container works the same way: platform copies, moves, and replaces it identically, whatever language lives within.

Tradeoff

  • Kubernetes and other orchestrators add another system you need to learn & manage.

  • They also make networking and storage more complex.

  • If the cluster is configured incorrectly, it can introduce new production problems of its own.

Why it matters

Almost any modern microservice, autoscaling workloads, and zero-downtime rolling deploys.

Docker is the standard container format; Kubernetes, AWS ECS and Fargate, and Nomad are platforms.

12. API Composition

API Composition answers a query that spans services by calling each owning service and then joining the results in a composer.

With a database per service, NO single data store holds the entire picture.

Sometimes a client needs data from several services. For example, showing an order page requires information from the Order, Customer, and Inventory services.

An API composer, often part of an API gateway or a Backend for Frontends (BFF), calls each service, combines the results, and returns a single response.

It usually calls the services in parallel, so the response is faster (as FAST as the slowest service).

Analogy

A restaurant meal prepared by different chefs:

One chef cooks the main dish, another prepares the salad, and a third makes the dessert. The waiter collects everything and serves it as one complete meal.

Tradeoff

The composer must wait for its slowest service.

If one service is unavailable, the entire response may fail. Combining large amounts of data in application memory is also much less efficient than joining it inside a database.

For complex or high-traffic queries, use a CQRS9 read model that stores the data in a form designed for fast reads.

Why it matters

Use API composition when a page needs data from a few services, such as an order page that combines customer, payment, and shipping information.

API composition is often built into an API gateway/Backend for Frontends (more on this in concept 15). GraphQL10 is another common way to combine data from many services into a single response.

If these requests become too slow/occur frequently, consider using a CQRS read model instead. It stores the combined data in advance, so clients can read it with a single query.

13. Transactional Outbox

Transactional Outbox pattern saves the database change and the message to be sent in the same database transaction. After the transaction succeeds, the service publishes the message, ensuring data changes and messages remain consistent.

A problem occurs when a service updates its database & then sends a message…

If the database update succeeds but the message never gets sent, other services never learn about the change…

The Transactional Outbox pattern solves this problem:

Instead of sending the message immediately, the service saves both the business data and the message in an outbox table as part of the same database transaction. This guarantees that either both are saved or neither is.

A separate background process later reads messages from the outbox table and sends them to the message broker. After a message is successfully published, it’s marked as sent.

This process can either periodically check the outbox table or automatically detect new rows using Change Data Capture11 (CDC).

Analogy

Mailing a letter...

When you update your records, you immediately place the outgoing letter into your company’s outbox. Both happen together, so you can never have an updated record without the letter waiting to be sent.

Later, the mail carrier picks up the outbox and delivers the letter.

Tradeoff

  • It requires an extra outbox table and a background process to send messages.

  • Messages are NOT sent immediately, so there is a tiny delay.

  • As a message could be sent more than once, receiving services must be able to safely ignore duplicates.

Why it matters

Use the Transactional Outbox pattern when a service needs to update its database and notify other services about the change. For example, publishing an “Order Placed” event or keeping a search index or cache up to date.

Tools such as Debezium can automatically detect new outbox records using Change Data Capture (CDC) and publish them to Kafka without repeatedly checking the database.

TIP: As the same message could be delivered more than once, pair this pattern with the Idempotent Consumer pattern so duplicate messages do not cause duplicate work.

14. Remote Procedure Invocation

Remote Procedure Invocation (RPI) is when one service directly calls another service and waits for a “synchronous” response.

The two most popular ways to do this are REST & gRPC:

  • REST (Representational State Transfer) sends requests over HTTP, usually using JSON. It is simple, widely supported, and easy to test & debug.

  • gRPC (Remote Procedure Call) sends data in a compact binary format called Protocol Buffers over HTTP/2. This makes it faster and more efficient than REST. Before the services communicate, they agree on the structure of the requests and responses, which helps catch errors early. gRPC also supports streaming, allowing both sides to send multiple messages over a single connection.

TIP: Use REST for public & browser-facing APIs, and gRPC for fast communication between internal services.

Analogy

A phone call instead of sending a letter.

You call someone, ask a question, and wait for the answer before hanging up.

  • REST is like speaking a common language that almost anyone understands.

  • gRPC is like two professionals using a fast, shared technical language because they have already agreed on exactly how to communicate.

Tradeoff

A service that makes a synchronous call must wait for the other service to respond.

If the other service is slow or unavailable, the caller also becomes slow or fails. When one request depends on several services, delays can quickly add up.

gRPC is faster and catches more communication errors than REST, but it is harder to debug and is NOT suitable for web browsers.

TIP: To make synchronous calls reliable, use timeouts, retries with increasing delays between attempts (backoff), and a circuit breaker to stop sending requests to a service that is already failing.

Why it matters

Use Remote Procedure Invocation (RPI) when a service needs an immediate response, such as checking inventory before placing an order or fetching the latest account balance.

REST is a good choice for public APIs because it is simple & widely supported. gRPC is better for fast communication between internal services.

If the work does NOT need an immediate response, use event-driven messaging instead.

15. Backends for Frontends

A Backend for Frontends (BFF) is a backend built for a specific type of client, such as a web app/mobile app.

Different clients often need different data:

A mobile app needs a small response to load quickly, while a web application needs much more information.

Instead of making one API satisfy both, each client gets its own Backend for Frontends (BFF). The BFF collects data from the required services, returns only what the client needs, and handles client-specific logic.

As each BFF is independent, the web and mobile teams can change their backends without affecting each other.

Analogy

Separate menus for dine-in and takeout.

The dine-in menu is full and descriptive; takeout menu is stripped down for quick ordering. Same kitchen, two presentations, each tuned to how that customer actually orders.

Tradeoff

  • BFF pattern adds another service that must be built, deployed, and maintained for each client.

  • Similar logic could end up being copied across many BFFs, and if shared functionality is not kept in one place, the different BFFs can become inconsistent over time.

Why it matters

Use a BFF when different clients, such as web and mobile apps, need different data or have different performance requirements.

A BFF helps avoid sending too much or too little data by returning only what each client needs.

BFFs are often used together with an API gateway. Another option is GraphQL, which lets clients choose exactly which fields they want in the response.

16. Bulkhead

The bulkhead pattern isolates resources into separate pools so failure in one part of the system don’t exhaust the resources the rest depends on.

Each dependency gets its own pool of threads/connections instead of sharing one large pool.

If one dependency becomes slow or stops responding, only its pool fills up. Requests to other healthy services continue normally, preventing one failure from affecting the entire application.

Analogy

A ship divided into watertight compartments…

A breach floods one compartment, but the bulkheads stop the water from spreading, and the ship stays afloat. The failure is sealed off instead of allowing it to sink everything.

Tradeoff

  • Using separate pools means resources cannot be shared as efficiently as one large pool.

  • Each pool also needs to be configured and monitored.

  • If a pool is too small, it can become a bottleneck even when the rest of the system is healthy.

Why it matters

Use the Bulkhead pattern when a service depends on several other services, and you don’t want one slow or failing dependency to affect the rest.

Libraries such as Resilience4j provide bulkhead implementations. The Bulkhead pattern is often used together with the Circuit Breaker pattern to make systems more resilient.

17. Idempotent Consumer

An idempotent consumer can process the same message more than once without changing the result.

Message brokers could deliver the same message more than once.

For example, after a network problem or a retry. If a service processes every message without checking, it will perform the same action twice, such as charging a customer twice.

The Idempotent Consumer pattern prevents this by remembering which message IDs were processed. When the same message arrives again, the service recognizes the ID and ignores the duplicate.

So store processed message IDs in a database table, enforce them with a unique constraint, or carry them as an idempotency key in the message.

Analogy

A bouncer with a guest list who checks off each name.

When someone already inside tries to walk in again, the bouncer sees the check mark and waves them off. Nobody gets counted, charged, or admitted twice.

Tradeoff

  • It requires storing processed message IDs & checking them for every message.

  • The storage also needs to be cleaned up over time.

  • If processing a message involves several steps, you must carefully ensure repeating the same message cannot cause any side effects.

Why it matters

Use the Idempotent Consumer pattern whenever messages might be delivered more than once. It is crucial for payment processing, order processing, and services using retries or the transactional outbox pattern.

Kafka and most brokers deliver at least once by design, so this isn’t optional at scale. With at-least-once delivery, duplicates will arrive eventually, so plan for them…

18. Strangler Fig

The strangler fig pattern migrates a legacy system gradually, routing one slice of functionality at a time to new services until the old system can be retired.

Replacing an entire system all at once is risky & often fails…

The Strangler Fig pattern replaces the system one feature at a time instead:

A router/facade sits in front of the old system. At first, every request goes to the old application. As new features get built, the router sends those requests to the new services while the remaining requests still go to the old system.

Over time, more and more traffic moves to the new services until the old system is no longer used and can be removed.

This pattern is named after the strangler fig tree, which gradually grows around another tree until it can stand on its own.

Analogy

Renovating a house while you live in it.

You redo one room at a time and keep sleeping in the others. You’d never demolish the entire house and pitch a tent in the yard. The home stays livable throughout, just as the system stays running throughout.

Tradeoff

  • During the migration, you must build, run, and maintain both the old & new systems.

  • The router that routes requests also needs to be managed carefully.

  • Keeping data consistent between the two systems can be difficult, and if the migration slows down or loses priority, you end up maintaining both systems.

Why it matters

Use the Strangler Fig pattern when you need to replace a monolith or legacy system without taking it offline.

It’s also a good choice for large migrations where replacing everything at once is too risky.

The pattern usually uses a router or API gateway to decide whether each request goes to the old system or the new one. During the migration, an Anti-Corruption Layer (more on this in concept 21) can translate between the old and new systems so the new services don’t have to understand the legacy design.

19. CQRS

Command Query Responsibility Segregation (CQRS) splits the write model from the read model so each can be designed & scaled for its own job.

CQRS separates writing data from reading data:

The write side handles changes, such as creating an order or updating an account, and ensures business rules are followed.

The read side is optimized for showing data quickly. It often stores data in a format designed for fast queries and may use a separate database.

Changes made on the write side are copied to the read side in the background. This lets reads and writes scale independently and allows you to create different read models for different screens, such as dashboards or reports.

Analogy

A restaurant with one counter for orders and another for pickup…

The order counter is built to take orders accurately; the pickup counter is built for fast handoff. They handle the same meals but are optimized for opposite jobs, so neither slows the other down.

Tradeoff

  • CQRS makes the system more complex because you must build and maintain separate read and write models.

  • The read model is updated after the write model, so it briefly shows outdated data.

  • You also need a way to keep the two models synchronized.

TIP: For simple applications that only perform basic create, read, update, and delete (CRUD) operations, CQRS usually adds unnecessary complexity.

Why it matters

Use CQRS when your application has many more read requests than write requests, or when different users or screens need different views of the same data.

It is also useful when the logic for updating data is much more complex than the logic for reading it.

CQRS is often used together with Event Sourcing (more on this in concept 22). If your application only needs simple create, read, update, and delete (CRUD) operations, a single data model is usually the better choice.

20. Sidecar/Service Mesh

A sidecar is a proxy container that runs alongside each service & handles tasks such as networking, security, and monitoring.

A service mesh connects ALL of these sidecars, allowing you to manage communication between services from one central place.

Every service needs the same features, such as retries, timeouts, encryption (mTLS), load balancing, and tracing. Adding this code to every service is repetitive and hard to keep consistent.

  • A sidecar lets the service focus only on its business logic.

  • While a service mesh makes it easy to apply the same networking and security rules across every service.

Analogy

A building with a shared security & maintenance team:

Every office focuses on its own work. The building’s security team handles access control, the maintenance team keeps everything running, and the reception desk directs visitors. Each office doesn’t need to build those services itself.

A service mesh does the same for your services by handling networking, security, and communication in one shared system.

Tradeoff

  • A service mesh adds another complex system that your team must operate.

  • The sidecar proxy also adds a tiny delay and uses extra CPU & memory for every service call.

  • As traffic passes through another layer, it can also become harder to trace & debug.

TIP: Use a service mesh only if you have enough services that managing retries, security, and traffic rules inside each service becomes very difficult.

Why it matters

Use a service mesh when you have many services and want the same security, traffic rules, and monitoring across all of them without adding extra code to each service.

Some popular service meshes are Istio, Linkerd & Consul Connect.

They are a good choice for large microservices systems, but are “unnecessary” for small apps with only a few services.

21. Anti-Corruption Layer

An anti-corruption layer is a translation boundary to keep a legacy/third-party system’s model from leaking into & corrupting your clean one.

When a new service needs to communicate with a legacy system or a third-party API, it can easily start using the system’s data format and business rules.

Over time, this makes the new service harder to maintain…

An Anti-Corruption Layer (ACL) sits between the two systems and translates data and requests from one format to the other. This allows the new service to use its own clean design without depending on the old system’s design.

Analogy

An embassy translator.

They convert the other country’s words and customs into yours, so your team works in its own language and never has to think in someone else’s.

The foreign rules stop at the embassy door.

Tradeoff

  • Anti-Corruption Layer adds extra code that must be built and maintained.

  • Every request also goes through an extra translation step, which adds a small amount of overhead.

  • If the layer grows too big, it can become difficult to maintain on its own.

Why it matters

Use an Anti-Corruption Layer when connecting a new service to a legacy system during a migration, working with a complicated third-party API, or keeping a new part of your app independent from an older one.

The pattern comes from Domain-Driven Design (DDD).

It’s often used with the Strangler Fig pattern to keep the new system clean while the old and new systems run together during the migration.

22. Event Sourcing

Event Sourcing stores every change as a separate event instead of overwriting the current data.

Most apps store only the latest version of the data, so earlier changes get lost.

Event Sourcing works differently… Instead of updating/replacing data, it saves every change as a separate event in the order it happened.

When the current state is needed, the application rebuilds it by replaying those events. As every change gets stored, you can see the complete history, restore the state from any point in time, and create new reports or read models from past events.

To avoid replaying every event from the beginning, the application periodically saves a snapshot of the current state. It can then replay only the events that happened after the latest snapshot.

Analogy

A bank ledger instead of just a balance.

Your balance is the sum of every deposit and withdrawal. The ledger shows exactly how you got there and lets anyone recompute the balance at any past date.

The history is the source of truth; the balance is just a number you compute from it.

Tradeoff

  • Event sourcing is more difficult to build than storing only the latest state.

  • Because events cannot be changed/deleted, mistakes must be fixed by adding new correction events.

  • Rebuilding the current state requires replaying events or reading from precomputed views.

  • As the application changes over time, keeping old events compatible can be challenging.

  • Without snapshots, replaying a long event history becomes slower, and storage requirements continue to grow.

Why it matters

Use event sourcing when you need a complete history of every change, such as in banking, accounting, or audit systems, or when understanding how data changed is just as important as its current value.

Event Sourcing is often used together with CQRS.

Some common ways to implement are EventStoreDB, Axon, and Kafka.

Because it adds significant complexity, it is best reserved for apps that truly need a complete audit trail and historical data.

Bringing It Home

None of these patterns live alone…

They are building blocks, and they combine into systems that survive massive traffic, failures, and real growth.

The strongest engineers learn the tradeoffs and reach for the right one when a specific problem shows up. They also resist a pattern adopted for its own sake. You do not need a service mesh, event sourcing, or sagas on day one. A well-bounded set of services with solid monitoring carries you a long way.

So start simple. And add a pattern only when the problem demands it:

  • A cascading failure usually means missing circuit breakers & bulkheads.

  • An order that charges twice points to a consumer without idempotency.

  • Slowness with no obvious source is the exact job of distributed tracing.

  • A terrifying rewrite is a sign to strangle the monolith one route at a time.

  • A system you cannot split cleanly means the boundaries are wrong, not the tooling.

These patterns give you the vocabulary to name what went wrong and the toolkit to set it right.
