Data Sync

When apps store data on the device, they also need to keep that data in sync with the server.

This section explains how apps synchronize data, handle conflicts when changes occur across multiple places, and maintain app consistency even when the network connection is slow or unreliable.

20. Conflict Resolution Strategies

When mobile apps allow users to edit data offline, a new challenge appears: conflicts.

Why Conflicts Happen

Imagine two users editing the same document:

  1. User A edits the document while offline.

  2. User B edits the same document at the same time.

  3. Later, both devices reconnect and try to sync.

Now, the server has two different versions of the same data. The system must decide how to merge or choose between them.

To solve this problem, apps use various conflict-resolution strategies.

Common Conflict Resolution Strategies

There are several ways apps handle these conflicts:

a. Last-Write-Wins (LWW)

This is the simplest approach.

Each update includes a “timestamp”. When two versions conflict, the system keeps the latest update and discards the older one.

For example:

  • User A updates at 10:01 p.m.

  • User B updates at 10:02 p.m.

Since User B’s change happened later, the system keeps that version.

This approach is simple to implement and works well for simple data, but earlier changes may be lost.

b. Versioning

Versioning tracks different versions of the same data.

Each update increases the version number or records which device made the change. When a conflict occurs, the system can compare the versions and either automatically merge them or ask the user to choose.

This approach is more flexible, but requires extra logic to manage versions.

c. CRDTs (Conflict-Free Replicated Data Types)

CRDTs are special data structures designed to merge changes automatically without conflicts.

They use mathematical rules that ensure that different versions of the same data can always be merged into a single, consistent result, even when updates occur in different places.

This approach is often used in real-time collaboration tools.

Why It Matters

Without a proper conflict strategy, one user’s changes might silently overwrite another user’s work.

For example, someone may edit a document, sync it later, and suddenly see that their changes have disappeared.

This can break user trust and cause data loss.

Real-World Example

Many well-known applications use these strategies:

  • Figma and Notion use “CRDT” based systems to support real-time collaborative editing.

  • Dropbox often uses a “last-write-wins” approach and may generate a “conflicted copy” when it cannot merge two versions.

Trade-offs

Each approach has its advantages and limitations:

  • Last-Write-Wins: Very simple to implement, but can cause data loss because earlier changes may be overwritten.

  • CRDTs: Automatically merge changes without conflicts, but are complex to implement and not suitable for every type of data.

  • Versioning: Keeps track of multiple changes clearly, but may require users to manually resolve conflicts.

Once conflicts can be resolved safely, syncing becomes more efficient when only changes are transferred.

21. Delta Sync

When mobile apps sync data with a server, downloading the entire dataset every time can be slow and waste a lot of data. This is especially true for apps that store large amounts of information.

To make syncing more efficient, many apps use a technique called delta sync.

Delta sync means the app downloads only the data that has changed since the last sync, rather than downloading everything again.

How It Works

When the app syncs for the first time, it downloads the full dataset from the server.

After that, the server gives the app a sync token or timestamp that represents the latest state of the data.

On the next sync:

  1. App sends the last sync token to the server.

  2. The server checks what has changed since that token.

  3. Server sends only new, updated, or deleted records.

This makes syncing much faster and more efficient.

Why It Matters

Imagine a contacts app with 5,000 contacts.

If the app downloaded all contacts every time it synced, it would waste a large amount of bandwidth and battery. With delta sync, the app downloads only the contacts that were added or changed, saving both data and processing time.

This makes background syncing practical even on mobile networks.

Real-World Example

Many well-known platforms use delta syncing:

  • Google Contacts uses a “syncToken” to track changes.

  • Apple CloudKit uses a “serverChangeToken” for the same purpose.

The app stores this token and sends it during the next sync request, so the server knows exactly what updates to return.

Trade-offs

Delta sync improves efficiency but requires extra work on the server.

The server must keep track of which data has changed. This usually means storing timestamps or maintaining a change log.

Deletions must also be tracked. Instead of completely removing a record, the system may temporarily store a “tombstone” record that indicates the item was deleted, so the client knows to remove it as well.

Practical Tip

The sync system should rely on timestamps or sequence numbers generated by the server, not the client.

Client devices may have incorrect clocks, which can cause sync problems. Using a server-controlled timestamp or sequence number ensures that the order of updates is always correct.

Even with efficient syncing methods like delta sync, distributed systems can still struggle to maintain perfect consistency across devices.

22. Eventual Consistency

Mobile apps often run in environments with slow, unstable, or completely unavailable network connections. Because of this, different devices may not always have the exact same data at the same time.

This situation is called eventual consistency.

Eventual consistency means that data may temporarily differ across devices, but all devices will eventually reach the same state once they sync with the server.

How It Works

In mobile apps, users may perform actions while offline or on unstable networks.

For example:

  1. A user updates some data on their phone.

  2. The change gets saved locally on the device.

  3. When the network connection becomes available, the app sends the update to the server.

  4. Server then sends the updated data to other devices.

For a short period, different devices may show slightly different versions of the data, but eventually they all become consistent after syncing.

Why It Matters

Trying to keep data perfectly synchronized at all times would require the app to wait for the server to confirm every action before updating the interface.

This would make the app feel slow and unresponsive.

Instead, mobile apps usually update the UI immediately, while ‌server synchronization happens in the background.

This approach makes the app feel fast and responsive while still keeping the data consistent over time.

Real-World Example

Messaging apps are a common example of eventual consistency.

For example, WhatsApp shows different message states:

  • A single check mark means the message has been sent from the device.

  • A double check mark means the message has been delivered to the recipient.

The message appears in the chat immediately, even before the server fully confirms it. Later, the status updates when the system finishes syncing.

Trade-offs

Eventual consistency improves user experience, but it also introduces some challenges…

Sometimes the server may reject a change or update the data differently. When this happens, the app must update the UI carefully to avoid confusing the user.

To handle this, many apps display clear states such as pending, confirmed, or failed. This helps users understand what is happening with their actions.

To handle temporary failures during syncing, apps often rely on background processes that automatically retry operations, as discussed in the next section.

23. Background Sync & Retry Queues

Mobile apps often perform actions that need to be sent to a server, such as sending a message, liking a post, or submitting a form. But sometimes the network connection may be weak or unavailable, causing these actions to fail.

Instead of losing these actions, apps use a system called a retry queue.

A retry queue stores failed operations locally on the device so they can be retried later when the network connection is available.

Mobile operating systems also provide tools that allow apps to perform tasks in the background efficiently.

For example:

  • WorkManager on Android

  • BGTaskScheduler on iOS

These tools allow apps to run background tasks while managing battery usage and system resources.

How It Works

When a user performs an action that requires a network request, the app tries to send it to the server:

  1. User performs an action (for example, sending a message).

  2. If the request succeeds, the server processes it normally.

  3. If the request fails because of network issues, the app stores the action in a retry queue.

  4. When the device reconnects to the network, a background sync process retries the queued operations.

  5. Once the server confirms the request, the action is removed from the queue.

This ensures that user actions are not lost even when the network is unreliable.

Why It Matters

Users expect their actions to work, even if the network connection is unstable.

For example, if a user taps “send message” or “like”, the app should not simply ignore the action because the network was unavailable.

By storing the action and retrying it later, the app respects the user’s intent and completes the action when conditions improve.

Real-World Example

Many apps use retry queues and background syncing:

  • Email apps like Gmail and Outlook allow users to send emails while offline. The email is queued and automatically sent when the network returns.

  • E-commerce apps may queue actions such as adding items to a cart or saving user activity and sync them later.

Trade-offs

Background processing on mobile devices has limitations.

Operating systems control how long apps can run in the background to protect battery life. These background windows are usually short and unpredictable. Because of this, apps should not rely only on background syncing. Synchronization should also happen when the user opens the app again.

These mechanisms also allow the app’s interface to respond instantly, while the actual synchronization happens quietly in the background.

24. Optimistic UI Updates

In many apps, users expect actions to happen instantly. For example, when you tap “like”, send a message, or add a comment, you expect to see the result immediately.

If the app waited for the server to respond before updating the screen, it could take a few hundred milliseconds. Even that slight delay can make the app feel slow.

To solve this, apps use a technique called optimistic UI updates.

Optimistic UI means the app assumes the request will succeed and updates the interface immediately, even before the server confirms it.

The server request still happens in the background. If everything succeeds, nothing changes. If it fails, the app corrects the UI and shows an error.

How It Works

The process usually follows these steps:

  1. User performs an action (e.g., tapping a like).

  2. App updates the UI immediately and stores the change locally.

  3. App sends the request to the server.

  4. If the server confirms the request, the change remains unchanged.

  5. If the server rejects the request, the app reverts the change and shows a small error message.

This makes the app feel fast while still keeping the data accurate.

Why It Matters

Users expect apps to respond instantly to their actions.

If the app shows a loading spinner every time the user taps a button, the experience feels slow and frustrating.

Optimistic UI removes this delay, making the app feel smooth and responsive, similar to native device interactions.

Real-World Example

Many popular apps rely heavily on optimistic UI:

  • Twitter shows the like animation immediately when you tap the heart.

  • Instagram displays your comment instantly in the thread.

  • Slack shows a message in the chat immediately after you send it.

In the background, the app syncs with the server and updates the data if needed.

Trade-offs

An optimistic UI improves the user experience, but it also adds complexity.

If the server rejects the request, the app must roll back the UI change smoothly without confusing the user. Because of this, optimistic UI is usually avoided for actions that cannot be easily reversed, such as permanent deletion, payments, and financial transactions.

Security & Auth

Mobile apps often store and handle sensitive user data, such as personal information, login details, and payment data. Because of this, security is an important part of mobile system design.

In this section, you’ll learn how apps protect user data using methods like authentication, secure storage, encryption, and privacy protections.

25. Authentication (JWT / OAuth)

Authentication is the process of verifying a user’s identity before granting them access to an app.

In simple terms, it answers the question: “Is this user really who they claim to be?”

Most modern mobile apps use OAuth 2.0 for login, especially when users sign in with services like Google, Apple, or Facebook. After login, the server issues the app a special token, a JWT (JSON Web Token), that proves the user is authenticated.

The app sends this token with future requests so that the server knows which user is making the request.

Usually, there are two types of tokens:

  • Access token: Used to access APIs and usually expires quickly (about 15–60 minutes).

  • Refresh token: Used to get a new access token when the old one expires.

This system keeps users logged in while also improving security.

How It Works

The authentication process usually looks like this:

  1. User taps “Sign in with Google” or another login option.

  2. App redirects the user to the authentication provider.

  3. After the user logs in successfully, the server sends an authorization code.

  4. App exchanges this code for access and refresh tokens.

  5. App uses the access token when making requests to the server.

Many mobile apps also use PKCE (Proof Key for Code Exchange).

This adds an extra security step to ensure that the same app that started the login process is the one finishing it.

Why It Matters

Mobile apps cannot safely store secret keys inside the app because the app’s code can be inspected.

PKCE solves this problem by adding a verification step that proves the request came from the same app that started the login process.

This makes the authentication flow much more secure.

Real-World Example

Most modern apps use this authentication approach.

For example:

  • Sign in with Apple

  • Sign in with Google

  • Many social media, banking, and productivity apps

All of these typically rely on OAuth 2.0 with PKCE and JWT tokens.

Trade-offs

Authentication systems must balance security and user experience.

Short-lived access tokens improve security because stolen tokens stop working quickly. But this means the app must automatically request new tokens using the refresh token.

Some systems also rotate refresh tokens (generate a new one each time). This improves security but requires careful handling to avoid errors if the network fails during the refresh process.

Once users are authenticated, the next challenge is storing tokens and credentials securely on the device.

26. Secure Token Storage (Keychain / Keystore)

After a user logs in, the app receives tokens (such as access tokens and refresh tokens). These tokens prove that the user is authenticated, so they must be stored securely on the device.

If an attacker gets access to these tokens, they could potentially access the user’s account. Because of this, tokens should never be stored in plain text or normal storage systems.

Mobile operating systems provide secure storage systems specifically designed for sensitive data:

  • Keychain on iOS

  • Keystore on Android

These systems store data in encrypted, secure storage that is protected by the device’s security hardware.

How It Works

When a user logs in and the app receives tokens from the server:

  1. App stores the tokens in Keychain (iOS) or Keystore (Android).

  2. These storage systems encrypt the tokens and protect them using the device’s security features.

  3. When the app needs to call an API, it securely retrieves the token.

  4. The token is then used to authenticate the request.

Some apps also require additional protections, such as device unlock or biometric authentication, before the token can be accessed.

Why It Matters

Normal storage systems like NSUserDefaults (iOS) or SharedPreferences (Android) are not designed for sensitive data.

If someone gains access to the device or extracts the app’s files, they may be able to read those values.

A stolen refresh token could allow someone to access the user’s account without needing their password. Secure storage prevents this by encrypting the data and limiting access to it.

Real-World Example

Apps that handle sensitive information rely heavily on secure storage.

For example:

  • Banking apps store login tokens in the Keychain or Keystore.

  • Some enterprise apps restrict token access so that it only works when the device is unlocked and only on that specific device.

This prevents tokens from being copied or restored on other devices.

Trade-offs

Secure storage systems are very safe, but they can sometimes fail in certain situations:

  • User changes biometric settings.

  • The device is restored or upgraded.

  • Security settings change.

If this happens, the app may no longer be able to access the stored token. When that occurs, the app should ask the user to log in again, rather than crashing or silently failing.

But protecting stored credentials is only one part of security. Communication between the app and the server must also be protected.

27. Certificate Pinning

When a mobile app communicates with a server, it usually uses HTTPS to keep the data encrypted and secure. Normally, the device trusts certificates that are verified by the operating system.

In some situations, attackers can try to intercept the connection using a technique called a man-in-the-middle (MITM) attack. i.e., someone secretly places themselves between the app and the server to read or modify the data being sent.

Certificate pinning helps prevent this.

With certificate pinning, the app stores a trusted version of the server’s certificate or public key inside the app itself. When the app connects to the server, it checks whether the server’s certificate matches the one it expects. If it doesn’t match, the connection is immediately rejected.

This ensures the app is only communicating with the real server.

How It Works

The process typically works like this:

  1. App connects to the server using HTTPS.

  2. Server sends its security certificate.

  3. App compares the certificate (or public key) with the one stored inside the app.

  4. If the values match, the connection continues normally.

  5. If they do not match, the connection is blocked.

Most apps pin the public key instead of the full certificate because certificates can change over time, while the key may stay the same.

Why It Matters

Sometimes attackers install fake certificates on a device to intercept secure connections.

This can happen in situations such as public Wi-Fi networks, compromised devices, or corporate proxies that inspect network traffic.

Without certificate pinning, these attackers may still be able to read encrypted traffic. Certificate pinning prevents this by allowing the app to trust only the expected certificate or key.

Real-World Example

Many apps that handle sensitive information use certificate pinning, such as banking apps, payment apps, and VPN applications.

These apps must ensure that all communication happens with the correct server and cannot be intercepted.

Trade-offs

Certificate pinning improves security, but it must be implemented carefully.

If the pinned certificate or key changes and the app has not been updated, the app may fail to connect to the server. To avoid this problem, many apps pin multiple keys (a primary and a backup). This allows servers to rotate certificates without breaking the app.

Modern mobile devices also provide additional ways to verify a user’s identity, such as biometric authentication, which adds another layer of security…

28. Biometric Authentication

Many modern smartphones allow users to unlock their devices using biometric authentication, such as Face ID, fingerprint, or facial recognition.

Mobile apps can also use these features to securely verify a user’s identity. These systems are connected to the phone’s secure hardware (often called the Secure Enclave or secure chip), which safely stores and processes biometric information.

Importantly, the app never receives the user’s fingerprint or face data. Instead, the device simply tells the app whether authentication succeeded or failed.

How It Works

The process usually looks like this:

  1. App asks the device to verify the user using biometrics.

  2. User scans their fingerprint or face.

  3. The device checks the biometric data using its secure hardware.

  4. If the verification succeeds, the device allows the app to access a secure key or continue the operation.

  5. If verification fails, the app denies access or asks the user to try again.

The biometric data itself never leaves the device.

Why It Matters

Biometric authentication makes security both stronger and easier for users.

Typing a password repeatedly can be inconvenient, so users may choose weak passwords or avoid security features. Biometrics removes that friction by allowing fast and secure authentication with just a fingerprint or face scan.

This encourages users to keep their devices locked and protected.

Real-World Example

Many apps use biometrics to confirm sensitive actions:

  • Banking apps may require Face ID or fingerprint verification before showing full account numbers.

  • Some apps require biometric verification before completing payments or transfers.

  • Password managers often unlock stored credentials using biometrics.

Trade-offs

Although biometrics are secure, they still have some limitations.

If someone has physical access to the device, they might be able to register their own fingerprint or face. Because of this, apps should always provide a password or PIN fallback.

For very sensitive operations, some apps also require step-up authentication, meaning the user must enter their full password instead of relying only on biometrics.

Beyond verifying the user’s identity, apps must also protect themselves from tampering and reverse engineering, which is why application security techniques are also important.

29. Code Obfuscation & Tamper Detection

Mobile apps can sometimes be reverse-engineered, which means someone can analyze the app’s code to understand how it works.

Attackers may try to extract things like API endpoints, business logic, or secret keys from the app. To make this harder, use techniques such as code obfuscation and tamper detection.

Code obfuscation changes the structure of the app’s code, so it becomes difficult to read and understand. For example, meaningful variable and function names may be replaced with random characters. This makes reverse engineering much harder.

Tamper detection checks whether the app has been modified or is running in an unsafe environment. If the app detects suspicious behavior, it can block certain features or prevent access to the server.

How It Works

These protections are applied at both build time and runtime to increase the difficulty of reverse engineering:

  • During the build process, app’s code is obfuscated (e.g., renaming classes and methods, removing metadata, optimizing bytecode). This makes static analysis and decompilation harder, but does not provide strong security on its own.

  • At runtime, the app may perform integrity and environment checks such as:

    • detect if a debugger or instrumentation tool is attached

    • detect rooted or jailbroken devices

    • detect signs of runtime hooking or code injection

  • If the app detects tampering, it may block the action or restrict access to sensitive features.

  • Some apps also use platform-supported integrity signals (e.g., Play Integrity API on Android, App Attest or DeviceCheck on iOS) to verify that the app is running in a trusted environment. These signals are usually validated on the server.

These measures make it harder for attackers to modify the app or analyze its internal logic.

Why It Matters

If attackers reverse engineer an app, they might discover:

  • Hidden API keys

  • Backend endpoints

  • Business rules

  • Potential vulnerabilities

Even partial protection can make reverse engineering much more difficult and discourage casual attackers.

Yet it’s important to remember that these protections are not a guarantee of security. Determined attackers may still bypass them.

That’s why server-side validation is always the most important security layer.

Real-World Example

Many apps use these techniques:

  • Game apps use “tamper detection” to prevent cheating tools or modified game versions.

  • Financial apps often check if a device is rooted or jailbroken before allowing sensitive actions such as transactions.

These checks help reduce the risk of attacks.

Trade-offs

Obfuscation improves security but can make debugging harder.

For example, crash reports from production apps may contain obfuscated function names, which makes them difficult to understand.

To solve this, keep a mapping file that allows them to translate obfuscated names back into the original code during debugging.

Apps must also ensure that external links and navigation flows inside the app remain secure, which leads to the next topic.

30. Secure Deep Linking

Deep linking allows users to open a specific screen inside an app directly from a link.

For example, tapping a link in an email might open a product page or a password reset screen inside the app. Some apps use custom URL schemes like:

myapp://profile/123

But this approach can be unsafe…Another app on the device could register the same URL scheme and intercept those links.

To solve this problem, modern mobile apps use Universal Links (iOS) and App Links (Android).

These links use standard HTTPS domains rather than custom schemes. The domain is verified with the app using special configuration files on the server. This ensures that only your app can open those links.

How It Works

The process typically works like this:

  1. App registers a domain such as https://example.com

  2. Server hosts a verification file that proves the app owns the domain

  3. When the user taps a link from that domain, the operating system verifies it

  4. If the domain is verified, the link opens directly inside the app

  5. If the app is not installed, the link opens in the browser instead

This prevents other apps from hijacking the link!

Why It Matters

If apps rely on custom URL schemes like myapp://, another malicious app could register the same scheme.

This means the malicious app might receive the link and capture sensitive information, such as authentication tokens.

Universal Links and App Links prevent this by verifying domain ownership through the server, making it much harder for attackers to intercept the link.

Real-World Example

Secure deep links are commonly used in authentication flows.

For example:

  • OAuth login flows redirect the user back to the app after they log in.

  • Email magic links allow users to log in without a password.

  • Many apps open specific pages (such as products or articles) directly from links shared on the web.

Using verified links ensures the correct app always opens.

Trade-offs

Universal Links and App Links require additional setup.

The app’s server must host a verification file, such as:

  • apple-app-site-association (iOS)

  • assetlinks.json (Android)

The device may also need network access during installation to verify the domain.

Despite this extra setup, verified deep links are much safer than custom URL schemes.

31. User Data Privacy (GDPR, CCPA, App Tracking Transparency)

Mobile apps often collect and process user data, such as email addresses, location information, device data, or usage behavior. Because of this, protecting user privacy has become an important part of modern app development.

Many countries and platforms now have privacy regulations that apps must follow.

Here are some of the most important ones:

  • GDPR (General Data Protection Regulation), in Europe

  • CCPA (California Consumer Privacy Act), in the United States

  • ATT (App Tracking Transparency), introduced by Apple

These rules require apps to be transparent about how they collect and use user data.

What These Regulations Require

Privacy regulations give users more control over their personal data.

For example, apps may need to:

  • Ask for clear user consent before collecting certain data.

  • Allow users to download their data.

  • Allow users to delete their data.

  • Allow users to opt out of tracking or data sharing.

Apple’s App Tracking Transparency (ATT) also requires apps to ask permission before tracking users across different apps or websites.

If the user declines, the app must respect that choice.

Why It Matters

Ignoring privacy regulations can have serious consequences:

  • GDPR fines can reach up to 4% of a company’s global revenue.

  • Apple may remove apps from the App Store if they violate privacy rules.

Beyond legal risks, privacy also affects user trust. Apps that respect user privacy are more likely to keep users long-term.

Real-World Example

When Apple introduced App Tracking Transparency in iOS 14.5, most users opted out, with around 75% of iOS users choosing not to allow tracking. This significantly affected the mobile advertising industry.

According to Meta’s CFO Dave Wehner, the potential loss of $10 billion in ad sales revenue accounted for nearly 8% of Facebook’s yearly revenue, and the market reacted, with the stock price dipping 26%.

This shows how strongly privacy policies can influence the design of mobile systems.

Trade-offs

Privacy-friendly systems often collect less data, which can make analytics and personalization more difficult:

  • Advertising targeting may become less precise.

  • Analytics may rely on aggregated or anonymous data instead of individual tracking.

Because of this, many companies now build privacy-focused analytics systems, such as aggregated metrics or anonymized event tracking.

Practical Tip

Many mobile apps include third-party SDKs (for analytics, ads, or payments). Some of these SDKs may collect user data automatically.

It’s important to audit every third-party SDK and understand what data it collects.

Platforms like Apple’s Privacy Nutrition Labels and Android’s Data Safety section help you clearly document how their apps handle user data.

Beyond security and networking, mobile apps must also run efficiently within the limited resources of mobile devices, such as battery, memory, and processing power.

Takeaway

In mobile apps, privacy is not just a rule to follow; it changes how you design the system.

You can’t always collect or track everything, so your app should work even with limited data. This is why many apps now use on-device processing, simple analytics, and carefully choose third-party SDKs to avoid unnecessary data collection.

Beyond security and networking, mobile apps must also run efficiently within the limited resources of mobile devices, such as battery, memory, and processing power.

Performance & Background Processing

Mobile devices have limited resources such as CPU power, memory, and battery. So apps must be carefully designed to run efficiently.

In this section, you’ll learn how mobile apps handle background tasks, improve startup time, and keep the app smooth and responsive without using too much battery or system resources.

32. App Lifecycle & State Management

Every mobile app goes through different states while it is running on a device. This is called the app lifecycle.

For example, an app can be:

  • Active (Foreground): The user is currently using the app.

  • Background: User switches to another app, but the app is still running.

  • Terminated: App is closed or stopped by the system.

Both iOS and Android manage these states automatically.

When the app transitions between these states, the system sends signals to allow the app to save or restore its data.

How It Works

When an app changes state, the system gives the app a chance to save its data.

For example:

  1. The user is using the app.

  2. User switches to another app.

  3. The app then moves to the background.

  4. App saves important data such as user input or the current screen.

  5. If the user returns later, the app restores the saved state.

Modern frameworks also provide tools to help manage this state, such as

  • ViewModels on Android

  • SceneDelegate or lifecycle callbacks on iOS

These help store UI data safely across lifecycle changes.

Why It Matters

Mobile operating systems can close apps, especially when the device runs low on memory. And this can happen without warning.

If the app does not save its state, the user may return to find that their progress or input is lost, leading to a poor experience.

Proper lifecycle handling ensures the app can restore the user’s progress smoothly.

Real-World Example

Imagine a user filling out a long form in an app.

If the user switches to another app or receives a phone call, the app may move to the background. A well-designed app will automatically save the form as a draft.

If the operating system later closes the app because of low memory, the form will be restored when the user opens the app again.

Trade-offs

Saving the app’s state too frequently can result in extra disk operations and increased processing power.

To avoid this, apps often save only the data that has changed, instead of always saving everything. Some temporary UI states can also remain in memory while the app is running, while important data should be stored permanently.

These lifecycle rules also affect how apps run background tasks, which leads to the next topic.

33. Background Processing Limits (iOS / Android constraints)

Mobile operating systems carefully control what apps can do in the background. This is mainly done to protect battery life and device performance.

When a user switches away from an app, the operating system usually pauses the app and limits its functionality.

Both iOS and Android have strict rules for background processing:

  • iOS usually allows only about 30 seconds of background execution after the app moves to the background.

  • Android uses systems like Doze Mode and App Standby to limit network access and CPU usage when the device is idle.

Because of these restrictions, apps cannot run an unlimited number of tasks in the background.

How It Works

Instead of running background tasks freely, apps must use special system APIs that allow controlled background work:

  • WorkManager on Android

  • BGTaskScheduler on iOS

These systems allow apps to schedule background tasks. But the operating system decides the best time to run them based on factors such as battery level, device usage, and network availability.

This helps ensure that background work does not drain the device’s battery.

Why It Matters

If an app constantly runs tasks in the background, it can quickly drain the device’s battery.

Users often notice when an app uses too much battery, and they may uninstall it. In some cases, app stores may even reject apps that misuse background processing.

So you must design apps to work within these limits, rather than trying to bypass them.

Real-World Example

A health-tracking app may collect data from sensors throughout the day.

Instead of uploading this data immediately, the app might schedule a background task using “BGProcessingTask” on iOS. The operating system may then run this task overnight while the device is charging, which is more efficient.

This approach saves battery and avoids interrupting the user.

Trade-offs

One challenge with background tasks is that you cannot control exactly when they run.

The operating system determines the timing based on factors such as battery level, network availability, and user behavior. So background tasks should be designed to be flexible and delay-tolerant. Tasks that require immediate action should run while the app is in the foreground.

Efficient background processing is also important for saving battery and improving overall app performance, which leads to the next topic.

34. Battery Optimization (Radio Wake-Up Cost, Batching)

Battery life is one of the most important factors in mobile apps.

If an app uses too much battery, users quickly notice and may uninstall it.

One major reason apps consume battery is network communication. When an app sends or receives data over the internet, the phone’s cellular radio must wake up to establish a connection.

Activating the cellular radio requires additional time and energy. According to Android developer documentation, transitioning from a low-power state to full power takes about 1.5 seconds, and from standby it can take over 2 seconds. After sending data, the radio typically remains active for around 20–30 seconds (known as tail time) before powering down.

As a result, sending many small network requests can significantly increase battery usage. To reduce this overhead, apps often batch network operations or combine multiple events into fewer requests.

How It Works

To reduce battery usage, apps batch network operations together.

Instead of sending data every time something happens, the app collects multiple events and sends them together in a single request.

For example:

  1. App collects several minor events.

  2. These events are stored temporarily.

  3. After a short period, the app sends them in one combined request.

  4. Radio wakes up once instead of multiple times.

This reduces the number of times the cellular radio must wake up, saving battery.

Why It Matters

Users often judge an app by how much battery it consumes.

Even a well-designed app with outstanding features may be removed if it drains the battery too quickly. Optimizing network behavior helps apps remain efficient and user-friendly.

Real-World Example

Music streaming apps often collect usage analytics.

Instead of sending every event separately, apps like Spotify batch multiple analytics events and send them together every few minutes.

This significantly reduces the number of network requests and improves battery efficiency.

Trade-offs

Batching improves battery life but may delay when data is sent:

  • Analytics events can be sent later without any problem.

  • Messages or notifications must be sent immediately.

So apps usually separate network operations into two types:

  • Real-time requests (send immediately)

  • Non-urgent requests (batch and send later)

This balance helps maintain both performance and battery efficiency.

Network requests themselves must also be designed efficiently to avoid wasting system resources.

35. Network Optimization & Rate Limiting

Mobile apps often send many requests to a server to load data, update information, or perform actions.

If these requests are not managed properly, the app may send too many requests at once, wasting network bandwidth, draining the battery, and overloading the server.

To prevent this, apps use techniques such as rate limiting, request deduplication, and connection reuse to make network communication more efficient.

How It Works

There are several ways apps optimize network requests:

a. Rate Limiting

Rate limiting controls how frequently the app can send requests to the server. This prevents the app from sending too many requests in a short time.

For example, if a user taps a button repeatedly, the app may limit how often the request is sent.

b. Request Deduplication

Sometimes the same request may be triggered many times, such as when a user taps a button repeatedly or navigates quickly between screens.

Request deduplication ensures that duplicate requests are ignored or merged, preventing the same request from being sent many times.

c. Connection Reuse

Opening a new network connection for every request is inefficient. Instead, apps reuse existing connections.

Protocols such as HTTP/2 allow multiple requests to be sent over a single connection simultaneously. This improves performance and reduces network overhead.

d. Debouncing Requests

In some cases, apps delay sending a request slightly to avoid unnecessary calls.

For example, in a search-as-you-type feature:

  • When the user types a letter, the app waits briefly.

  • If the user keeps typing, the previous request is canceled.

  • Request is sent only after the user pauses typing.

This prevents many unnecessary API calls.

Why It Matters

Without proper optimization, simple actions can trigger many unnecessary requests.

For example, quickly navigating between screens could send multiple identical API requests within milliseconds. This wastes bandwidth, increases server load, and drains battery without improving the user experience.

Efficient request handling helps apps remain fast, stable, and resource-efficient.

Real-World Example

Search bars in many apps use “debouncing”.

Instead of sending a request for every keystroke, the app waits about 300 milliseconds after the last keypress before sending the request. If the user continues typing, previous requests are canceled.

This speeds up the search feature and reduces unnecessary server calls.

Practical Tip

Whenever possible, mobile apps should use HTTP/2 for API communication.

HTTP/2 allows multiple requests to share the same connection. This improves performance and avoids many limitations of older protocols.

Another performance factor users notice immediately is how quickly an app starts, as discussed in the next section.

36. Startup Time Optimization (Cold vs Warm Launch)

When a user opens a mobile app, the time it takes for the app to appear and become usable is called startup time. A fast startup is very important because it forms the user’s first impression of the app.

There are 2 main types of app launches:

  • Cold launch: App starts from scratch because it is not running in memory.

  • Warm launch: The app was already running in the background and quickly returned to the screen.

A warm launch is usually very fast, while a cold launch takes longer because the system must load the entire app.

How It Works

During a cold launch, several steps happen before the user sees the first screen:

  1. Operating system loads the app from storage.

  2. App’s libraries and resources get initialized.

  3. Main app code starts running.

  4. The app prepares the first screen.

  5. First UI frame is displayed to the user.

During a warm launch, most of this work has already been done. The system simply brings the app back from memory, which makes the launch much faster.

Aim for:

  • Cold launch: Under ~400 milliseconds to show the first screen.

  • Warm launch: Under ~100 milliseconds.

Why It Matters

Startup time has a big impact on user experience.

According to Google’s mobile page speed research, 53% of mobile users abandon a page that takes longer than three seconds to load. Even delays of one or two seconds can make an app feel slow.

Because the launch screen is the first interaction users have with the app, it strongly affects how they perceive performance.

Real-World Example

Large apps often improve startup time by delaying work that is not immediately needed.

For example, instead of loading analytics tools or crash-reporting services during startup, the app may initialize them after the first screen appears. This allows users to see content faster while the remaining setup continues in the background.

Trade-offs

Reducing startup time often means delaying certain tasks until after the app is visible.

Yet if too many tasks are delayed, they may later compete with UI work, affecting performance. Because of this, you must carefully decide which tasks are essential for the startup and which can be run later.

Once the app is running, the next challenge is ensuring smooth UI rendering and responsive interactions.

37. Rendering Performance (UI Thread, Jank, ANR)

Mobile apps need to update the screen many times every second to appear smooth.

This is handled by something called the UI thread (also known as the main thread). The UI thread is responsible for drawing the interface and responding to user actions.

To keep animations and scrolling smooth, the app must render a new frame roughly every 16 milliseconds (for 60 frames per second). On devices with faster displays, such as 120Hz screens, this must happen even faster.

If something blocks the UI thread for too long, the app cannot update the screen in time. This causes frame drops, which users see as lag or stuttering. This problem is commonly called jank.

How It Works

When an app is running:

  1. UI thread draws the interface and handles user interactions.

  2. Heavy tasks such as data processing or file loading should run on background threads.

  3. Once the background task finishes, it sends the result back to the UI thread.

  4. UI thread then updates the screen with the new data.

This keeps the UI thread free to focus only on rendering and user interaction.

Why It Matters

If the UI thread is blocked for too long, the interface becomes unresponsive.

On Android, if the main thread is blocked for around 5 seconds, the system may show an ANR (Application Not Responding) error. This makes the app appear frozen and often leads users to close it.

Even short delays can cause noticeable lag, leading to a poor user experience and negative app reviews.

Real-World Example

Consider a messaging app receiving a new message.

Instead of processing the message on the UI thread, the app:

  • Parses the message data in a background thread.

  • Calculates layout and formatting in the background.

  • Sends the final result to the UI thread.

The UI thread then only needs to display the message, which keeps scrolling and animations smooth.

Trade-offs

Using multiple threads improves performance but also adds complexity.

You must carefully manage how tasks move between the background and UI threads to avoid race conditions. Use Swift Concurrency (iOS) and Kotlin Coroutines (Android) to help manage this more safely.

Golden Rule

The UI thread should do only two things:

  • Respond to user input

  • Draw the interface

All heavy work, such as database queries, image processing, or network operations, should run on background threads.

Poor memory management can also slow down apps or even cause crashes, which is why memory usage must be carefully controlled.

38. Memory Management & Leak Prevention

Mobile devices have limited memory (RAM). When an app uses memory, it should release that memory once the data is no longer needed. If the app keeps holding onto memory unnecessarily, it creates a memory leak.

A memory leak happens when objects stay in memory even though the app is no longer using them. Over time, this causes the app’s memory usage to keep increasing.

If the memory usage becomes too large, the operating system may forcefully close the app to free resources. On iOS, this is called jetsam, where the system kills apps that consume too much memory.

Common causes of memory leaks include:

  • Objects strongly referencing each other (reference cycles).

  • Activities or screens are being held in memory after they are closed.

  • Observers or listeners who were never removed.

  • Large images or bitmaps that are not properly released.

Because of this, you must manage memory carefully and make sure unused objects can be removed from memory.

Why It Matters

If an app has memory leaks, its memory usage keeps growing during a session. Eventually, the operating system closes the app without warning.

From a user’s perspective, it looks like the app randomly restarted or crashed, which creates a poor experience and often leads users to uninstall the app.

Real-World Example

A common issue on Android happens when a background object still holds a reference to a screen (Activity) that the user has already left.

Because that screen is still being referenced, the system cannot remove it from memory. If this happens repeatedly while the user navigates through the app, memory usage keeps increasing.

Practical Tip

Tools are available to detect memory leaks during development.

For example:

  • Memory Graph Debugger in Xcode (iOS)

  • LeakCanary or Android Profiler on Android

These tools help you find objects that are staying in memory longer than they should. Detecting leaks early is important because fixing them before release is much easier than debugging crashes after users start reporting problems.

Finally, another important goal in mobile system design is keeping the app lightweight, which helps improve both installation size and startup performance.

39. App Size Optimisation (Binary Size, On-Demand Resources)

Mobile apps should be as small as possible. A large app takes longer to download, uses more storage on the device, and can discourage users from installing it.

This is especially important in regions where internet data is expensive or devices have limited storage.

Because of this, try to reduce the binary size (the final packaged file users download) of the app and load resources only when they are needed.

Some common techniques include:

a. App Thinning

App thinning means users only download the parts of the app that their device actually needs.

For example, a phone with a small screen does not need large image assets meant for tablets. The app store automatically delivers only the correct assets for that device.

b. On-Demand Resources

Instead of including all images, videos, and assets inside the app download, some resources can be downloaded later when the user actually needs them.

For example, a game might download additional levels only when the player reaches them. This keeps the initial app download much smaller.

c. Removing Unused Code

During development, apps often contain unused code or libraries. Tools in the build process can remove this unused code so that only the necessary parts remain in the final app.

This helps reduce the overall app size.

Why It Matters

Studies show that larger apps lead to fewer installs. In fact, Google’s research found that every 6MB increase in APK size leads to a 1% decrease in install conversion rate.

If an app is too large:

  • Users may cancel the download.

  • Devices with limited storage may reject the installation.

  • Users may uninstall the app to free up space later.

Keeping the app small improves both installation rates and user retention.

Real-World Example

Companies like Facebook and Instagram created lite versions of their apps (Facebook Lite and Instagram Lite).

These versions are designed to be much smaller and work better on slower networks and lower-end devices.

Practical Tip

On Android, you can use Android App Bundles (AAB) instead of a single APK file.

With App Bundles, the Play Store automatically sends only the parts of the app needed for each device, such as the correct language, screen size, and processor architecture.

On average, this can reduce the app size by 20%.

Closing Thoughts

Security decisions affect performance, performance decisions affect architecture, and architecture decisions affect how you handle sync.

These aren’t separate topics; they’re all part of the same system.

The goal isn’t to memorize everything. It’s to understand enough that when a problem shows up, you recognize it and know where to look.

One thing worth remembering:

The best architectures aren’t the most clever ones; they’re the ones where every tradeoff is made intentionally.
