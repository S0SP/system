1. Caching

Imagine the “same” API route gets called a thousand times per second.

And each call hits the database for the result.

i.e., every read will:

  • access disk storage,

  • lock tables during reads,

  • consume connection pool slots.

But all this work just to return data that has NOT changed since the last request…

You can use in-memory caching to solve this problem by storing frequently accessed data in memory.

Your app checks the “cache” first before querying the database. Cache hits return data from memory, while cache misses query the database & then store the result for later.

Advantages

You get extremely fast response times because memory access is 100x faster than disk.

Plus the database handles fewer requests since only cache misses reach it. Also, this lets you scale “read” capacity without adding more database replicas.

Disadvantages

But cache invalidation becomes difficult because it's hard to know exactly when cached data must be removed/refreshed.

Also you need to keep the cache & database in “sync” to avoid stale data. Plus, memory is significantly more expensive than disk storage.

This increases infrastructure costs.

Best practices

So cache only the data that can tolerate some staleness, such as product catalogs & user profiles.

Besides, set an appropriate Time-to-Live (TTL) based on how often the data changes. Also use the cache-aside pattern1 to keep the cache populated only when data is requested.

Caching gives you fast reads for data that doesn’t change often.

But it only helps when the same data gets requested over & over. So what about systems where users read “different” data?

2. Scaling reads

Your query performance looks good,,, but your database is “struggling”.

The problem is NOT slow queries; instead, it’s the volume. Thousands of users hit your API at the same time…

Every query runs fast, but every request still:

  • Uses CPU on the database server

  • Consumes a database connection

  • Waits in line when the server gets overloaded

To overcome slow reads, you can add indexes and tune query execution plans.

This lets you get the most out of your existing servers. Then, when your servers reach their limits, add read replicas…

Your application sends writes to the primary database and routes reads to replicas…While the replicas stay synchronized through replication.

Advantages

You can scale reads simply by adding more replicas instead of upgrading a single database server.

Also, you can reduce latency by placing replicas closer to your users. Plus distributing reads across many servers prevents one database from becoming a bottleneck.

Disadvantages

Yet replication is NOT instant; replicas need time to copy changes from the primary.

Also, read-after-write requests may receive stale data if they hit a replica too soon. Plus, running replicas adds operational complexity because they must be monitored, maintained, and kept healthy.

Best practices

So optimize your existing database before adding more infrastructure.

Also, use read replicas only when eventually consistent reads are acceptable. Besides, route critical read-after-write operations to the primary database to guarantee fresh data.

Read replicas are great for high-read traffic applications where some stale data is acceptable. But how do you manage high-write traffic?

3. Scaling writes

Your database handles every write,,, but eventually:

  • You’ve already optimized inserts & added batching,

  • You cannot keep upgrading to a larger database instance,

  • CPU and IOPS2 (Input/Output Operations Per Second) has reached their limits.

You can solve this through sharding.

i.e., distribute writes across many database nodes…

You choose a partition key, and a hash function routes each record to a specific shard. Think of sharding like splitting a large phone book by region, where every region has its own book.

Yet each shard stores only a “subset” of the entire data…

So it’s important to choose a good partition key:

  • User IDs: many of them, evenly distributed

  • Geographic regions: related data stays together for better local queries

  • Time windows: great for time-series data where older shards become read-only

This lets you scale writes...

You can add shards to increase capacity & reduce latency by placing shards closer to users.

Advantages

You can scale write capacity simply by adding more shards instead of relying on a single database server.

Plus, each shard handles only part of the total traffic, which reduces the load on individual machines. Also, placing shards closer to users can reduce write latency.

Disadvantages

But resharding is difficult because moving data between shards requires downtime and/or complex migrations.

Also, changing your partition key later requires relocating large amounts of data (this is expensive!). Plus, queries spanning many shards require extra coordination to combine the results.

Best practices

So choose partition keys with many distinct values to distribute traffic evenly.

Also monitor for hot partitions and rebalance shards if necessary. Besides, design your schema to minimize queries that must access many shards.

Sharding distributes writes across different machines. But what about distributing them across time?..

4. Message queues

Imagine your API receives a burst of 10,000 requests in one minute.

Each request triggers database writes. And this could make your system performance BAD. Some requests succeed, while others fail/time out!

Then the problems cascade:

  • One slow service blocks the entire request chain

  • Services must scale together even with different workloads

  • Retry logic makes it worse, as clients repeatedly hit the same overloaded endpoint

You can solve this problem using message queues such as Amazon SQS, RabbitMQ, or Kafka.

They buffer messages between services. So when one service slows down, it has less impact on the others.

Here’s how a message queue works:

  1. Producers send messages to the queue

  2. The queue stores messages until they’re ready to be processed

  3. Consumers retrieve messages at their own pace, process them, & then acknowledge completion

So instead of processing requests immediately, your API places them in a message queue.

Background services then process the messages asynchronously…

Advantages

Message queues “absorb traffic spikes” because messages get stored until workers can process them.

Plus, they decouple services, so each one can scale independently. Besides they set the foundation for event-driven architectures where services communicate through events instead of direct API calls.

Disadvantages

But in asynchronous processing, clients do NOT immediately know whether a request has completed successfully.

Also, message queues add latency because work happens later instead of during the request. Plus, they introduce another piece of infrastructure that must be deployed, monitored & maintained.

Best practices

So make consumers idempotent3 because messages could be delivered more than once.

Also use dead letter queues4 to isolate failed messages. Besides, monitor queue depth because growing backlogs are often an early sign of system problems.

Message queues make asynchronous processing possible. But what does asynchronous processing actually look like from a user’s perspective?

5. Asynchronous processing

Imagine users uploading a 10GB file through the API…

Or they request a report which queries millions of database records. The API cannot keep an HTTP request open for 20 minutes while it finishes the work.

Here’s what happens without asynchronous processing:

  • HTTP requests time out after 30 seconds,

  • Users don’t know whether the work succeeded/failed,

  • Retries create duplicate processing.

You can solve this through asynchronous processing.

i.e., accept work immediately & then finish it in the background.

Here’s how it works:

  1. API accepts the request & assigns it a unique job ID

  2. It places the job in a message queue & returns the job ID to the client

  3. Background workers process jobs asynchronously

  4. Workers update the job status (processing, completed, failed)

  5. Clients poll a status endpoint with the job ID and/or receive callbacks when processing finishes

Advantages

Users receive a quick response instead of waiting for long-running work to finish.

Plus, web servers stay available to handle new requests instead of being blocked by SLOW jobs. Also, background workers can scale independently based on queue size.

Disadvantages

But asynchronous processing requires you to store & update the state of every job.

Also, clients must wait until processing finishes before knowing whether the work succeeded. Plus, running background workers and message queues increases infrastructure costs & operational complexity.

Best practices

So return the job ID immediately instead of performing long-running work inside the request handler.

Also use exponential backoff5 together with dead letter queues for failed jobs. Besides, provide status endpoints so clients can track progress while the job is running.

Asynchronous processing works well when users can wait for results. But what about use cases where users expect an update right away?

6. Real-time updates

Imagine your chat app loads new messages every 5 seconds using polling…

It creates a BAD user experience because new messages only appear after next poll.

Here are the problems with polling:

  • Servers get many unnecessary requests,

  • Updates don’t appear until the next polling interval,

  • Your app requests updates even when nothing has changed.

You can solve this through real-time updates.

i.e., push data from the server to the client as soon as something changes.

Think of it like receiving a notification on your phone instead of refreshing the app every few seconds.

If you only need one-way communication, Server-Sent Events (SSE) is a good choice.

SSE lets servers continuously push updates to clients over HTTP. It’s simple, works well through proxies & automatically reconnects if the connection drops.

Yet if you need communication in both directions, use WebSockets.

They maintain a persistent connection so clients & servers can send messages to each other any time.

Advantages

Users receive updates quickly instead of waiting for the next polling interval with real-time updates.

Plus, servers avoid handling thousands of unnecessary polling requests. Also, persistent connections make real-time apps feel much more responsive.

Disadvantages

Yet every active connection consumes server resources.

Also, applications must detect dropped connections & reconnect automatically. Plus, network infrastructure becomes more complex because load balancers require sticky sessions6, and some networks “block” WebSockets.

Best practices

  • Use SSE for one-way updates such as notifications & live dashboards.

  • Use WebSockets when clients and servers both need to exchange messages, such as chat & online gaming.

Besides, design for connection failures by using exponential backoff for reconnects and heartbeats to detect dead connections.

Real-time updates create responsive user experiences, but they also increase infrastructure complexity. So start with polling, then move to SSE when you need server push, and use WebSockets only when two-way communication is required.

Just as users expect real-time updates, they also expect fast search results. Both have become standard features in modern applications.

7. Search & discovery

Imagine a user searches for “blue running shoes size 10.”

The database scans millions of rows, and the search could take seconds to finish.

Here are some common problems with this approach:

  • Queries scan entire tables,

  • Complex searches become expensive,

  • There’s no built-in relevance ranking, typo tolerance, and/or partial matching.

You can solve this by using a search service such as Algolia/Constructor, or by building your “own” search system with Elasticsearch.

Both approaches follow a similar pattern…

Here’s how it works:

  1. Primary data stays in the database

  2. Database writes trigger events

  3. Background jobs update the search index

  4. Users then search the index instead of the database

  5. Search engine returns results ranked by relevance

Search engines use inverted indexes7 to make text search extremely fast.

They also provide features such as autocomplete, relevance ranking, typo tolerance, and filtering by attributes like price/category.

Advantages

Search engines return relevant results faster than traditional database search.

Plus, they provide features such as autocomplete, typo tolerance, and relevance ranking out of the box. Also, your primary database no longer handles expensive text search queries.

Disadvantages

But search indexes are usually slightly behind the primary database because updates happen asynchronously.

Also, running a search system adds extra operational complexity (especially if you manage Elasticsearch yourself). Plus, search indexes consume extra disk space, thus increasing infrastructure costs.

Best practices

So use a dedicated search engine ONLY when database search becomes too slow, or you need relevance ranking.

Also design your system for eventual consistency between the database and the search index. Besides, start with a managed search service unless your team has experience operating search infrastructure.

Search helps users find what they’re looking for. But you also need to protect your systems from users who send too many requests (very quickly)…

8. Rate limiting

Imagine a script sends 10,000 requests to the API each minute…

Without limits, buggy clients, abusive users, or malicious attacks can overwhelm your system. One bad actor can affect everyone else. You can solve this through rate limiting. Rate limiting controls how many requests a client can make within a given time window.

Once the limit is reached, extra requests get rejected until the window resets.

You can implement rate limiting at several layers:

  • Application code enforces limits within your service,

  • Shared memory stores rate limit state across many services,

  • API gateways reject requests before they reach your application.

Advantages

Rate limiting protects your services from overload by preventing excessive requests.

Plus, it ensures FAIR usage so one client cannot consume all available resources. Also, blocking excessive traffic early reduces unnecessary work for your app servers.

Disadvantages

But every request must go through extra rate-limiting logic,,, this adds a tiny amount of latency!

Also, maintaining consistent limits across many servers increases system complexity. Plus, limits that are too strict can negatively affect legitimate users.

Best practices

So apply many layers of limits, such as per-user, per-IP & system-wide quotas.

Also return HTTP 429 (Too Many Requests) together with a Retry-After header so clients know when to retry. Besides, log rate-limit violations to identify abuse patterns & tune your limits.

Rate limiting protects shared resources and keeps systems stable under heavy traffic. But when requests fail and clients retry, another problem appears: duplicate processing…

9. Idempotency & retries

Imagine a payment request times out… Did the payment succeed/fail?

The client then retries the request, and now the customer gets charged “twice”.

You must design for network failures because:

  • Temporary network failures occur all the time,

  • Clients don’t know whether an operation completed, so they retry the request,

  • Retries can create duplicate processing, such as double charges, duplicate records, and/or repeated side effects.

You can solve this problem through idempotency…

An idempotent operation produces the same result no matter how many times it runs. Think of it like an elevator button… pressing it five times doesn’t send five elevators, only one.

Here’s how it works:

  1. Clients generate unique idempotency keys (UUIDs) & include them in requests

  2. Servers check whether the key already exists in a deduplication store

  3. If the key exists, the server returns the original response

  4. If it’s a new key, the server processes the request and then stores the response

  5. The server keeps the key for a predefined deduplication window

Advantages

Clients can “safely” retry requests without creating duplicate side effects with idempotency.

Plus, it makes distributed systems more resilient to network failures. Also, clients become much simpler because they can retry requests without worrying about duplicate processing.

Disadvantages

But idempotency requires extra storage to keep processed request keys.

Also, clients must generate & manage unique idempotency keys correctly. Plus, old keys must eventually expire to prevent the deduplication store from growing indefinitely.

Best practices

So make state-changing APIs idempotent by default whenever possible.

Also use client-generated UUIDs instead of timestamps for idempotency keys. Besides, choose an appropriate deduplication window and return the original response when the same key is received again.

Idempotency protects individual operations. But once requests reach your application, you still need to distribute traffic efficiently across multiple servers.

This is where load balancers come in…

10. Load balancing

Imagine you deploy three web servers…yet most users keep getting routed to the same server…

One server becomes “overloaded” while the others sit mostly idle.

Without load balancing:

  • Traffic gets distributed unevenly,

  • Failed servers continue receiving requests,

  • There’s no automatic failover during outages.

A load balancer sits between clients & your servers and distributes incoming requests across many machines.

Every request first reaches the load balancer, which then selects a server using a routing algorithm.

Here are the common load balancing algorithms:

  • Round robin: distributes requests evenly across servers

  • Least connections: sends requests to the server with the fewest active connections

  • Consistent hashing8: routes requests based on properties such as a user ID

Load balancers make it easy to scale by adding more servers.

They also improve availability by removing unhealthy servers through health checks.

Advantages

You can increase capacity simply by adding more servers behind the load balancer.

Plus, traffic gets distributed more evenly across your infrastructure. Also, health checks automatically remove failed servers, thus improving system availability.

Disadvantages

But every request passes through another network hop; this adds a tiny amount of latency.

Also, advanced routing algorithms consume extra resources. Plus, a poorly configured load balancer can become a “single point of failure” itself.

Best practices

So use health checks to remove failed servers as quickly as possible.

Also choose your routing algorithm based on the workload, such as round robin for stateless services and consistent hashing for stateful ones.

Besides, let active requests finish before shutting down a server to avoid user interruptions.

Final Thoughts

You now have 10 tools in your system design toolkit…

But knowing the patterns is NOT enough. You also need to recognize which problem you’re actually solving. Most system design problems reveal themselves through metrics.

Here’s a tiny cheat sheet:

  • Slow response times → caching and/or read scaling

  • Slow data updates → scale writes

  • Request timeouts → message queues and/or asynchronous processing

  • Users constantly refreshing → real-time updates

  • Slow search → dedicated search engines

  • Traffic spikes → rate limiting and/or message queues

  • Duplicate side effects → idempotency

  • Uneven server load → load balancing

But every pattern comes with trade-offs…

Can your system tolerate eventual consistency? Do you have the budget for extra infrastructure? Does your team have the expertise to operate it? And what’s the cost of choosing the wrong solution?

A three-person startup will make very different decisions than a 100-engineer platform team…

When existing patterns don’t fit, apply first-principles thinking:

  • Challenge your assumptions,

  • Break the problem into smaller pieces,

  • Identify the most important constraints,

  • Combine multiple patterns when necessary.

Start with the simplest solution that meets today’s requirements, then evolve it as your system grows…

The best system design is usually the simplest one that solves the problem.
