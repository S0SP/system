You’ve heard it before: “It works on my machine.”

The app is under development. Tests pass, dependencies install, and everything looks ready to ship. But the moment it reaches production, something breaks. The server might use a different Python version, or a library may exist locally but not in the deployment environment. Sometimes the operating system itself causes the issue.

The problem was never just the application…it was the environment around it.

For a long time, virtual machines were the best solution engineers had.

Instead of deploying only the application, teams started packaging an entire operating system along with it. This approach fixed a big part of the consistency problem. The environment behaved the same no matter where the workload ran. But the tradeoff was hard to ignore.

Each virtual machine included its own kernel1, services, and system overhead to run a single application. They consumed a large amount of memory, took time to boot, and became too difficult to manage as the infrastructure grew.

What the industry needed was a way to isolate applications without paying the cost of a full operating system every time.

The interesting part is GNU/Linux already had most of the building blocks required to make this possible:

Namespaces could isolate processes from each other. cgroups could control how much CPU and memory a process was allowed to consume. The primitives2 already existed, but they were hard to use directly and too complex for most developers to manage on their own.

Docker changed this by turning those low-level kernel features into a developer-friendly workflow.

Engineers no longer had to configure isolation primitives manually. They got a simple CLI, portable images, reproducible environments, and a runtime for running containers at scale.

This shift fundamentally changed modern infrastructure.

Today, containers sit underneath almost everything in modern infrastructure. From CI/CD pipelines to Kubernetes clusters, they power it all. But despite how common they are, most engineers interact only with the surface layer. They know the commands. They know how to build images and start containers. What they rarely see is the runtime stack operating underneath those commands.

This newsletter is about the lower layer.

Docker Architecture

Docker is NOT one program.

It is a stack of cooperating components where every layer has a specific responsibility and passes work to the next.

Most engineers interact with the CLI and assume Docker handles everything behind the scenes. But when you execute docker run, the command travels through an entire runtime chain before a process ever starts.

Understanding this chain makes the rest of Docker's internals easier to follow…

Every layer has a specific responsibility.

Some components manage APIs. Some manage container lifecycle operations. Others interact directly with the Linux kernel. That separation keeps the runtime modular and easier to maintain.

Let’s see how the chain works:

Docker CLI

The Docker CLI3 is a thin client.

When you type docker run or docker build, it converts your command into an API request and sends it over /var/run/docker.sock4 to the Docker daemon.

The CLI itself does not build images, pull layers, or start containers. It only forwards requests.

The real work happens behind it.

This separation matters because the CLI and daemon do not even need to run on the same machine. Docker can expose its API remotely, so external tools and automation systems can communicate with the daemon directly.

dockerd

dockerd is the Docker daemon.

It receives requests from the CLI and manages images, networks, volumes5, and the overall Docker API surface. But dockerd does NOT run containers directly. Instead, it hands container lifecycle management to containerd.

This separation keeps containers running even if the Docker daemon restarts.

So the runtime layer lives independently from the higher-level Docker API layer.

The daemon also acts as the orchestration layer for local Docker operations.

When you pull an image, create a network, or attach a volume, the request first goes through dockerd. Then it reaches the lower runtime components.

containerd

containerd is the core container runtime responsible for managing container lifecycles.

It manages image pulling, snapshots, image unpacking, and runtime operations6 through a gRPC7 API.

When dockerd needs to start a container, it delegates that work to containerd. From that point onward, the Docker daemon mostly steps out of the execution path.

containerd originally started as part of Docker itself.

In 2017, Docker donated it to the Cloud Native Computing Foundation (CNCF) as an independent project. Today, Kubernetes communicates with containerd and other CRI-compatible runtimes instead of Docker.

This shift significantly changed the container ecosystem.

Docker remained the developer platform, while containerd became the runtime underneath orchestration systems. Even then, containerd does not directly create containers. It passes that responsibility further down the stack.

containerd-shim

The containerd-shim is a lightweight process between containerd and the running container.

Before a container starts, containerd launches a shim process first. The shim becomes the parent of the container process and keeps the container alive even if containerd crashes or restarts.

Each container gets its own shim. That process isolates the running container from the runtime layer and keeps the connection alive.

The shim also manages container input/output streams and exit status reporting. Without it, containerd would need to stay directly attached to every running container process.

Once the shim is ready, it calls the component that actually creates the container.

runc

runc is the Open Container Initiative (OCI) runtime that directly interacts with the Linux kernel to create the container.

It reads the container configuration and creates namespaces and cgroups. Then it configures the filesystem and starts the container process.

This is the layer where containers stop behaving like Docker objects and become ordinary Linux processes. The kernel enforces its isolation boundaries.

After the process starts, runc exits…

Its job is complete. The shim continues supervising the container and reports its status back to containerd.

OCI Standards

Every component in this stack works together because they follow the same OCI standards.

The Open Container Initiative (OCI) defines open standards for container images and runtimes. This standardization allows different tools to interoperate cleanly across the container ecosystem.

Docker-built images run unchanged on containerd, CRI-O, and Podman8. Kubernetes can swap one OCI runtime for another without changing the rest of the stack.

Before OCI standardization, container tooling was far more tightly coupled. Docker helped popularize containers, but OCI allowed different container tools to work together.

OCI standards made container runtimes modular rather than tied to a single vendor or toolchain.

Now the runtime stack is clear, let’s look at the Linux primitives that actually make containers possible…

Linux Primitives: Namespaces

Containers are not a feature of Docker… They are a feature of the Linux kernel.

Docker provides the tooling, CLI, image format, and workflow. But the isolation that makes containers actually work comes from the kernel itself. And at the center of that isolation is a single primitive: namespaces.

A namespace wraps a global system resource and makes it appear private to a specific process.

The process inside the namespace believes it has its own isolated version of that resource. Host and every other process on the machine still see the original global resource.

Linux has six namespaces that containers rely on. Each one isolates a different part of the system. Together, they create the illusion that a container is running on its own machine.

Let’s go through each one:

1. PID Namespace

Every process on a Linux system has a process ID (PID).

On the host, these IDs are global. All the running processes share the same numbering space.

The PID namespace changes this.

When a container starts inside its own PID namespace, the first process it runs gets assigned PID 19. From inside the container, that process looks like the root of the entire system. It can see its own child processes, but it cannot see anything running on the host or in other containers.

While the host sees the container process with its real PID in the global namespace. The container has NO idea.

It matters because PID 1 carries special responsibilities in Linux. It’s expected to handle signals and reap orphaned child processes. Containers that do not handle this correctly end up with zombie processes. That is why what runs as PID 1 inside a container is an important design decision.

2. Network Namespace

By default, every process on a Linux machine shares the same network stack.

They see same interfaces, same routing tables, and same ports.

The network namespace gives a container its own isolated network stack. Each container gets its own virtual network interface, IP address, routing table, and set of ports10. A process inside the container can bind to port 80 without conflicting with anything else on the host.

This is how different containers can each listen on port 80 simultaneously on the same machine. They are not actually sharing the same port. Instead, each has its own private network namespace.

Docker creates a virtual Ethernet pair to connect each container’s network namespace to the host. Traffic flows through that pair, and the host routes it appropriately.

This bridge makes container networking possible, but the namespace is what makes the isolation real.

3. Mount Namespace

The mount namespace controls what a process can see when it looks at the filesystem.

Without it, every process on the system shares the same view of the filesystem. Any process could see every mounted disk, every directory, and every file on the machine.

With a mount namespace, each container gets its own filesystem view. When Docker starts a container, it sets up a layered filesystem using OverlayFS11 and mounts it inside a new mount namespace. The container sees only that filesystem. It cannot browse the host’s directories or access files outside its own root.

This gives each container its own isolated root filesystem.

It includes its own operating system files, libraries, and application code without touching the host.

4. UTS Namespace

The Unix Time-Sharing (UTS) namespace12 controls hostname and domain name of a process.

This one is simpler than the others, but it matters for how containers identify themselves on a network. Without it, every container would share hostname of the host machine. Without it, logs, monitoring systems, and service discovery tools would struggle to distinguish containers from the host.

The UTS namespace lets each container have its own hostname.

When a container runs hostname, it sees the name Docker assigned to it, NOT the name of the underlying host. That small detail keeps container identities clean and predictable.

5. IPC Namespace

Linux lets processes communicate directly through mechanisms like shared memory segments and message queues.

The Inter-Process Communication (IPC) namespace isolates these mechanisms13. Processes inside a container can only communicate with other processes in the same IPC namespace. They cannot access another container or the host via shared memory.

Without this isolation, a process in one container could potentially interfere with or read data from shared memory segments belonging to another container on the same host. The IPC namespace closes this gap.

6. User Namespace

The user namespace is the most powerful of the six, and also the most nuanced.

It maps user IDs and group IDs inside the container to different IDs on the host. A process can appear to run as root inside the container while actually mapping to an unprivileged user ID on the host.

This distinction is critical for security.

Many containers run their processes as root by default. Without user namespaces, the process is root on the host too. A container escape14 would give an attacker full root access to the machine.

With user namespaces enabled, root inside the container is just a regular unprivileged user on the host. The blast radius of a container escape shrinks significantly.

User namespaces are what make rootless containers15 possible.

Docker, Podman, and other container runtimes use them to let engineers run containers without needing root privileges on the host at all.

How Namespaces Work Together

No single namespace makes a container.

It is the combination of all six working together that creates the isolation engineers rely on:

  • The PID namespace hides host processes.

  • Network namespace provides private networking.

  • Mount namespace gives each container its own filesystem.

  • UTS namespace sets a clean identity.

  • IPC namespace prevents cross-container memory interference.

  • User namespace limits the damage if something goes wrong.

But namespaces only control what a container can see.

They say nothing about what it can consume. That is where the second Linux primitive is used…

Linux Primitives: cgroups

Namespaces control what a container can see.

But they say nothing about what a container can consume.

Without resource control, a single container could consume all the CPU on the host and exhaust available memory. It could starve every other process running on the machine. The isolation would be real, but the system would still be fragile. One badly behaved container could take everything down.

This is the problem control groups (cgroups) solve.

cgroups are a Linux kernel feature that limit, track, and isolate the resource usage of a group of processes. Every container you run sits inside a cgroup. The cgroup defines how much CPU, memory, and disk I/O it is allowed to use. Go beyond those limits, and the kernel steps in…

Docker didn’t invent cgroups either.

They have been in the Linux kernel since 2008. Docker just made them easy to configure.

What cgroups Control

cgroups give you precise control over the resources a container can access.

Here are the main ones:

  • CPU: You can assign CPU shares to containers, which determines how much CPU time16 a container gets relative to others. You can also set hard quotas, which cap the container to a fixed percentage of CPU, regardless of what else is running.

  • Memory: This is used to set a maximum memory limit for a container. If the container tries to exceed the limit, the kernel’s Out of Memory (OOM) killer steps in and terminates the process. This prevents one container from consuming all available memory and crashing the host.

  • Disk I/O: You can throttle how much read and write bandwidth a container is allowed to use on disk. This stops storage-heavy workloads from monopolizing input/output (I/O) and affecting other containers on the same machine.

These controls are what make it safe to run many containers on the same host.

Each one gets its share of resources, and the kernel enforces those boundaries automatically.

cgroups v1 and cgroups v2

cgroups have gone through two major versions, and the difference between them matters:

cgroups v1 was the original implementation.

It worked, but it had a fundamental design problem. Each resource type, CPU, memory, and I/O, lived in its own separate hierarchy. This means a container’s resources were spread across separate control groups. Managing them consistently was complicated, and some edge cases were difficult to handle correctly.

cgroups v2 fixed this by unifying everything into a single hierarchy.

All resource controls for a container live in one place. That makes resource accounting cleaner, more consistent, and easier to reason about.

Most modern Linux distributions now default to cgroups v2.

Kubernetes also moved to cgroups v2 support. So if you are running a recent kernel, cgroups v2 is almost certainly what’s managing your containers under the hood.

How Docker Uses cgroups

When you set resource limits on a container, Docker translates those into cgroup configurations on the host.

For example, when you run:

docker run --memory=512m --cpus=1.5 nginx

Docker creates a cgroup for that container and writes the limits into the kernel. From that point, the kernel enforces them automatically. Docker doesn’t need to police the container itself. The kernel does it at the lowest level possible.

That is the key insight behind cgroups. The enforcement doesn’t happen in userspace. It happens in the kernel, which means it is fast, reliable, and impossible for the container to bypass.

Namespaces and cgroups explain how containers achieve isolation and resource control. But isolation alone does not make containers secure. To understand the real security boundaries of containers, you need to look at the container security model.

Container Security Model

Containers share the host kernel.

Every container running on the same machine uses the same underlying kernel. Sharing the kernel is the biggest security tradeoff containers make compared to virtual machines. A kernel vulnerability does NOT affect just one container. It can affect every container on that host.

So Kubernetes, Docker, and the Linux kernel add more security layers on top of namespaces and cgroups to make containers safer in practice.

Let’s look at each one:

Shared Kernel Risk

In a virtual machine, each workload runs its own kernel. And the hypervisor enforces a hard boundary between them.

Virtual Machines:

  • Each VM runs its own kernel

  • The hypervisor isolates workloads

  • Kernel exploits stay contained to the VM

Containers:

  • All containers share the host kernel

  • A kernel exploit17 can affect the entire host

  • Isolation is lighter and weaker

This does not make containers insecure.

It means the security model is different. Virtual machines offer stronger isolation by design. Containers trade isolation for speed and efficiency.

Understanding this trade-off is what allows you to make the right infrastructure decisions.

Privilege Reduction

Root18 inside a container is not the same as the root on the host…but without additional controls, it comes uncomfortably close.

Linux processes carry a set of capabilities that define what they are allowed to do. Capabilities control what a process can do. This includes binding to privileged ports19, loading kernel modules, and modifying network interfaces. A fully privileged process has all of them. A restricted process has only what it needs.

By default, Docker drops many of these capabilities when starting a container.

A container running as root still cannot load kernel modules or modify host network interfaces. Docker removes those capabilities before the container starts.

You can tune this further using two flags:

  • --cap-drop removes a capability the container would otherwise have.

  • --cap-add grants a capability the container would not have by default.

The principle here is the same as everywhere else in security.

Give a process only what it needs to do its job, and nothing more.

Rootless Containers

Rootless containers take privilege reduction one step further.

They allow the Docker daemon and its containers to run without root privileges on the host.

In a standard Docker setup, dockerd runs as root. That means a compromise of the daemon is a compromise of the host. Rootless mode changes this by running the daemon and all containers as an unprivileged user.

Combined with user namespaces, root inside the container maps to an unprivileged user ID on the host.

The tradeoff is real, though. Rootless containers come with limitations:

  • Some networking features are unavailable

  • Certain cgroup operations require additional configuration

Some environments prioritize security over convenience.

In those cases, rootless mode reduces the blast radius of a container escape.

Seccomp

Even with capabilities dropped, a container process can still make a wide range of Linux system calls20 (syscalls).

Most of those syscalls are never needed by typical applications. But they remain available, and a malicious process could use them to exploit the kernel.

Secure computing mode (Seccomp) addresses this by filtering the syscalls a container is allowed to make. Docker applies a default seccomp profile to every container. That profile blocks around 44 syscalls that are rarely needed but commonly exploited.

If a container attempts to make a blocked syscall, the kernel immediately kills the process. The application never gets a chance to do damage.

You can apply custom seccomp profiles for workloads with specific needs.

Trusted containers may need fewer restrictions, while sensitive workloads may need stricter ones.

AppArmor and SELinux

AppArmor and SELinux are Linux security modules.

They add another layer of enforcement on top of namespaces, cgroups, and seccomp.

Seccomp filters individual syscalls. While AppArmor and SELinux enforce broader policies around process behavior and system access.

They control:

  • Files a process can read,

  • Network operations it can perform,

  • And its interactions with other processes.

Docker applies a default AppArmor profile on systems where it is available. SELinux serves the same purpose on Red Hat-based systems. Both operate independently of Docker itself and are enforced directly by the kernel.

This independence matters.

Even if Docker is misconfigured or compromised, the kernel’s own security policies remain in place.

No single layer makes containers secure.

But container security does not rely on a single layer. Namespaces, capability dropping, rootless mode, seccomp, and kernel security modules all work together as a defense-in-depth model.

Container Images: Layers and OverlayFS

Every container starts from an image.

But an image is NOT a zip file and NOT a VM snapshot. It behaves differently from both.

Understanding how images work changes how you build and debug them. It also explains why some Dockerfile21 patterns build faster than others.

So let’s look at what an image is under the hood:

What an Image Really Is

An image is a stack of read-only filesystem layers.

Each layer represents a set of changes to the filesystem. Adding a file creates a layer. Installing a package creates a layer. Copying your application code creates a layer.

These layers are not merged into one big filesystem when you build the image.

They stay separate. When Docker runs a container from that image, it merges all those layers together into a single unified view at runtime.

The merging is handled by OverlayFS.

OverlayFS: How Layers Merge

OverlayFS is a Linux filesystem that can take different directories and present them as a single unified directory.

Docker uses it to merge all the read-only image layers into one coherent filesystem the container can use.

This is how it works at runtime:

  • All read-only image layers sit at the bottom of the stack

  • Docker adds a single writable layer on top when container starts

  • Reads go down through the stack until the file is found

  • Writes go only to the top writable layer, never touching the read-only layers underneath

So when a container modifies a file, OverlayFS first copies the file up from the read-only layer into the writable layer. The container then modifies the copy. The original file in the read-only layer stays untouched.

The writable layer is temporary. Delete the container, and it disappears.

The read-only layers remain unchanged and ready for the next container.

Layer Sharing and Build Cache

Because image layers are read-only and content-addressed, they can be shared across images on the same host.

If ten containers all use the same base image, that base layer is stored only once on disk. Docker does NOT duplicate it ten times. Every container shares the same underlying read-only layers and gets its own writable layer on top.

This is also what makes the Docker build22 cache work.

When you build an image, Docker checks each instruction in the Dockerfile against its cache. If nothing has changed since the last build, Docker reuses the cached layer instead of rebuilding it. The moment something changes, Docker invalidates that layer and all subsequent layers.

The last point matters more than most engineers realize.

If you copy source code early in the Dockerfile, even a small code change forces Docker to reinstall all dependencies from scratch. But if you install dependencies first and copy source code last, Docker only rebuilds the layers that changed.

Layer order is not just a style choice. It directly affects how fast your builds are.

OCI Image Spec

Docker did not just popularize containers…

It also defined a standard image format rest of the ecosystem now follows.

The Open Container Initiative (OCI)23 image specification defines a standard image format. Because of this, a Docker-built image can run unchanged on containerd, CRI-O, Podman, and other OCI-compatible runtimes.

Here are a few things worth knowing about how OCI images work:

  • Each layer is identified by a sha256 digest. The digest is a hash of the layer’s contents, so if two layers have the same digest, they are guaranteed to be identical.

  • Images are content-addressed. The digest acts as both identifier and integrity check.

  • Docker verifies each layer’s digest when pulling from a registry24.

  • A single image tag can point to different builds for different architectures. When you pull nginx on an amd64 machine and an arm64 machine, you get different layers, but the same tag. The manifest list handles this mapping transparently.

These properties make OCI images portable, verifiable, and efficient to distribute.

The layered model is not just an implementation detail. It is what makes Docker images fast to build, efficient to store, and portable across any OCI-compatible runtime.

We now understand how images work under the hood. Next, we need to understand how Docker builds them…

Dockerfile: How Images Are Built

Every container image starts as a Dockerfile.

It’s a plain text file with a set of instructions. Each instruction tells Docker what to add, install, or configure. The result is a reproducible, portable image that behaves the same way every time it runs.

Dockerfile is the recipe, and the image is the result.

Instructions and What They Do to Layers

Not every Dockerfile instruction behaves the same way.

Some create new filesystem layers. Others just set metadata. Understanding the difference helps you write leaner, faster Dockerfiles.

Here are instructions to create layers:

  • FROM sets the base image. Every Dockerfile starts here, and every later layer builds on top of it.

  • RUN executes a command during the build. Installing packages, compiling code, or running scripts all happen through RUN. Each RUN instruction creates a new layer.

  • COPY and ADD copy files from your local machine into the image. Each one creates a layer containing those files.

Here are instructions to set metadata:

  • ENV sets environment variables available at runtime.

  • EXPOSE documents which ports the container listens on.

  • CMD and ENTRYPOINT define what runs when the container starts. They do NOT create filesystem layers, but they are critical for container behavior.

Every RUN instruction creates a new layer, so combining commands helps keep the image smaller and the layer count lower.

Layer Cache Strategy

The Docker build cache is one of the most useful features in the build process.

But it is also one of the easiest to break without realizing it…

Docker evaluates each instruction in order. If a layer has NOT changed since the last build, Docker reuses it from cache. The moment a layer changes, Docker invalidates the layer and rebuilds every layer after it.

This means the order of instructions in your Dockerfile matters enormously.

Here’s a simple rule to follow:

  1. Copy dependency files first

  2. Install dependencies next

  3. Copy the application source code last

This order matters because your dependencies change far less often than your source code.

If you copy your source code before installing dependencies, every code change forces a full reinstall. But if dependencies are installed first, Docker only rebuilds from the source copy step onward. Builds stay fast even as your codebase grows.

Unnecessarily breaking the cache is one of the most common reasons Docker builds feel slow.

Multi-Stage Builds

A common problem with Dockerfiles is the build tools end up in production images:

Compilers, test frameworks, and build dependencies help during the build process. But they do NOT belong in the final production image. They add size and increase the attack surface.

Multi-stage builds solve this cleanly.

You can use multiple FROM instructions in a single Dockerfile, each defining a separate stage. The first stage handles the build, while the second defines the final image. You copy only the compiled output from the build stage into the final stage, leaving everything else behind.

The result is a small, clean production image that contains only what the application needs to run, so build tools never make it into production.

BuildKit

BuildKit is the modern Docker build engine, and it replaced the legacy builder as the default in recent Docker versions.

It improves on the old builder in several important ways:

  • Parallel execution: BuildKit runs independent build steps in parallel. This reduces build time.

  • Better caching: Cache behavior is more precise and consistent across different environments.

  • Secret handling: BuildKit lets you pass secrets into the build process, like API keys or credentials, without baking them into any layer. The secret is available during the build but never written to the image.

  • Build attestations: Modern BuildKit builds can generate Software Bill of Materials (SBOMs) and provenance metadata. These records show what went into the image and how the build created it. They also improve supply chain security.

Recent Docker versions enable BuildKit by default.

But knowing what it does under the hood helps you take full advantage of it.

A well-written Dockerfile keeps images small and builds fast. While poor Dockerfile practices increase image size, slow builds, and introduce security risks.

Image Registries and Distribution

Once an image is built, it needs to get to wherever it will run.

This might be a production server, a Kubernetes cluster, or a colleague’s machine. That’s what image registries are for.

A registry is a storage and distribution system for container images.

Docker Hub is the default. But the same protocol also works with GitHub Container Registry, Amazon ECR, Google Artifact Registry, and private registries.

Registries25 do more than store images. They also control how images move between systems. Every time Docker pulls an image, it downloads and assembles the image layer by layer.

Before a container starts on a new machine, Docker may need to pull the image from a registry first. This pull process is more sophisticated than downloading a single archive file.

How Docker Pull Works

When you run docker pull nginx, Docker does NOT download just a single file. Instead, it downloads a series of independently verified layers26.

Here is what happens during a pull:

  1. Docker contacts the registry and requests the image manifest

  2. The manifest describes the image, including its layers, their digests, and the architecture it targets

  3. Docker checks which layers already exist on the local machine

  4. Only the missing layers are downloaded

  5. Each layer also has a SHA-256 digest, which acts like a unique fingerprint generated from the layer’s contents

  6. Docker verifies that the digest after download confirms the layer arrived intact and was not modified during transit

The verification step matters.

Because layers are content-addressed, Docker immediately detects corruption or tampering during transit. A digest mismatch means the pull fails before anything runs.

Layer deduplication also applies here.

If two images share a base layer, Docker downloads that layer only once. Every image that shares its points to the same local copy. Shared layers reduce disk usage and speed up pulls.

But efficient downloads alone are not enough in production. You also need to know exactly which version of an image Docker is pulling.

To solve this problem, Docker uses image tags.

Tags are human-readable labels attached to container images. You have probably seen tags like nginx:latest, python:3.12, or node:20.

The problem is tags are mutable.

The latest Tag Problem

Every image tag is a pointer.

When you push nginx:latest, you are telling the registry to move that tag to point at your new image. But the tag itself carries no version information. It is just a label.

This creates a real problem in production.

Pulling nginx:latest today may give you a different image than it did six months ago. That makes deployments harder to reproduce. A base image update can silently change the behavior of your application without any code change on your end.

The fix is to pin to a specific version tag, or better yet, pin to a digest directly:

nginx@sha256:a3b2c1...

The SHA-256 digest27 uniquely identifies a specific image.

Unlike tags, digests never move because they are permanently tied to the image's contents. This makes deployments reproducible regardless of what happens to the tag.

Of course, reproducible images still need a place to live. And depending on your use case, that registry may be public or completely private…

Public vs Private Registries

Docker Hub is public by default, which makes it convenient for open source projects and base images.

But for proprietary application images, a private registry is the right choice.

Most cloud providers offer managed private registries. Amazon ECR28 integrates with AWS. Google Artifact Registry integrates with Google Cloud. Azure Container Registry integrates with Azure. They handle access control, vulnerability scanning, and geographic replication out of the box.

If you need full control, you can also run a self-hosted registry using the open-source distribution project.

The registry sits between the build pipeline and the runtime environment. Proper tagging and digest pinning make deployments predictable and prevent unexpected production changes.

At this point, the image is finally on the machine. But an image by itself does nothing. The real story starts when Docker turns that image into a running container.

And it starts with the container lifecycle…

Container Lifecycle

An image sitting in a registry, like Docker Hub, does nothing on its own.

The moment Docker turns that image into a running container, it enters a predictable sequence of states. Knowing this sequence makes it easier to debug containers and understand failures.

A container moves through four states: created, running, stopped, and removed.

  • Created: Container exists but has not started yet. Docker has prepared the filesystem and allocated resources, but no process is running.

  • Running: The container process is actively running and handling application work. This is the state containers spend most of their life in.

  • Stopped: Container process has exited, either cleanly or because of a failure. The container still exists on disk and can be restarted.

  • Removed: The container is deleted entirely. Its writable layer, temporary filesystem used while the container runs, is gone. Any data not stored in a volume is lost permanently.

Each state has a clear meaning, and each transition is triggered by a specific action.

PID 1 and Process Behavior

When a container starts, whatever you define as the entrypoint runs as PID 1 inside the container.

It sounds like a tiny detail. But it carries real consequences…

In Linux, PID 1 is treated differently from normal processes29. It is responsible for handling system signals correctly and cleaning up orphaned child processes.

Signals are messages sent to a process to tell it what to do. For example:

  • SIGTERM tells a process to shut down gracefully so it can finish ongoing work and clean up resources.

  • SIGKILL forces a process to stop immediately without cleanup.

PID 1 is also responsible for cleaning up orphaned child processes.

When a child process exits, Linux expects its parent process to clean it up properly. If the parent process is gone, PID 1 inherits the responsibility.

The problem is most applications were never designed to run as PID 1.

A Node.js server, a Python app, or a Go binary is built to handle application logic. They are not built to behave like an init system.

So when Docker sends a SIGTERM to stop the container gracefully, many applications ignore it or handle it incorrectly. Docker waits for the process to exit, times out, and then sends SIGKILL instead. The container shuts down abruptly30 instead of exiting cleanly.

This is why small init systems like tini exist.

They run as PID 1, handle signals correctly, clean up orphaned processes, and then pass control to your application. A single line in your Dockerfile solves the problem entirely.

Restart Policies and Ephemerality

Containers are meant to be replaceable, not precious.

When a container stops, Docker can automatically restart it based on the restart policy you configure:

  • no: Never restart. The default.

  • on-failure: Restart only if the container exits with a non-zero error code.

  • always: Always restart, regardless of how it stopped.

  • unless-stopped: Always restart unless you manually stopped it.

But restart policies only tell you whether a container is running.

They say nothing about whether the application inside it is actually healthy.

A container can be running while still serving errors on every request. It’s what health checks are for. They let Docker detect broken application state and react to it, independent of whether the process itself is alive.

One more thing worth remembering:

The writable layer inside a container is temporary. When a container is removed, everything written inside it disappears. Any data that needs to survive belongs in a volume, NOT inside the container itself.

Now that the lifecycle is clear, let’s see how Docker starts your application…

How Docker Works: From docker run to a Running Container

You now understand the individual pieces: namespaces, cgroups, images, layers, and runtime stack.

But learning these components separately is different from seeing how they work together.

This section connects the entire flow…

Here is what happens inside your machine from the moment you execute docker run to the moment your application starts running:

Step 1: CLI sends the Request to dockerd

When you run docker run nginx, Docker CLI converts the command into an API request and sends it through /var/run/docker.sock to the Docker daemon.

The CLI’s role ends here.

From this point forward, the rest of the work moves deeper into the container runtime stack.

dockerd receives the request and checks whether the image already exists on the machine. If the image is available locally, the process continues immediately.

Otherwise, Docker pulls it from the registry and downloads only the missing layers.

Step 2: dockerd Hands Off to containerd

Once the image is ready, dockerd delegates container creation to containerd.

This is where the Docker API layer steps aside, and the runtime layer takes control.

containerd prepares something called a bundle. A bundle is a directory created for the container runtime, and it contains two main parts:

  • A root filesystem built by merging image layers with OverlayFS

  • A configuration file describing how the container should run

This configuration includes namespaces, cgroups, mounts, networking details, and resource limits.

Step 3: containerd Launches the Shim

Before the container starts, containerd launches a containerd-shim process.

The shim is a lightweight helper process that stays attached to the container after startup. Its role is important… The shim becomes the parent process of the container and keeps it alive independently of containerd itself.

This separation allows containerd to restart or upgrade without interrupting running containers.

Once the shim is ready, it invokes the component responsible for creating the container.

Step 4: runc Creates the Container

The shim calls runc with the prepared bundle. At this point, the Linux kernel becomes directly involved.

runc reads the configuration and prepares the container environment:

  • Namespaces isolate processes, networking, mounts, hostnames, and inter-process communication from the host system

  • OverlayFS builds the container’s root filesystem from image layers

  • cgroups enforce CPU, memory, and disk I/O limits

  • Linux capabilities remove unnecessary privileges

  • seccomp blocks sensitive system calls that the container should never make

Once the environment is ready, runc starts the container process.

That process becomes PID 1 inside the container’s PID namespace. From this point onward, container exists as an isolated process on the system.

After startup, runc exits because its work is complete.

Step 5: Docker Configures Networking

With the container process active, Docker sets up networking.

A virtual Ethernet pair acts like a cable between the host and the container. One side connects to the container’s network namespace, while the other connects to Docker’s virtual bridge network on the host.

Docker then assigns an IP address to the container and installs the required iptables rules to route traffic.

If you publish a port with -p 8080:80, Docker creates a forwarding rule. Traffic arriving on port 8080 on the host gets redirected to port 80 inside the container.

At this stage, the container becomes reachable from outside.

Step 6: Container Is Live

The shim now supervises the container process.

It manages input and output streams, tracks exit status, and reports state changes back to containerd.

The container is now fully active, and your application is running.

What makes this sequence powerful is not any single step. The real strength comes from the layered design underneath it.

Each component handles a specific responsibility:

  • namespaces provide isolation

  • cgroups control resource usage

  • OverlayFS builds the filesystem

  • The shim keeps containers alive independently of higher runtime layers

In the end, all of these layers work together to start an isolated container process.

This is what happens behind the scenes when you run docker run. Now let’s see how containers communicate with each other and external systems…

Container Networking

Containers are isolated by design.

Each one gets its own network namespace, IP address, and network stack. But isolation alone is NOT enough. Containers still need to communicate with each other and receive traffic from the outside world. In some cases, they also need to talk to services running on the host. This is what container networking solves.

Docker handles this through different network drivers, each designed for a different use case.

Bridge Network

When Docker installs on a machine, it creates a virtual network bridge31 called docker0.

This bridge acts like a software switch on the host. Every container connected to it gets its own IP address and can communicate with other containers on the same bridge.

When a container starts, Docker creates a virtual Ethernet pair:

  • One end appears inside the container as eth0.

  • Other connects to the docker0 bridge on the host.

Traffic flows through this pair in both directions.

But the default bridge network has an important limitation. Containers cannot resolve each other by name. They can only communicate using IP addresses.

And since container IPs are ephemeral, relying on them quickly becomes fragile.

User-Defined Networks and DNS

Docker solves this through user-defined networks.

Once containers join the same custom network, they can communicate using names instead of IP addresses. A container named api can communicate with another container named database simply by using database as the hostname.

Docker’s internal DNS32 server handles the resolution behind the scenes. It does not matter:

  • what IP address the database container has,

  • whether the container restarted,

  • or whether its IP changed afterward.

This is the standard approach for most real-world setups.

User-defined networks also improve isolation. Containers on different networks cannot communicate unless you explicitly connect them.

Port Publishing and iptables

Containers run inside their own isolated network namespace.

By default, nothing outside the host can reach them.

To expose a container externally, Docker allows you to publish ports using the -p flag:

docker run -p 8080:80 nginx

In this example:

  • 8080 is the port exposed on the host,

  • 80 is the port the application listens on inside the container.

Behind the scenes, Docker installs an iptables rule on the host to forward incoming traffic into the container.

So when traffic arrives on port 8080:

  • Docker forwards it to port 80 inside the container.

  • Application processes the request.

  • The response flows back through the same path.

From the outside, the application appears to run directly on the host. Inside the container, it is still listening on port 80.

Other Network Modes

Docker also supports several other network modes for specific scenarios:

  • Host networking: The container shares the host’s network namespace directly. There is NO virtual interface or port translation. This provides the best performance but completely removes network isolation.

  • None: The container gets no network interface at all. Useful for workloads that should have zero network access.

  • Overlay: Connects containers running across multiple hosts through a distributed virtual network. Commonly used in Docker Swarm33.

  • Macvlan: Gives the container its own MAC address and makes it appear as a physical device on the network. Useful for legacy applications that expect direct network access.

For most workloads, a user-defined bridge network is the right choice.

It provides DNS resolution, isolation, and simple connectivity without adding much complexity.

With networking handled, the next piece of the runtime picture is storage. Specifically, how containers manage data that must survive beyond the container’s lifetime…

Container Storage and Volumes

Containers are ephemeral.

When a container is removed, its writable layer, where runtime changes are stored, disappears with it. Logs, uploads, and database records stored inside the container are permanently lost.

This is fine for stateless applications.

But most real systems need data to survive beyond the lifetime of a single container. A database cannot lose its records every time it restarts. A file upload service cannot lose its files every time it deploys.

Docker solves this through three storage mechanisms, each designed for a different situation:

Volumes

Volumes are the standard way to persist data in Docker.

Docker manages them outside the container filesystem, so the data survives even after the container is removed.

The container writes to a volume exactly as it writes to any other directory. But the volume is separate from the container and survives even after the container is removed.

Volumes also solve a problem that becomes obvious in production.

Many containers can mount the same volume simultaneously. A web server and a logging agent can both access the same directory without coordinating with each other.

They also integrate cleanly with Docker’s backup and migration tools. If data matters, it belongs in a volume.

Bind Mounts

Bind mounts map a specific directory on the host directly into the container.

Whatever exists at that path on the host is exactly what the container sees. Changes made inside the container appear immediately on the host, and vice versa.

This makes bind mounts extremely useful during development. You mount your source code directory into the container. Every local change immediately shows up inside the running container. There are no rebuilds and no restarts.

But bind mounts carry a real risk in production. A misconfigured bind mount can expose sensitive host directories to the container.

This is why production workloads typically use volumes, while bind mounts are mostly used for local development.

tmpfs Mounts

tmpfs mounts store data in the host’s memory instead of writing it to disk.

The data disappears the moment the container stops.

This makes tmpfs34 useful for sensitive data that should never touch the filesystem. Secrets, tokens, and temporary credentials are common examples.

Each storage mechanism solves a different problem. Volumes persist data, bind mounts connect containers to host files, and tmpfs keeps sensitive data only in memory.

Choosing the right one depends entirely on what the data is and how long it needs to live.

Limitations of Docker

Docker made containers easy to use.

But the simplicity also hides a lot of complexity underneath:

What Docker Gets Right

Before containers, teams managed environment consistency manually through scripts, documentation, and “hope”. Docker changed this by making environments portable and reproducible across different systems.

Here are a few other things Docker gets right:

  • Packaging applications with their dependencies in a single image greatly reduces environment drift.

  • Layered image format speeds up builds and saves storage by reusing cached layers.

  • OCI standards allow Docker images to run across different platforms without modification.

  • Docker Compose made it much easier to run multi-service applications locally.

Where Docker Struggles

Containers share the host kernel.

This single fact means container isolation is fundamentally weaker than VM isolation. For most workloads, the tradeoff is acceptable. For sensitive multi-tenant environments, it is not…

Here are a few other areas Docker falls short:

  • Poor Dockerfile practices can quickly create bloated and slow-building images

  • Root inside a container is still risky because containers share the host kernel

  • Stateful workloads look simple at first. But managing persistent data in containers is difficult.

  • Docker works well on a single machine. But Docker alone struggles once workloads span multiple machines and require automatic recovery.

That last point is where the next piece of infrastructure comes in.

Beyond Docker

Docker popularized containers.

But it is no longer the only runtime, and in many modern systems, it is not even the default.

The container ecosystem has moved toward modularity. Each layer of the stack is now replaceable, and new tools have emerged to handle different parts of Docker’s workflow:

  • Podman removes the daemon entirely. Containers run as regular processes, without a background service, and do not require root privileges by default.

  • containerd runs directly under Kubernetes without Docker involved at all. It is the most widely used container runtime in production today

  • CRI-O is a lightweight container runtime built specifically for Kubernetes. It includes only the components required by the Container Runtime Interface (CRI).

  • Kata Containers runs each container inside a lightweight virtual machine to provide stronger isolation. It closes the shared kernel gap that standard containers leave open.

What made all of this possible is OCI.

Because every runtime follows the same open standards, Docker-built images run unchanged across all of them. Kubernetes talks to any OCI-compatible runtime through CRI without caring which one it is.

Docker started the container revolution. But the ecosystem it created has grown well beyond it…

One Container is Easy—Now Try a Thousand

Running one container on one machine is ‘easy’.

But production is where things start getting complicated.

Which machine should the next container run on? What restarts it after a crash? And what happens when the machine itself goes down?

Containers also need to find each other across hosts, updates need to roll out without downtime, and failed deployments need a safe rollback path.

These are not unusual situations. They are the normal problems of running containers in production.

Docker was never designed to handle all of this on its own. It solves the problem of running containers on a single machine. But once applications start spreading across many servers, you need something that can coordinate everything happening underneath.

You need a system that can schedule containers across machines, automatically recover failed workloads, manage networking between services, and handle deployments without bringing the application offline.

That system is Kubernetes.

Docker changed how applications are packaged and shipped. Kubernetes changed how those applications are managed at scale.

And that is exactly what the next newsletter in this series covers…

Closing Thoughts

Docker feels simple on the surface.

You run a command, container starts, and application behaves the same way almost everywhere.

But underneath that simplicity is a stack of Linux primitives working together behind the scenes. Every part you learned about exists for one reason: to isolate processes while still sharing the same kernel.

At this point, you should understand what each layer is actually doing:

  • Docker runtime stack (dockerd, containerd, runc, and containerd-shim) manages the full container lifecycle behind the scenes

  • Namespaces isolate what a container can see, including processes, networking, and the filesystem

  • cgroups control what a container can consume by enforcing CPU and memory limits

  • Layered images make containers portable, efficient to store, and fast to distribute

  • Networking and storage are built using normal Linux primitives like virtual Ethernet pairs, iptables rules, and host directories

Once you understand those layers, container behavior starts making a lot more sense.

They are just Linux processes running inside carefully controlled environments.

This understanding becomes important in production. When containers fail, consume excessive resources, or behave differently across environments, the root cause usually lies somewhere in the underlying layers.

And while running one container is straightforward, running hundreds across many machines introduces a completely different challenge. Containers now need scheduling, service discovery, health management, scaling, and automated recovery.

This is the problem Kubernetes was built to solve.

And once containers start spreading across multiple machines, orchestration becomes the next thing you need to understand.
