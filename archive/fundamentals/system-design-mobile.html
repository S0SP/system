40. Modular Architecture/Feature-Based Modules

As mobile apps grow, the codebase can become very large and difficult to manage.

If everything is written in one BIG project, it becomes harder to understand the code, make changes, and test new features.

To solve this problem, you can use modular architecture.

In modular architecture, app is divided into separate modules, where each module represents a specific feature of the app.

An app could have modules like:

  • Auth module: Handles login and signup.

  • Feed module: Shows posts or content.

  • Checkout module: Handles payments and orders.

Each module contains its own code and exposes only the parts other modules need.

This keeps features separate and prevents different parts of the app from interfering with each other.

This structure makes the app easier to understand and maintain.

Why It Matters

In a very large app, building the entire project can take a long time…

If a single codebase contains hundreds of thousands of lines of code, compiling the app could take several minutes.

With modular architecture, only the module that changed needs to be rebuilt. This makes builds much faster and helps you work more efficiently.

Real-World Example

Airbnb, Uber, and Spotify use modular architecture in their mobile apps.

They adopted this approach to accelerate development, improve code organization, and allow different teams to work on separate features simultaneously.

Trade-offs

Modular architecture also introduces some challenges.

You need to carefully design the boundaries between modules and define clear interfaces for how modules communicate with each other. Some shared functionality, such as analytics, navigation, or design systems, may need to live in a common core module that all features can use.

It can also be difficult to convert an existing large app into a modular structure after it has already grown.

Practical Tip

It’s useful to visualize how modules depend on each other.

Tools like dependency graph visualizers can help teams see how modules are connected and identify problems such as circular dependencies, where two modules depend on each other. This usually means the architecture needs improvement.

While modular architecture improves how the app code is organized, mobile apps also depend heavily on backend systems designed specifically for them.

41. Backend for Frontend (BFF) for Mobile

Mobile apps often need data from “many” different backend services.

A single screen requires data from a user service, a recommendation service, and a content service.

If the mobile app directly calls all these services, it would need to make several network requests and combine the results on the device. This can SLOW down the app and increase battery usage.

To solve this, use a technique called Backend for Frontend (BFF).

A BFF2 is a special backend layer designed specifically for a specific type of client, such as a mobile app.

Instead of the mobile app calling many services, it sends one request to the BFF. The BFF then communicates with the required services, gathers the data, combines it, and sends back a single optimized response.

This makes the mobile app simpler and reduces the number of network requests.

Why It Matters

Every network request adds delay & consumes battery.

If a mobile screen requires data from five services, the app will make five separate API calls. This increases latency and slows down the user experience.

With a BFF, the mobile app only makes one request, and the server handles the rest. This improves performance and keeps the app more efficient.

Real-World Example

Netflix uses the BFF approach to serve different types of clients.

They maintain separate backend layers for iOS apps, Android apps, TVs, and web browsers.

Each BFF returns data formatted specifically for that device.

A mobile BFF sends smaller responses optimized for mobile screens, while the TV version may include higher-resolution metadata.

Trade-offs

Using a BFF also introduces an additional service that needs to be maintained.

It is important BFF does not become overly complex. Its main responsibility should be to aggregate and transform data for the client. Core business logic should remain in the backend services that actually own the data.

42. App Versioning & Backward Compatibility

When mobile apps are released, users do NOT always update them immediately.

Some people update right away, but others may continue using an older version of the app for weeks or even months.

So the backend system must support many versions of the app simultaneously.

i.e., server should continue to work with older app versions while also supporting the latest version.

To manage this, use versioning:

Versioning assigns each API, or app release, a version number so the server knows how to communicate with different app versions.

Check these API endpoints:

/v1/users
/v2/users

Each version can return data in a format that matches what that specific app version expects.

Why It Matters

If the backend changes something in the API without considering older app versions, older apps will suddenly stop working…

If the server removes a field that an older app depends on, the app could crash or show broken screens.

Unlike websites, mobile apps cannot be updated instantly for every user. This is why systems must remain backward compatible.

Real-World Example

Stripe uses API versioning to maintain compatibility.

When a client makes an API request, it specifies which API version it expects. Even if Stripe changes the API later, older clients still receive responses in the format they were built for.

This allows the platform to evolve without breaking existing apps.

Trade-offs

Supporting many versions of an API requires extra maintenance.

You need to keep older fields or response formats in the system for some time.

A common strategy used to manage this safely is called the Expand–Contract pattern:

  1. First, add new fields or features without removing the old ones.

  2. Gradually update apps to use the new fields.

  3. Once all users have updated, remove the old fields.

This approach prevents breaking older versions while still allowing the system to evolve.

43. Feature Flags & Remote Configuration

When you add a new feature to a mobile app, you must release a new version of the app and wait for users to update it.

This process can take time because apps must go through the app store review, and not all users update their apps immediately.

Feature flags solve this problem:

A feature flag is a switch that lets you remotely enable or disable a feature without releasing a new version of the app.

The feature’s code is already included in the app, but it stays disabled by default. You can later enable it from a dashboard for specific users or for everyone.

This allows you to control when features are released.

Remote configuration extends this idea even further. It allows you to change certain app behaviors remotely, such as:

  • UI text or labels

  • Feature limits

  • Layouts or design elements

  • Experiment settings

Tools such as Firebase Remote Config are commonly used for this.

Why It Matters

Submitting an app update to the app store can take up to 3 days for approval.

If a new feature has a bug and has already been released to millions of users, fixing it through another app update can take time.

With feature flags, you can disable the feature instantly from a dashboard without waiting for another release.

This makes apps safer and easier to manage in production.

Real-World Example

Many companies use feature flags to run A/B testing3 experiments.

Airbnb tests two different versions of a feature:

  • One group of users sees the original version.

  • Another group sees a new version.

Feature flags control which users see which version, allowing the company to measure which design performs better.

Trade-offs

While feature flags are powerful, they can also create complexity.

If too many flags are added and never removed, the codebase can become cluttered with outdated flags. To avoid this, you should define a lifecycle policy where every feature flag has a purpose and an expiry date. Once the feature becomes permanent, the flag should be removed from the code.

Feature flags help control when features are released, but navigation systems determine how users actually reach those features inside the app.

44. Deep Linking for Navigation & Growth

Sometimes users open an app from outside the app itself.

They could click a link in an email, tap a push notification, or open a link shared on social media.

Deep linking allows these links to take users directly to a specific screen inside the app, instead of just opening the home screen:

  • Notification about a shipped order opens the order tracking screen.

  • Promotion link opens the offer page.

  • Shared product link opens the product details screen.

This helps users reach the exact content they want much faster.

Modern mobile platforms provide a secure way to implement this using Universal Links (iOS) and Android App Links.

These links use normal HTTPS web URLs that are verified with your domain. When a user taps the link:

  • If the app is installed, the app opens directly.

  • If the app is NOT installed, the link opens in the browser.

This avoids problems that older custom URL schemes had, where many apps could claim the same link format.

Another related concept is deferred deep linking.

Deferred deep linking handles the situation when a user clicks a link before installing the app. In this case:

  1. User clicks the link.

  2. They are redirected to install the app.

  3. After installing and opening the app, it automatically navigates to the original intended screen.

Why It Matters

Deep links connect your app to the rest of your ecosystem.

Many important user flows depend on them, such as push notifications, marketing emails, social media sharing, referral links, and web-to-app experiences.

If deep links do not work correctly, users may land on the wrong screen or fail to complete an action, which can reduce engagement and conversions.

Real-World Example

Imagine receiving a notification that says, “Your order has shipped.”

When you tap the notification, the app opens directly on the order tracking screen, instead of the home screen.

Similarly, if a user clicks a promotional link before installing the app, deferred deep linking ensures that after installation, they still land on the correct promotional page.

Practical Tip

Deep links should be tested in several situations:

  • When the app is already open.

  • When the app is running in the background.

  • When the app is not installed.

  • When the user has an older version of the app.

Each situation may require slightly different handling to make sure the link always works correctly.

Deep linking helps users land directly on specific screens inside the app. Once users enter the app, a well-designed navigation system ensures they can move smoothly between different screens and features.

45. Navigation & Screen Flow Architecture

Navigation architecture defines how users move between different screens inside a mobile app.

It also determines how screens are connected, how data is passed between them, and how the app remembers the user’s navigation history.

When a user navigates from the home screen to a product page and then to the checkout page, the navigation system tracks this path. If the user taps the back button, the app knows which screen to return to.

Designing navigation carefully is important because it affects how smoothly users can move through the app.

Here are three common navigation patterns used in mobile apps:

a. Stack-Based Navigation

This is the simplest navigation model.

Screens are placed on top of each other like a stack.

  • Opening a new screen pushes it onto the stack.

  • Pressing back pops the screen off the stack.

This pattern is commonly used in simple flows, such as moving from a list to a details page.

b. Tab + Stack Navigation

Many apps combine tabs with stack navigation.

At the bottom of the app, there are tabs such as Home, Search, Notifications, and Profile.

Each tab contains its own stack of screens.

A user might open the Home tab and navigate through several screens there, then switch to the Profile tab and see a completely different navigation path.

This is one of the most common patterns used in social media and content apps.

c. Coordinator / Router Pattern

In larger apps, navigation logic can become complex.

The Coordinator (or Router) pattern separates navigation logic from the screen’s UI code. Instead of each screen deciding where to go next, a separate component called a coordinator manages navigation.

This makes the code easier to test and maintain because screens focus only on displaying content while the coordinator handles navigation decisions.

Why It Matters

Navigation architecture has a big impact on how easy it is to maintain and expand an app.

A well-designed navigation system makes it easier to:

  • Support deep links that open specific screens.

  • Restore the user’s state when the app restarts.

  • Write tests for individual screens.

  • Maintain predictable back button behavior.

A poorly designed navigation system can cause confusing back navigation, broken deep links, and complicated code that becomes difficult to maintain over time.

Real-World Example

Many large apps use the Coordinator pattern to manage navigation.

In this approach, the screen itself does not decide where to navigate next. Instead, the coordinator controls the flow.

When a user completes the login screen, the coordinator decides whether to go to the home screen, the onboarding flow, or another step.

This allows you to change navigation flows without modifying the screen’s UI code.

Trade-offs

Each navigation pattern has advantages and limitations:

  • Stack navigation: Simple to implement and works well for basic flows, but can become difficult when flows become complex.

  • Tab + Stack navigation: Very common for large apps and keeps sections of the app organized, but requires careful management of navigation state.

  • Coordinator pattern: Flexible, easier to maintain in large apps, and improves testability, but requires more planning and consistent use across the team.

Device & Platform Awareness

Mobile apps run on many different devices, each with its own hardware capabilities and operating system rules.

So apps must adapt to device limitations, system permissions, accessibility features, and different languages or regions.

This section explains how mobile apps handle these platform differences to provide a smooth experience for all users.

46. Permissions Model (Runtime Permissions)

Mobile apps often need access to certain device features, such as the camera, location, contacts, or microphone. Because these features can involve sensitive user data, both iOS and Android require apps to ask for permission before using them.

This is called runtime permissions. i.e., app asks for permission while it is running, not automatically when it is installed.

For example:

  • If a user wants to take a photo in the app, it will request camera permission.

  • If the app needs to show nearby places, it’ll request location permission.

Users must approve these requests before the app can access those features.

A good practice is to ask for permission only when it is actually needed. Instead of requesting camera access when the app opens, the app should request permission when the user taps the “Take Photo” button.

It is also helpful to explain why the permission is needed before showing the system permission pop-up.

Apps should also handle cases where the user denies permission. If camera access is denied, the app should allow users to upload an existing photo instead.

Why It Matters

If an app asks for many permissions immediately when it launches, users may feel uncomfortable & deny them.

But when permissions are requested at the moment they are needed, users are more likely to understand the reason and grant access.

According to a study, unexpected permission requests are more than twice as likely to be denied, and permission requests accompanied by an explanation have a denial rate roughly half that of requests without one.

Real-World Example

Airbnb asks for location permission when a user wants to search for nearby listings.

Before showing the system permission pop-up, the app first displays a simple explanation, such as “Allow location access so we can show places near you.”

This helps users understand the purpose of the permission and makes them more likely to approve it.

Trade-offs

On iOS, the system permission dialog usually appears only once. If a user denies the request, the app cannot show the same system prompt again. Instead, the user must manually enable the permission in the device settings.

So, apps must design their permission requests carefully and provide clear explanations before asking for access.

Accessibility is another important factor in mobile app design, ensuring that apps can be used by people with different abilities.

47. Accessibility (a11y)

Accessibility design makes mobile apps usable by everyone, including people with disabilities.

This includes users who may have difficulty seeing, hearing, or interacting with the screen.

According to the WHO Report on Disability, around 15% of the world’s population lives with some form of disability. So making apps accessible is both important and often required by law in many regions.

Mobile platforms provide built-in accessibility tools such as VoiceOver (iOS) and TalkBack (Android). These tools read screen content aloud and help users navigate the app using gestures or assistive devices.

To support accessibility, apps should follow a few key practices:

  • Add labels for screen readers so VoiceOver or TalkBack can describe buttons and elements.

  • Use good color contrast so the text is easy to read.

  • Support dynamic text sizes so users can enlarge fonts if needed.

  • Maintain a logical focus order so screen readers move through the interface meaningfully.

These practices help ensure that users can understand and interact with the app properly.

Why It Matters

Accessibility is not only about legal compliance or ethical responsibility. Accessible apps also tend to be easier for all users to understand and navigate.

Apps that support accessibility often receive better user feedback and higher ratings because users appreciate inclusive and well-designed experiences.

Real-World Example

An app called “Be My Eyes” was designed specifically with accessibility in mind. It connects blind or low-vision users with volunteers who help them through live video.

Because accessibility was built into the product from the beginning, the app has grown to millions of users and volunteers and even received “Apple’s App of the Year award”.

Practical Tip

One of the easiest ways to test accessibility is to turn on a screen reader, such as VoiceOver or TalkBack, and try using your app for a few minutes.

You will quickly notice problems such as:

  • Buttons without labels.

  • Confusing navigation order.

  • Elements that are difficult to activate.

These simple tests can reveal accessibility issues that are easy to fix early.

Supporting users around the world also requires apps to adapt to different languages and regions, which is where localization becomes important.

48. Localisation & Internationalisation (i18n)

Mobile apps are used by people all around the world, so they often need to support multiple languages and cultural formats.

To make this possible, design apps with internationalization and localization.

Internationalization (often written as i18n) means building the app in a way that makes it easy to support different languages and regions without changing the core code.

Localization (L10n) is the process of actually translating the app’s text and adapting it for a specific language or culture.

Localization includes:

  • Translating text into another language.

  • Displaying dates in the correct format.

  • Showing currencies based on the user’s region.

  • Adjusting layouts for languages that read in a different direction.

Here are a few important practices to make localization easier:

  • Avoid combining text pieces together in code. Different languages may use different word orders.

  • Support right-to-left (RTL) languages, such as Arabic or Hebrew.

  • Format numbers, dates, and currencies correctly for each region.

These steps allow the app to adapt automatically depending on the user’s language or location.

Why It Matters

Since only about 25% of the world’s population speaks English as a native language, apps that support only one language can exclude a large number of potential users.

Apps that properly support localization can reach a much larger audience and provide a better experience for global users.

On the other hand, poorly localized apps often have issues like:

  • Text that gets cut off.

  • Layouts that break in other languages.

  • Incorrect formatting for dates or currencies.

These problems can make the app feel unpolished or difficult to use.

Real-World Example

When an app supports RTL languages properly:

  • The entire layout flips horizontally.

  • Navigation elements move to the opposite side.

  • Lists and reading direction change accordingly.

Back button may appear on the right side instead of the left.

i.e., localization is not only about translation but may also require adjusting the app's layout.

Trade-offs

Different languages use different amounts of space:

  • German text is often much longer than English.

  • Japanese text can be shorter, but it may require different line-breaking rules.

So, UI elements should be designed to handle longer or shorter text.

Fixed-width text containers can cause problems when translated content becomes longer.

Apps must also adapt gracefully when resources like battery or connectivity are limited.

49. Graceful Degradation (Low Network/Low Battery Modes)

Mobile devices sometimes operate under limited resources.

A user may have a slow network connection, a low battery, or may enable Low-Power Mode on their device.

In these situations, apps should adjust their behavior to use fewer resources instead of continuing to operate normally. This approach is called graceful degradation.

i.e., app still works, but some features may be reduced or simplified to save battery, data, or processing power.

Mobile operating systems provide special power-saving modes:

  • Low Power Mode on iOS

  • Battery Saver on Android

When these modes are enabled, the system may limit background activity, slow down animations, or restrict network usage to help extend battery life.

Apps should detect when these modes are active and adjust their behavior.

An app could:

  • Pause auto-playing videos.

  • Reduce how often it syncs data with the server.

  • Lower image or video quality.

  • Disable background location updates.

The goal is to protect the user’s battery and data while keeping the app's main features usable.

Why It Matters

When users enable Low-Power Mode, they are telling the device that battery life is more important than performance.

If an app ignores this and continues making frequent network requests or running heavy tasks, it will quickly drain the battery. This creates a poor user experience and may cause the operating system to stop the app’s background activity.

Designing apps to respect these conditions helps build trust with users and keeps the app running smoothly even when resources are limited.

Real-World Example

Many popular apps adjust their behavior when battery or network conditions are limited:

  • Netflix reduces video quality and disables certain visual effects when “Low-Power Mode” is active.

  • Spotify reduces streaming quality to save battery and data.

In both cases, the app still works, but it uses fewer resources, so the device can last longer.

Practical Tip

Mobile platforms provide system APIs that let apps detect when power-saving modes are active:

  • iOS: ProcessInfo.isLowPowerModeEnabled

  • Android: PowerManager.isPowerSaveMode()

Apps can listen for changes in these modes and update their behavior immediately when the user enables or disables power saving. By adapting to low-battery or weak-network conditions, apps can continue working smoothly without draining the device.

Location services are another feature that must be used carefully because they can affect both privacy and battery usage.

50. Geo-Location Usage (Location Modes, Battery Cost, Background Permissions)

Many mobile apps use location services to provide useful features.

Apps show nearby restaurants, track deliveries, or help users navigate.

But getting a device’s location can use a lot of battery. In fact, GPS is one of the biggest battery consumers on a phone, after network activity.

So, apps should choose the right location method depending on what they actually need.

Different Location Modes

Here are three ways mobile platforms provide to get a device’s location, each with different accuracy and battery usage:

a. Precise GPS

This is the most accurate method. It uses satellite signals to determine the device's exact location.

Yet it also consumes the most battery power.

Apps should use precise GPS only when they really need exact tracking, such as during navigation or ride-sharing trips.

b. Network-Based Location (Significant Location Change)

This method estimates the location using Wi-Fi networks and mobile towers.

It is less accurate than GPS, but it uses much less battery. It works well for features that only need an approximate location.

c. Geofencing

Geofencing allows the app to define a virtual boundary around a location, such as a store, airport, or delivery zone.

The operating system monitors the location in the background. When the user enters or leaves that area, the app is notified.

This approach is very efficient because the OS manages the monitoring, and the app doesn’t need to constantly check the user’s location.

Why It Matters

Using GPS continuously can drain a phone’s battery very quickly.

Research found that GPS apps depleted battery life by 13% in areas with good signal strength and as much as 38% in areas with weak signal strength, highlighting how significantly continuous location tracking can affect device endurance.

If users notice that an app is draining their battery, they should uninstall it or disable its permissions.

Choosing the right location method helps apps deliver useful features without draining the battery.

Real-World Example

Many apps switch between different location methods depending on the situation:

  • Uber uses precise GPS while a ride is active so it can track the driver accurately. When the ride ends, it switches to a lower-power location method.

  • A delivery app would use geofencing to detect when a driver is near the delivery area, rather than constantly tracking their exact position.

Permissions and Privacy

Location access is sensitive information, so mobile platforms require explicit user permission.

Apps may request different levels of location access:

  • While using: App can access location only when it is open.

  • Always: App can access location even in the background.

Background location requires a clear explanation of why the app needs it.

Both iOS and Android show users which apps are using location in the background. So apps should request background location only when absolutely necessary.

Trade-offs

More accurate location tracking provides better data, but it also consumes more battery and may raise privacy concerns.

To balance this:

  • Use precise GPS only when needed.

  • Prefer network-based location for general features.

  • Use geofencing for location-based triggers.

Designing location features carefully ensures the app remains helpful without draining the user’s battery or violating their privacy.

Finally, once the app is released, you need ways to monitor how the app performs in real-world conditions.

51. Crash Reporting & Performance Monitoring

When a mobile app is used by thousands or millions of people, problems can happen that you never saw during testing. The app could crash, load slowly, or behave differently on certain devices.

To understand and fix these problems, use crash reporting and performance monitoring tools.

Crash reporting tools automatically collect information whenever an app crashes. These tools record:

  • Error that caused the crash.

  • Device and operating system.

  • Exact line of code where the crash happened.

Popular tools include Firebase Crashlytics, Sentry, and Bugsnag.

Performance monitoring tools track how well the app is running. They measure:

  • App startup time

  • Screen loading time

  • Network request speed

  • Frame rate and UI performance

Together, crash reporting and performance monitoring help you understand what is happening inside the app after it is released.

Why It Matters

If an app crashes in production and there is no crash reporting system, you may only hear about it through user reviews or support emails.

Without technical details, it becomes very difficult to understand what caused the problem.

Crash reporting tools solve this by capturing a stack trace, which shows exactly where the error occurred in the code. This helps you find and fix the issue much faster.

Real-World Example

Tools like Sentry can record a timeline of events before the crash happens.

They show which screen the user opened, which buttons were tapped, and which network requests were made.

This information helps to quickly understand what the user was doing before the crash.

Trade-offs

Monitoring tools are very useful, but they also add a small amount of overhead to the app.

Each SDK increases the app’s size and may slightly affect startup time. So it is best to use one crash reporting tool and one performance monitoring tool, instead of installing many different ones.

You also need to be careful about user privacy, since crash reports may contain device information or other data.

Practical Tip

You should set up alerts for crash spikes.

If the crash rate suddenly increases after a new release, the system can notify the engineering team immediately. This allows them to quickly investigate and fix the problem before it affects more users.

Monitoring crashes is important, but you also need a way to measure how stable the app is overall.

52. Crash-Free Rate as an SLI

After an app is released, you need a simple way to measure its stability.

One of the most common metrics used for this is the crash-free rate. The crash-free rate shows the percentage of app sessions that finish without a crash.

A session is one complete use of the app, from the moment the user opens it until they close it.

If 1,000 users open the app and 10 of those sessions crash, then 990 sessions were completed successfully.

The crash-free rate would be:

Crash-Free Rate = (Sessions without crash / Total sessions) × 100

So in this example:

990 / 1000 × 100 = 99%

Why It Matters

Crash-free rate gives you a clear way to measure app reliability.

Instead of guessing whether the app is stable, you can track a number that shows how often user experience crashes.

Most mobile apps aim for very high stability. Current industry benchmarks show:

  • 99.95% crash-free sessions are the median across apps (both iOS and Android).

  • 99.9% is the minimum threshold; apps that fall below this threshold are significantly more likely to receive poor store ratings.

  • 99.99% is the target for top-performing teams.

If the crash-free rate drops below the expected level, something in the app may be causing new crashes.

You can then investigate the issue quickly.

How Teams Use It

Engineering teams usually define Service Level Objective (SLO).

An SLO is a reliability goal for the app.

For example, “The app should maintain 99.7% crash-free sessions over the last 7 days.”

Monitoring tools watch this metric and trigger alerts if the crash rate increases.

Real-World Example

Imagine a financial app releases a new update.

The team expects a 99.9% crash-free rate.

After the update goes live, monitoring tools detect that the crash-free rate drops to 99.85%. This triggers an alert for the engineering team. They check the monitoring dashboard and discover that the crashes started after the latest release.

Because the problem was detected early, they can stop the rollout or release a fix quickly before more users are affected.

Trade-offs

The crash-free rate is helpful, but it has one limitation: it shows problems after users have already experienced them.

For this reason, you should combine it with other practices such as:

  • Testing before release

  • Staged rollouts

  • Automated code analysis

These methods help catch problems earlier, before they reach most users.

To reduce the risk of large-scale problems, you must also use safe release strategies that gradually roll out updates instead of sending them to all users at once.

53. Staged Rollouts & Safe Releases

When a new version of a mobile app is ready, it might seem logical to release it to all users at once.

But this can be risky. If the new version contains a bug or causes crashes, millions of users could be affected immediately.

To reduce this risk, you should use a strategy called staged rollout.

A staged rollout releases the new version gradually to a small percentage of users first, instead of everyone at the same time.

A rollout might look like this:

  • 1% of users receive the update

  • then 5%

  • then 20%

  • then 50%

  • and finally 100%

At each stage, monitor important metrics such as crash rate, performance, and user feedback.

If everything looks stable, the rollout continues to the next group of users. If problems appear, the rollout can be paused or stopped before the update reaches everyone.

Why It Matters

Imagine a bug that causes crashes in 2% of sessions:

If the update is released instantly to 100 million users, that could create 2 million bad experiences in one day. But if the update is first released to 1% of users, the issue can be discovered much earlier and fixed before it spreads to the rest of the user base.

This makes releases much safer.

Real-World Example

Both major app stores support staged rollouts:

  • Google Play allows for a gradual increase in the rollout percentage.

  • Apple’s App Store offers phased releases, where updates are distributed over several days.

Many teams start with a small percentage of users and expand the rollout as long as stability metrics remain healthy.

Trade-offs

Staged rollouts allow different users to run different versions of the app simultaneously.

This can sometimes make debugging or customer support slightly more complex because reports may come from multiple app versions.

To handle this, you should track the app version in monitoring dashboards and analytics tools.

Practical Tip

Many teams define automatic safety rules before releasing an update:

  • If the crash-free rate drops below a certain level, pause the rollout.

  • If the ANR (Application Not Responding) rate increases, stop the rollout.

This allows the system to detect problems early and prevent the update from reaching all users.

Staged rollouts allow you to release updates gradually, monitor stability, and fix issues before they reach all users. This helps maintain reliability while continuously improving the app.

Final Thoughts

If you’ve made it through all three parts, you now have a clear mental model of how real mobile systems work, not just when everything goes right, but when things break.

These concepts aren’t separate checklists.

Architecture affects observability, observability affects how safely you release, and release decisions affect how confidently you build.

Everything builds on top of everything else.

One thing worth remembering:

Good engineering is what keeps the app working when things aren’t!

Mobile App
    │
    ▼
 Mobile BFF
    │
    ├── User Service
    ├── Recommendation Service
    ├── Content Service
    └── Notification Service

The mobile app sends a request:

GET /home

The BFF:

  1. calls the required backend services

  2. aggregates the data

  3. transforms it into a mobile-friendly format

  4. returns a single response

Why companies use it:

  • Fewer network requests from mobile devices

  • Lower latency

  • Less battery usage

  • Smaller payloads

  • Frontend teams can evolve APIs without changing core backend services
